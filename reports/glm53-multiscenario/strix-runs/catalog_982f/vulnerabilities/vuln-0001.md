# SQL injection in app.py search() via unparameterized LIKE clause

**ID:** vuln-0001
**Severity:** HIGH
**Found:** 2026-11-20 07:27:59 UTC
**Target:** /workspace/catalog (local project)
**CWE:** CWE-89
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Trivial

## Description

The `search` function in `app.py` builds its SQL query by concatenating the user-controlled `query` argument directly into a `LIKE` clause, allowing SQL injection. The parameterized alternative `search_v2` is not vulnerable, but `search` is independently reachable and injectable.

## Evidence

Observed outputs from the local reproduction (see `poc_script_code`):

- `normal   : [(1, 'public book')]` — baseline honors `published=1`.
- `payload1 : [(1, 'public book'), (2, 'unreleased book')]` — attacker-supplied string returns the row the `published=1` filter is supposed to hide.
- `payload2 : [(1, 'CREATE TABLE products(id INTEGER, name TEXT, published INTEGER)')]` — `sqlite_master` dumped via `UNION SELECT`.
- `v2 attack: []` — the same payloads against `search_v2` return nothing, isolating the concatenation as the root cause.

## Impact

An unauthenticated attacker (the query originates from an HTTP query string) can read the entire database, including products where `published=0`, defeating the documented access-control filter. Demonstrated locally: the injected payload returned the hidden row `(2, 'unreleased book')` and dumped the full schema via a UNION against `sqlite_master`.

## Counterevidence

Actively looked for mitigations: no input validation, sanitization, escaping, or allowlisting is applied to `query` anywhere between the caller and `db.execute`; the query is used verbatim in string concatenation. The only control in the file is the parameterization in `search_v2`, which is a separate function and does not run on the `search` path. Both normal and attack inputs were executed locally to confirm the differential.

## What Would Change This Severity

Confirmation that `search` is exposed on a deployed, internet-reachable endpoint (rather than only invoked internally as in this local synthetic test) would raise exploitability confidence from demonstrated-local to full remote; nothing would lower it short of removing the concatenation.

## Technical Analysis

`search` executes `"SELECT id,name FROM products WHERE published=1 AND name LIKE '%" + query + "%'"`, where `query` originates from an HTTP query string and is concatenated into the SQL text without any validation or escaping. A payload containing a single quote terminates the string literal, allowing arbitrary SQL to be injected. The `published=1` predicate — the application's documented access control for hiding unpublished products — is bypassable because the injected expression (`OR 1=1`) short-circuits it, and a UNION clause allows reading any other table in the database. `search_v2` demonstrates the correct pattern (placeholder binding), confirming the vulnerability is specific to the concatenating implementation and that both functions are individually reviewable versions of the same feature.

## Proof of Concept

1. Import `app` in a local Python process and create the in-memory database with `app.database()`.\n2. Call `app.search(db, "book")` to establish the baseline: only the published product `(1, 'public book')` is returned.\n3. Call `app.search(db, "book' OR 1=1 --")` and observe the unpublished product `(2, 'unreleased book')` is also returned, proving the `published=1` filter is bypassed via injection.\n4. Call `app.search(db, "x' UNION SELECT 1, sql FROM sqlite_master --")` and observe the injected UNION extracts the full schema from `sqlite_master`.\n5. Run the same payloads against `app.search_v2(db, ...)` and observe they return no rows, confirming the parameterized variant is not injectable and isolating the defect to `search`.

```python
import sqlite3
import app

db = app.database()

# Baseline: normal query — only the published product is returned
print("normal   :", app.search(db, "book"))

# Payload 1: injection bypasses the published=1 access-control filter
print("payload1 :", app.search(db, "book' OR 1=1 --"))

# Payload 2: UNION-based extraction of the full schema from sqlite_master
print("payload2 :", app.search(db, "x' UNION SELECT 1, sql FROM sqlite_master --"))

# Control: the same payloads against the parameterized search_v2 return no rows
print("v2 normal :", app.search_v2(db, "book"))
print("v2 attack :", app.search_v2(db, "book' OR 1=1 --"))
```

## Remediation

Replace the string-concatenated query in `search` with the parameterized form already implemented in `search_v2`: pass the user-supplied value as a bound parameter (`db.execute('SELECT id,name FROM products WHERE published=1 AND name LIKE ?', ('%' + query + '%',))`) instead of interpolating it into the SQL string. If `search_v2` is intended as its replacement, remove or gate the legacy `search` function so no reachable code path builds SQL by concatenation; the demonstrated impact is bypass of the `published` access-control filter plus arbitrary read of the database (schema and data disclosure).

## Assumptions

The docstring states the query argument originates from an HTTP query string, so attacker control of the input is part of the application contract. The proof was executed locally with synthetic data per engagement rules, which is representative of the same code path executing in production.
