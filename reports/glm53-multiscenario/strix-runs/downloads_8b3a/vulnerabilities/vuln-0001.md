# Path traversal / arbitrary file read in download() via unvalidated filename

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-11-20 07:29:12 UTC
**Target:** local_code: /home/ec2-user/bedrock/scan/deploy/glm53-ec2/benchmarks/fixtures/downloads (app.py)
**CWE:** CWE-22
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Trivial

## Description

The **`download()`** function in `app.py` joins a user-supplied `filename` onto the administrator-configured `root` without any validation or containment check, allowing arbitrary file reads anywhere the process can access. Both relative traversal sequences (`../../`) and absolute paths (which entirely replace the root when joined) escape the intended download root.

## Evidence

Local Python process executing the module's functions:

```
download benign: b'public-file-content\n'
download absolute RESULT: b'TOP-SECRET-VALUE\n'
download relative traversal RESULT: b'TOP-SECRET-VALUE\n'
download_v2 blocked: PermissionError
```

`download()` returned `TOP-SECRET-VALUE` for a file outside the root via two distinct payload classes; `download_v2()` correctly rejected the same inputs with `PermissionError: outside download root`, serving as the control.

## Impact

An attacker able to supply the `filename` parameter can read any file accessible to the application process, including files outside the download root: credentials, configuration, source code, and other users' data. This fully breaks the documented trust boundary that restricts downloads to the configured root.

## Counterevidence

The docstring confirms the root and ancestors are admin-controlled and clients cannot create symlinks, so symlink races and root-tampering variants are out of contract and were not tested. Absolute-path joining is standard Path behavior, not a framework bug. The only mitigating observation found is that the sibling download_v2 function implements a correct resolve-and-containment check, which shows the intended invariant exists but does not protect the unguarded download() path.

## Confidence Rationale

Working PoC executed in a local Python process with synthetic data, demonstrating arbitrary file read both via relative traversal and absolute-path injection, with a negative control (v2) proving the environment otherwise permits the operation when guarded.

## What Would Change This Severity

If the application were confirmed to run as an unprivileged user in a container with no sensitive files readable, the confidentiality impact would lower; conversely, proof that the filename reaches an unauthenticated network interface would confirm network-reachable exploitation.

## Technical Analysis

In `app.py` line 7, `(Path(root) / filename)` is passed directly to `.read_bytes()`. `pathlib` performs no sanitization of the right-hand operand: a relative payload containing `..` segments escapes the root after resolution, and an absolute `filename` discards the root entirely (pathlib semantics: `Path('/a') / '/b'` yields `/b`). The documented trust boundary (root and ancestors are admin-controlled, no client symlink creation) makes this an attacker-controlled input reaching an unguarded filesystem sink. The sibling function `download_v2` (lines 9-14) implements the correct control — resolve both paths and require `target.is_relative_to(base)` — demonstrating the intended invariant that `download` fails to enforce.

## Proof of Concept

Set up a synthetic download root and a secret file outside it. Call `download(root, filename)` with a benign filename to establish baseline behavior. Then call it with a relative traversal payload (`../../secret/flag.txt`) and an absolute path payload (the direct path to the secret file). Both payload classes return the secret file's contents. Call `download_v2()` with the same payloads as a control and observe it rejects them.

```python
import sys
sys.path.insert(0, '/workspace/downloads')
from app import download, download_v2
from pathlib import Path

base = Path('/tmp/poc_test')
(base / 'root/downloads').mkdir(parents=True, exist_ok=True)
(base / 'secret').mkdir(exist_ok=True)
(base / 'root/downloads/readme.txt').write_bytes(b'public-file-content\n')
(base / 'secret/flag.txt').write_bytes(b'TOP-SECRET-VALUE\n')

root = str(base / 'root/downloads')

print(download(root, 'readme.txt'))                      # baseline: works
print(download(root, '../../secret/flag.txt'))            # traversal: b'TOP-SECRET-VALUE\n'
print(download(root, str(base / 'secret/flag.txt')))      # absolute: b'TOP-SECRET-VALUE\n'

for payload in ['../../secret/flag.txt', str(base / 'secret/flag.txt')]:
    try:
        download_v2(root, payload)
        print('v2 leaked', payload)
    except PermissionError:
        print('v2 blocked:', payload)
```

## Remediation

Replace `download()` with the containment logic already implemented in `download_v2()`: resolve the root once, resolve the joined target, and verify the resolved target is relative to the resolved root (e.g. `Path.is_relative_to`) before opening the file, rejecting otherwise. Alternatively, restrict filenames to a safe character set and reject separators and absolute paths, though the resolve-and-containment approach is the robust fix because it holds after symlink resolution.

## Assumptions

Assumes the filename parameter is client-controlled (per the module docstring) and the attacker knows or can guess a target path; the documented boundary of an immutable admin-configured root is trusted per contract.
