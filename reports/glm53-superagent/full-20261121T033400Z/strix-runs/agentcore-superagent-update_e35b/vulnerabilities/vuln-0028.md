# Non-atomic duplicate-trigger guard in workflow scheduler causes double execution of scheduled workflows

**ID:** vuln-0028
**Severity:** LOW
**Found:** 2026-11-21 04:14:23 UTC
**Target:** super-agent backend (/workspace/agentcore-superagent-update/super-agent/backend)
**CWE:** CWE-367
**CVSS:** 3.1
**Confidence:** Medium
**Fix Effort:** Medium

## Description

The scheduled-workflow trigger guard in the scheduler tick is a non-atomic check-then-act sequence: concurrent or overlapping ticks can both pass it and execute the same schedule twice, causing duplicate workflow executions and duplicate outbound actions (API calls, notifications).

## Evidence

Static trace of the guard chain: `schedule.service.ts:465-485` — `findMany` (no lock) → `findFirst` running check (non-atomic) → `executeSchedule`; `schedule-processor.ts:31-35` — `setInterval(processSchedules, 15000)` with an async handler, so a slow tick overlaps the next; `config/index.ts:108,270` — `PROCESS_ROLE` enum `['all','api','worker','gateway']` documents multi-process worker deployments. No database transaction, advisory lock, or unique constraint guards the fetch-to-execution transition.

## Impact

Duplicate workflow executions: each duplicate run repeats the workflow's action nodes, so outbound api_call requests, messages, or state changes fire twice. For schedules performing payments, notifications, or external mutations this means duplicated real-world side effects. Availability/confidentiality are not affected; integrity impact is limited to duplicated (not arbitrary) actions.

## Counterevidence

Mitigating controls found: the 15-second poll interval means overlap requires processing latency above 15s (atypical for small schedules); a pre-execution status update of next_run_at and last_run_at narrows the window; a skip on existing 'running' executions catches most replays; the provided infra deploys a single EC2 instance with a single systemd backend process, so the multi-instance variant of this race requires an operator-configured PROCESS_ROLE split that no shipped deployment script performs. However, none of these are atomic on the fetch-to-execute path, and the documented PROCESS_ROLE worker split makes concurrent processors a supported configuration, so the guard remains a check-then-act window rather than an enforcing control.

## Confidence Rationale

Static-only trace of the complete non-atomic guard chain; no database or running service available in this isolated assessment to execute a concurrent-tick PoC. Control flow, guard ordering, and absence of any atomicity mechanism (lock, unique constraint, or skipLocked) are fully verified from source.

## What Would Change This Severity

A dynamic demonstration of duplicate executions against a real database (e.g. instrumented concurrency test) would raise confidence and, if duplicates are trivially reproducible with default single-process timing, could raise severity to medium.

## Technical Analysis

`startScheduleProcessor` (src/setup/schedule-processor.ts:31-35) runs `processSchedules` every 15s. `processDueSchedules` (src/services/schedule.service.ts:457-496) fetches due schedules with `findMany` (line 465), then for each schedule performs a separate `findFirst` for an existing `status: 'running'` execution record (line 471) as a duplicate guard, then calls `executeSchedule`. Inside `executeSchedule` (line 501+), `next_run_at` is updated before execution, but this is a plain `update`, not a conditional compare-and-set. There is no transaction, advisory lock, `FOR UPDATE SKIP LOCKED`, or unique constraint linking the fetch, the running-check, and the execution-record creation.

Two failure modes: (1) multi-instance — `config/index.ts:108` explicitly supports `PROCESS_ROLE = 'api' | 'worker' | 'gateway'`, and app.ts:220-225 starts the schedule processor in every process with role `worker` or `all`; two worker processes each fetch the same due rows and both pass the running-check before either has written a running record. (2) single-process overlap — `processSchedules` is an async function invoked by `setInterval` without an in-flight guard, so a tick whose DB round-trips exceed the 15s poll interval overlaps the next tick; JS concurrency allows both invocations to interleave at every `await`, hitting the same window. Impact is duplicate full workflow executions — duplicated outbound `api_call` actions, notifications, and state writes.

## Proof of Concept

1. Enable a workflow schedule with a cron expression that is due immediately.
2. Introduce latency (e.g. many simultaneously-due schedules, or a second worker process via PROCESS_ROLE=worker) so two ticks process the same schedule concurrently.
3. Both ticks pass the running-execution check (findFirst at schedule.service.ts:471) before either has inserted a 'running' record, and both call executeSchedule.
4. Observe two schedule_execution_records and two full workflow executions with duplicated outbound action nodes for a single due trigger.

## Remediation

Make the claim of a schedule atomic at the database level: update next_run_at with a conditional update (`WHERE id = ? AND next_run_at = :expectedNow`) and treat zero affected rows as "another worker claimed it", or wrap fetch-and-claim in a transaction with SELECT ... FOR UPDATE SKIP LOCKED (PostgreSQL), or use a unique partial index on (schedule_id) WHERE status='running' to reject the second execution. Also serialize ticks within a process by guarding processSchedules with an in-flight flag so a slow tick is not re-entered by the 15-second interval.

## Assumptions

Any enabled workflow schedule with side-effecting nodes; requires two overlapping scheduler ticks (high DB latency, many due schedules, or multi-worker deployment with PROCESS_ROLE=worker).
