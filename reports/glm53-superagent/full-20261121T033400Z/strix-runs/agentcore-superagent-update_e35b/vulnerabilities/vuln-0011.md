# Webhook trigger ignores stored secret — unauthenticated workflow execution and public execution-state disclosure

**ID:** vuln-0011
**Severity:** MEDIUM
**Found:** 2026-11-21 04:07:41 UTC
**Target:** super-agent/backend
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Low

## Description

The public webhook trigger endpoint accepts unauthenticated POSTs and never verifies the stored webhook secret, even when one was generated at creation time. The `secret_hash` column is written but no code reads it — a repository-wide search shows zero verification logic. Anyone who learns or guesses a webhook ID can trigger the associated workflow with attacker-chosen variables, and query its execution state through a companion public status endpoint.

## Evidence

Static evidence (white-box, no live service needed):

1. `rg -n "secret_hash|secretHash" -g '*.ts' src` returns only: the interface field (webhook.service.ts:24), generation (77-93), and mapping (524) — no consumer/verification anywhere.
2. The trigger route (webhooks.routes.ts:315-360) passes only `variables`, `headers`, `ipAddress` to `triggerWebhook`; no signature header is read.
3. `triggerWebhook` (webhook.service.ts:129-175) checks only: config exists, isEnabled, and optional IP allowlist.
4. Public status endpoint `GET /v1/webhook/status/:callRecordId` (webhook.routes.ts:362+) returns call status, error message, and full node-by-node execution progress with no authentication.

Local PoC demonstrating the unauthenticated trigger + secret non-verification was not executed against a live DB (no local Postgres seeded in sandbox); the static trace is complete: source (public route) → control (none; secretHash dead) → sink (workflow executor with attacker variables) → impact (arbitrary workflow execution, cost, and any side effects its nodes perform, including the SSRF in the api_call node).

## Impact

Anyone with a webhook ID can: (1) execute the target organization's workflows on demand with arbitrary input variables, consuming LLM/agent compute and triggering whatever side effects the workflow's nodes perform (API calls, document generation, message sending); (2) enumerate/infer workflow behavior through the public status endpoint which exposes node-level execution detail and error messages without authentication. Since webhook IDs appear in URLs (logs, browser history, referrer headers), disclosure risk is realistic.

## Counterevidence

Countervailing design intent: webhooks are deliberately public triggers and the secret generation option exists, so this is partly a design decision. However, the default is no secret (generateSecret is optional and false by default), there is no code path that verifies the hash even when a secret was generated, and the public status endpoint additionally leaks execution state. IP allowlist (allowedIps) exists but is optional and bypassed when unset. No rate limiting on the trigger route was found.

## What Would Change This Severity

Demonstrating a workflow with sensitive side effects (credential use, data modification, external messaging) reachable through a leaked webhook ID on a live deployment would raise severity to high; evidence that webhook IDs are systematically disclosed (e.g. in public logs) would do the same.

## Technical Analysis

`webhook.service.ts` `createWebhook` stores `secret_hash` when `options.generateSecret` is true, and the generated secret is shown once to the creator. But no verification exists: a repository-wide search for `secret_hash`/`secretHash` finds only the write path (lines 24, 77-93, 524) — nothing reads it to validate incoming requests. `triggerWebhook` (lines 129-175) checks only existence, enabled state, and the optional IP allowlist (which is empty by default, and the check is skipped entirely when `payload.ipAddress` is falsy). The trigger route `/v1/webhook/:webhookId/trigger` (webhooks.routes.ts:315) is intentionally unauthenticated but performs no HMAC check even when a secret exists. Additionally `GET /v1/webhook/status/:callRecordId` is public and returns execution details (comment in code: "public, no org check"). Webhook IDs are 24 hex chars (96 bits) — unguessable, but they circulate in URLs.

## Proof of Concept

1. Create a workflow webhook without generateSecret (the default).
2. POST /api/v1/webhook/<webhookId>/trigger with an arbitrary variables object — observe 200 received:true and workflow execution begins.
3. Repeat against a webhook created WITH generateSecret: still succeeds, because secret_hash is never consulted.
4. GET /api/v1/webhook/status/<callRecordId> — returns execution state without authentication.

```gdscript
# Unauthenticated trigger (no signature or secret required)
curl -s -X POST http://<backend>/api/v1/webhook/wh_<webhookId>/trigger \
  -H 'Content-Type: application/json' \
  -d '{"variables": {"attacker": "controlled"}}'
# → {"received":true,"callRecordId":"..."}

# Even with a generated secret, no verification occurs (secret_hash has no consumer):
rg -n "secret_hash|secretHash" super-agent/backend/src -g '*.ts'
# only generation + mapping — no verification code path exists

# Public execution-state disclosure
curl -s http://<backend>/api/v1/webhook/status/<callRecordId>
# → status, errorMessage, and per-node execution progress, unauthenticated
```

## Remediation

Verify the webhook secret on every trigger: require an HMAC-SHA256 signature header (e.g. X-Webhook-Signature) over the raw request body, computed with the stored secret, compared with a timing-safe comparison against the secret hash; reject triggers for webhooks with no configured secret unless the operator explicitly opts the webhook into unauthenticated mode. Add replay protection (timestamp + nonce or timestamp freshness in the signature base). Require authentication (or a capability token) on the /v1/webhook/status endpoint and scope it to the webhook's organization. Add rate limiting to the public trigger route.

## Assumptions

Attacker knows a workflow webhook ID (wh_..., delivered in webhook URLs and potentially leaked in logs/configs). Webhook was created with generateSecret unset or the secret is unknown to the attacker — signature verification is optional and disabled by default in the creation flow.
