# OAuth client secrets encrypted with hardcoded default key; provider upsert accepts arbitrary provider names

**ID:** vuln-0012
**Severity:** LOW
**Found:** 2026-11-21 04:07:52 UTC
**Target:** super-agent/backend
**CVSS:** 3.1
**Confidence:** High
**Fix Effort:** Low

## Description

Per-org OAuth client secrets are "encrypted" with AES-256-GCM using a key derived from `CONNECTOR_ENCRYPTION_KEY`, which defaults to a hardcoded string committed to the repository. Any party who obtains DB rows (or a DB backup) and the public source can decrypt every org's client secrets. Additionally, `oauth-provider-config.service.ts` `upsert` accepts arbitrary provider names with no allowlist — combined with the fact that `getProviderConfig` only hardcodes token URLs for google/salesforce, the door is open for a future per-provider URL field to become fully attacker-controlled.

## Evidence

Source evidence: `src/services/oauth-provider-config.service.ts:11-30`:

```ts title=oauth-provider-config.service.ts startLineNumber=12 endLineNumber=15
function getDerivedKey(): Buffer {
  const secret = process.env.CONNECTOR_ENCRYPTION_KEY ?? 'super-agent-connector-dev-key-change-in-prod';
  return crypto.scryptSync(secret, 'salt', 32);
}
```

The same static salt `'salt'` is used for every org and every secret, so the scrypt derivation is deterministic and precomputable against the known default. Encryption is AES-256-GCM with a random IV per value, but with the key known, decryption is trivial (`decrypt()` in the same file).

`upsert` (lines ~96-125) accepts any `provider` string — no allowlist — writing attacker-named provider rows (currently inert for fetching, but a design risk given getProviderConfig's hardcoded URLs are the only thing preventing attacker-directed token exchanges).

## Impact

Any attacker with database read access (or a leaked backup, or a SQL injection elsewhere) can decrypt all stored OAuth client secrets despite the at-rest encryption claim, then use them to impersonate the org's OAuth applications. Because the encryption key default is public in the repo, the encryption provides no protection in any deployment that has not set CONNECTOR_ENCRYPTION_KEY.

## Counterevidence

Provider names other than google/salesforce are rejected by getProviderConfig before any fetch. Google and Salesforce token URLs are hardcoded to the legitimate vendor endpoints, so an attacker cannot simply add a custom provider row with an arbitrary tokenUrl — the URL is not attacker-controlled in the current code. The exploitable path requires the upsert path to accept a crafted provider value, which I confirmed it does (no provider allowlist in upsert), combined with the fact that getProviderConfig would throw before fetching for unknown names. Checked for other fetch sites driven by db-stored URLs: none found in oauth-flow.service.ts beyond tokenUrl. The primary confirmed defect is the hardcoded default encryption key, which makes the "encrypted" client secrets decryptable by anyone with DB read access or the code; the SSRF angle is a latent design risk rather than a demonstrated exploit.

## What Would Change This Severity

Evidence that the deployment does not set CONNECTOR_ENCRYPTION_KEY (likely, given the dev-default pattern) with DB exposure elsewhere would raise impact; a demonstrated path where a db-stored token/authorize URL becomes fetchable would turn this into SSRF.

## Technical Analysis

`src/services/oauth-provider-config.service.ts:11-15` derives the AES key via `crypto.scryptSync(process.env.CONNECTOR_ENCRYPTION_KEY ?? 'super-agent-connector-dev-key-change-in-prod', 'salt', 32)`. When the env var is unset (the default in dev and any deployment that follows the same pattern as the JWT_SECRET default flagged in the threat model), the key is publicly computable from the source. The `upsert` method (lines ~96-125) performs `prisma.connector_oauth_providers.upsert` with `where: { organization_id, provider }` and no validation of the provider name beyond uniqueness. `oauth-flow.service.ts` `getProviderConfig` only supports 'google' and 'salesforce' with hardcoded authorize/token URLs, so the stored provider name currently cannot redirect the token-exchange fetch — this keeps the immediate SSRF risk latent.

## Proof of Concept

1. Use encrypt() from the service with the default env (no CONNECTOR_ENCRYPTION_KEY set) to encrypt a sample secret.
2. Call decrypt() on the result — round-trip succeeds, proving the key is fully derived from the public default.
3. Confirm no env var is set and the fallback string in source matches the derivation input.

```python
import crypto from 'crypto';

// Exactly the logic in oauth-provider-config.service.ts
function getDerivedKey(): Buffer {
  const secret = process.env.CONNECTOR_ENCRYPTION_KEY ?? 'super-agent-connector-dev-key-change-in-prod';
  return crypto.scryptSync(secret, 'salt', 32);
}
function encrypt(p: string): string {
  const key = getDerivedKey();
  const iv = crypto.randomBytes(12);
  const cipher = crypto.createCipheriv('aes-256-gcm', key, iv);
  const enc = Buffer.concat([cipher.update(p, 'utf8'), cipher.final()]);
  return Buffer.concat([iv, cipher.getAuthTag(), enc]).toString('base64');
}
function decrypt(b: string): string {
  const key = getDerivedKey();
  const raw = Buffer.from(b, 'base64');
  const iv = raw.subarray(0, 12), tag = raw.subarray(12, 28), ct = raw.subarray(28);
  const d = crypto.createDecipheriv('aes-256-gcm', key, iv);
  d.setAuthTag(tag);
  return Buffer.concat([d.update(ct), d.final()]).toString('utf8');
}

const stored = encrypt('super-secret-client-secret');
// Attacker with DB read + public source (no env var set):
console.log('decrypted:', decrypt(stored)); // → super-secret-client-secret
```

## Remediation

Remove the hardcoded fallback for CONNECTOR_ENCRYPTION_KEY and fail closed at startup when it is unset (or generate and persist a random key on first boot); use a per-value random salt for the scrypt derivation instead of the constant 'salt'; add a provider allowlist to the upsert route; rotate all stored client secrets once a proper key is in place since existing ciphertexts are recoverable with the old key.

## Assumptions

Org admin or member with OAuth provider configuration rights, or any flow that can influence stored per-org OAuth provider rows. Default `CONNECTOR_ENCRYPTION_KEY` unchanged.
