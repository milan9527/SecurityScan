# JWT accepted via ?token= query parameter leaks session tokens into logs and referrers

**ID:** vuln-0004
**Severity:** LOW
**Found:** 2026-11-21 04:06:32 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent/backend
**CWE:** CWE-598
**CVSS:** 2.6
**Confidence:** High
**Fix Effort:** Medium

## Description

The authentication middleware accepts JWTs via a `?token=` query parameter, causing full session tokens to appear in URLs — logged by the request logger, stored in server/proxy access logs, browser history, and leaked via Referer headers to any third-party resource on the page.

## Evidence

Source trace: `src/middleware/auth.ts:143` reads `request.query.token`; `src/middleware/requestLogger.ts:53-57` logs the full `url` including query string at info level; `src/app.ts:54` redact list covers only `req.headers.authorization` and `req.headers.cookie`.

## Impact

Session token disclosure through logs (backend.log, pino output, reverse-proxy/CDN access logs), browser history, and Referer leakage to third-party origins. A captured token grants full authenticated API access for up to its 24h lifetime.

## Counterevidence

Production logger redacts only Authorization/cookie headers, not the URL — so `?token=` is logged (src/app.ts:54 redact list; requestLogger.ts:57 logs full url). Impact requires the URL with token to be shared/logged/refered, so it is a leakage amplifier rather than a direct bypass. The endpoint exists intentionally for EventSource/img use; severity is limited by the fact that the app also supports the Authorization header on all routes.

## What Would Change This Severity

Removing query-token logging and limiting the parameter to specific low-risk endpoints would reduce this to informational.

## Technical Analysis

`authenticate` reads a fallback token from the query string (`src/middleware/auth.ts:142-166`) for iframe/img/SSE use cases. `requestLoggerHook` logs `request.url` — including the query string — into the pino log stream at info level (`src/middleware/requestLogger.ts:47-60`), and the production logger's redact list covers only `req.headers.authorization` and `req.headers.cookie` (`src/app.ts:50-55`). Tokens in URLs are also exposed to browser history and Referer headers when the page loads cross-origin resources.

## Proof of Concept

1. Send a request with the token in the query string (`/api/chat/sessions?token=<jwt>`). 2. Observe the request logger emits the full URL including the token (requestLogger.ts:53-57), while the equivalent Authorization-header request is redacted (app.ts:54). Verified by code trace; not executed against a live instance.

```splus
// No network needed: demonstration of the logging differential
// requestLogger.ts:57 logs: { method: 'GET', url: '/api/chat/sessions?token=eyJhbG...' }
// app.ts:54 redact: ['req.headers.authorization', 'req.headers.cookie']  <- URL not redacted
console.log('token in query string is logged verbatim; token in Authorization header is redacted');
```

## Remediation

Restrict query-param auth to the specific endpoints that need it (SSE/EventSource under /api/chat and image/avatar routes), reject it elsewhere, and prefer short-lived single-purpose tokens for those flows. Redact query strings containing tokens from the request logger, and set a strict Referrer-Policy on HTML responses.

## Assumptions

Browser-based access where a token-authorized URL is loaded as a subresource or navigated to; requires a victim holding (or being issued) a valid token.
