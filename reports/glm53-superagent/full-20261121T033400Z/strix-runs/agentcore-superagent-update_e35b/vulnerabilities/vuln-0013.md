# Path traversal to arbitrary file write via unvalidated skill name in workspace provisioning

**ID:** vuln-0013
**Severity:** HIGH
**Found:** 2026-11-21 04:09:18 UTC
**Target:** super-agent backend (/workspace/agentcore-superagent-update/super-agent/backend)
**CWE:** CWE-22
**CVSS:** 8.8
**Confidence:** High
**Fix Effort:** Low

## Description

Skill names are never validated or sanitized. A name containing `../` (fully attacker-controlled via the skill zip upload endpoint or marketplace install reference) is joined into filesystem paths without any containment check in `WorkspaceManager.installSkillToWorkspace` and `WorkspaceManager.downloadSkill`, so skill provisioning copies attacker-controlled files (arbitrary content from the uploaded zip) to arbitrary directories outside the session workspace — an arbitrary file write with controlled content on the backend host.

## Evidence

PoC harness output (real `WorkspaceManager` imported from the repo, base dir `/tmp/fs-poc/base`, skill name `../../../../../../../..\/pwned-by-skill`):

```text
[1] installSkillToWorkspace returned without error
```

```text
$ ls -la /tmp/pwned-by-skill/
-rw-r--r-- 1 pentester pentester 12 Nov 21 04:08 SKILL.md
$ cat /tmp/pwned-by-skill/SKILL.md
pwned skill
```

The write landed completely outside the configured workspace base directory, and the file content (`pwned skill`) was attacker-supplied. The same unguarded `join` also exists at workspace-manager.ts:969 (`downloadSkill`), reachable from every new chat session via `ensureSessionWorkspace`.

## Impact

Arbitrary file write with attacker-controlled content anywhere the backend process can write. Because the zip upload controls both the name and the file contents of the skill, an authenticated user can overwrite backend data, configuration, or user-level execution hooks (e.g. `~/.bashrc`, systemd user units, cron entries, or other service files writable by the backend user), leading to code execution on the backend host. The S3 mirror at skill-marketplace.routes.ts:197 builds `destKey` from the same unsanitized name, so the traversal additionally escapes the per-session S3 key prefix and can overwrite arbitrary workspace-bucket objects in agentcore deployments.

## Counterevidence

Checked for mitigations on every path: no skill-name validation exists anywhere between zip ingest (`installFromZip`), DB storage (`skillService.createSkill`), and provisioning (`installSkillToWorkspace`/`downloadSkill`) — no regex, allowlist, or sanitization was found. The traversal check that does exist in the same file (`deleteWorkspaceSkill` line 1416 `skillDir.startsWith(...)`) is not applied to install paths, and even that check lacks a trailing-separator boundary. The cp source `localPath` is server-generated (hash id) but its *contents* are attacker-supplied from the zip, so content control is confirmed. Env constraint: file contents must pass as a "skill" — no constraint, since any files in the zip's skill directory are copied verbatim (only SKILL.md presence is required for discovery). The write occurs outside the process only at install/session-creation time — both reachable via normal API use (install with `sessionId`, or starting a chat session on a scope with the skill assigned/bound).

## What Would Change This Severity

Demonstrating the overwrite of an execution hook (e.g. systemd user unit or shell startup file) with subsequent backend-user code execution would raise this to critical; a deployment where the backend runs as a fully sandboxed, read-only-root user would lower it.

## Technical Analysis

`POST /api/skills/marketplace/upload-zip` accepts an archive, extracts it, and derives the skill `name` from the parent directory of each discovered `SKILL.md` (`src/services/skill-marketplace.service.ts:826`) with no character or path validation; the same is true of the `installRef`-derived name in `install()` (`:384`). The stored name is later used verbatim as a path component:

- `src/services/workspace-manager.ts:1360-1361` — `installSkillToWorkspace` does `const targetDir = join(skillsDir, skillName); await cp(sourcePath, targetDir, { recursive: true })` with no containment check. Called from `src/routes/skill-marketplace.routes.ts` after every marketplace install with a `sessionId`.
- `src/services/workspace-manager.ts:969` — `downloadSkill` does `const skillDir = join(targetDir, skill.name)` and copies from the skill's `localPath` (whose contents come from the uploaded zip) — executed for every skill on every new session via `ensureSessionWorkspace`.

`join()` resolves `..` segments, so a name such as `../../../../tmp/x` escapes the workspace entirely. Only `deleteWorkspaceSkill` performs a (flawed, separator-less) `startsWith` check; install/copy paths have none. The skill *contents* are attacker-controlled end-to-end: the zip's skill directory is copied verbatim into the permanent skill store and then re-copied to the traversal target.

## Proof of Concept

1. Import the real `WorkspaceManager` from the repository and instantiate it with a scratch base directory.
2. Create a source skill directory containing an attacker-chosen `SKILL.md`.
3. Call `installSkillToWorkspace(orgId, scopeId, sessionId, skillName, sourcePath)` — the exact call made by `POST /api/skills/marketplace/install` with a `sessionId` — with `skillName` set to `../../../../../../../..\/pwned-by-skill`.
4. Observe the method returns without error and the file `/tmp/pwned-by-skill/SKILL.md` exists with the attacker-supplied content, entirely outside the workspace base directory.
5. Reachability of the name: upload a zip to `POST /api/skills/marketplace/upload-zip` whose skill directory is named with `../` segments — `installFromZip` derives the stored skill `name` verbatim from that directory name (skill-marketplace.service.ts:826), so the traversal name is persisted and later replayed into `join()` at provisioning time.

```python
// /tmp/fs-poc/harness.ts — run with: npx tsx /tmp/fs-poc/harness.ts (from super-agent/backend)
import { mkdir, writeFile, rm } from 'fs/promises';
import { join } from 'path';

const BASE = '/tmp/fs-poc/base';
const { WorkspaceManager } = await import(
  join(process.cwd(), 'src/services/workspace-manager.ts')
);
const wm = new WorkspaceManager(BASE);

const src = '/tmp/fs-poc/src-skill';
await rm(src, { recursive: true, force: true });
await mkdir(src, { recursive: true });
await writeFile(join(src, 'SKILL.md'), 'pwned skill\n');

await rm(BASE, { recursive: true, force: true });

// attacker-controlled skill name (from uploaded zip directory name)
const evilName = '../../../../../../../..\\/pwned-by-skill';

await wm.installSkillToWorkspace('org-1', 'scope-1', 'sess-1', evilName, src);
// -> /tmp/pwned-by-skill/SKILL.md created outside BASE
```

## Remediation

Validate skill names at the trust boundary: reject any skill name containing path separators, `..`, backslashes, absolute-path prefixes, or characters outside `[A-Za-z0-9._-]` when a skill is created (`installFromZip`, `install`, `createScopeLevelSkill`, scope-generator confirm). Independently, enforce containment at the sink: in `installSkillToWorkspace` and `downloadSkill`, resolve the target and verify `resolved === skillsDir || resolved.startsWith(skillsDir + path.sep)` before `cp`/`writeFile` (the same boundary-corrected check should replace the separator-less `startsWith` used elsewhere in the file). Apply the identical validation to the S3 key construction in the marketplace and enterprise-skill sync paths so a traversal name cannot escape the per-session prefix.

## Assumptions

Authenticated org member (any role with skill-install permissions; upload-zip and install routes only require `authenticate`). Default `AGENT_RUNTIME=claude` deployment is affected for the filesystem write; no agentcore configuration needed.
