# IM webhook signature verification fails open — unauthenticated message injection into agent sessions

**ID:** vuln-0026
**Severity:** MEDIUM
**Found:** 2026-11-21 04:13:15 UTC
**Target:** super-agent/backend
**CWE:** CWE-287
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Low

## Description

IM inbound webhook signature verification fails open: Slack, Telegram, DingTalk, Feishu and WhatsApp adapters return true when no secret is configured, and Discord/WeCom adapters always return true, so unauthenticated POSTs to the public /api/im/* webhook routes are accepted and injected into the org's agent chat pipeline whenever a binding exists without a stored secret.

## Evidence

Adapter code executed directly (project's own TS sources, isolated local sandbox, tsx): `SlackAdapter.verifyRequest({}, body)` → true, `TelegramAdapter.verifyRequest({}, body)` → true, `DingTalkAdapter.verifyRequest({}, body)` → true, `WhatsAppAdapter.verifyRequest({}, body)` → true (all with no headers — the fail-open branch). Control: Slack with a configured secret and a forged signature → false, confirming the check is real but only the unconfigured branch fails open. WeCom and Discord adapters structurally return true unconditionally (wecom-adapter.ts:177, discord-adapter.ts:23). Route chain: im.routes.ts verifyAndLookupBinding (lines 226-271) looks up the binding globally (no org) and calls adapter.verifyRequest; dedicated routes at im.routes.ts:290-433 (/api/im/slack/events, /api/im/telegram/webhook, /api/im/feishu/events, /api/im/dingtalk/callback) then call imService.handleMessage → chatService.processMessage with the binding's org/scope/created_by (im.service.ts:171-290).

## Impact

An unauthenticated remote attacker who can reach the webhook URLs can inject arbitrary text into the target organization's agent chat sessions. The message is processed with the binding creator's identity and the org's full agent configuration — credentialed agents, tools, MCP servers and workflows act on attacker-chosen instructions. This is a trust-boundary break: the design intends only the verified IM platform to reach this path. It is not a new server-side code-execution primitive by itself.

## Counterevidence

Controls that do exist: bindings must exist and be enabled; WeCom message callbacks and the WhatsApp verification challenge do enforce secret checks; Slack/Telegram/WhatsApp perform real timing-safe HMAC when a secret is configured (demonstrated). No WAF or additional signature middleware wraps these routes. The main constraint is the prerequisite that the binding's secret is unset — bindings created with secrets configured are protected on the strict-verification platforms. Discord/WeCom generic-webhook reachability additionally requires guessing the binding UUID. No org check exists anywhere on the webhook path (findByChannelTypeAndId is global), so once the precondition holds the path is fully unauthenticated.

## What Would Change This Severity

Confirmation that deployments commonly create bindings without secrets (e.g. the admin UI does not require signing_secret/app_secret/secret_token at binding creation) would firm up exploitability; discovery of an additional unauthenticated route that lists binding channel_ids would raise severity to high.

## Technical Analysis

The inbound chain is `imWebhookRoutes` (im.routes.ts, mounted at `/api/im`, routes/index.ts:255). Each platform route parses the payload to extract `channelId`, then `verifyAndLookupBinding` (im.routes.ts:226-271) loads the binding via `imChannelRepository.findByChannelTypeAndId` — a global lookup with no org scoping — injects the binding's stored secret (e.g. `config.signing_secret` → `x-slack-signing-secret-internal` header, im.routes.ts:243-260), and calls `adapter.verifyRequest`. Every adapter's fail-open behavior: Slack (slack-adapter.ts:39-42, `if (!signingSecret) return true`), Telegram (telegram-adapter.ts:31-34, `if (!secret) return true`), DingTalk (dingtalk-adapter.ts:80-83), WhatsApp (whatsapp-adapter.ts:66-69, `if (!appSecret) return true`), Feishu (feishu-adapter.ts:104-107, `if (!token) return true`), Discord (discord-adapter.ts:23-27, always true), WeCom generic path (wecom-adapter.ts:177-180, always true). When the secret is absent from the binding's `config`, no internal header is injected, so `verifyRequest` hits the fail-open branch and accepts the request. Secrets come only from the operator-entered `config` on binding create/update (im.routes.ts:84-175) — there is no server-side requirement that a secret exist, so a fresh binding created via the admin UI without filling the secret fields is unprotected by default. On success, `imService.handleMessage` (im.service.ts:171) resolves the binding, creates/reuses a thread session, and calls `chatService.processMessage` with the binding's `organization_id`, `business_scope_id` and `created_by` as the effective user — i.e. full agent authority under the org, driven entirely by attacker-supplied text. The generic `POST /api/im/webhook/:bindingId` (im.routes.ts:735-772) additionally accepts arbitrary `{text}` for any enabled binding with no verification at all (binding UUID is the only barrier). Counterpoints: WeCom Agent-mode message callbacks do perform real signature+AES verification (im.routes.ts:494-540), and the WhatsApp GET verification challenge checks `verify_token` — so those paths are stricter; the exposure is the fail-open branches and the always-true adapters above.

## Proof of Concept

Run the project's own adapters against an unauthenticated request (no headers, no secret configured). Observe verifyRequest returns true. For the route-level effect, POST a well-formed platform payload (e.g. Slack message_create event with the target channel_id) to /api/im/slack/events — parseEvent yields a message, verifyAndLookupBinding finds the binding and the adapter passes, and imService.handleMessage injects the text into the org's agent session.

```python
// /tmp/poc-oi/run.ts — executed against the repo's own adapters
import { SlackAdapter } from './slack-adapter.js';
import { TelegramAdapter } from './telegram-adapter.js';
import { DingTalkAdapter } from './dingtalk-adapter.js';
import { WhatsAppAdapter } from './whatsapp-adapter.js';

const body = JSON.stringify({ event: { text: "forge agent message" } });

// binding config has NO signing secret -> im.routes.ts injects no internal
// header -> adapter sees no secret -> returns true with zero auth material
console.log('Slack    no-secret:', new SlackAdapter().verifyRequest({}, body));    // true
console.log('Telegram no-secret:', new TelegramAdapter().verifyRequest({}, body)); // true
console.log('DingTalk no-secret:', new DingTalkAdapter().verifyRequest({}, body));  // true
console.log('WhatsApp no-secret:', new WhatsAppAdapter().verifyRequest({}, body));  // true

// control: with a configured secret, a forged signature is rejected
console.log('Slack forged sig w/ secret:', new SlackAdapter().verifyRequest(
  { 'x-slack-signing-secret-internal': 'real-secret',
    'x-slack-request-timestamp': String(Math.floor(Date.now()/1000)),
    'x-slack-signature': 'v0=' + 'a'.repeat(64) }, body));                         // false

// HTTP injection (unauthenticated):
// POST /api/im/slack/events
// {"type":"event_callback","event":{"type":"message","channel":"C0123456789","text":"run the reporting agent","user":"U1"}}
```

## Remediation

Make verification fail closed: if no secret is configured for a binding that supports signature verification, reject the inbound message (or refuse to enable the binding until a secret is stored). For adapters that genuinely cannot verify HTTP callbacks (Discord/WeCom gateway modes), disable their dedicated HTTP callback routes or require a per-binding shared secret on the generic /api/im/webhook/:bindingId path instead of returning true. Additionally, scope binding lookup by organization where the route carries org context.

## Assumptions

Attacker can reach the backend's IM webhook endpoints over the network and at least one IM channel binding exists with no signature secret stored in `config` (or is a discord/wecom binding). Credentialed agent operations must already be configured for the scope. Intended use by the real IM platform is not affected by the fix.
