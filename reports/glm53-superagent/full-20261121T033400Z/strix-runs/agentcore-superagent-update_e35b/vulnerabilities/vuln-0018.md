# Cross-tenant access-control gaps in scope memberships, scope plugin/MCP listings, and scope connector bindings

**ID:** vuln-0018
**Severity:** HIGH
**Found:** 2026-11-21 04:10:58 UTC
**Target:** super-agent/backend (local repository /workspace/agentcore-superagent-update)
**CWE:** CWE-639
**CVSS:** 8.3
**Confidence:** High
**Fix Effort:** Medium

## Description

Three authorization gaps around business scopes: (1) PATCH/DELETE /api/business-scopes/:id/members/:membershipId update or delete a scope membership by primary key only, letting a scope-admin in Org A grant themselves any role in (or strip members from) any scope in Org B; (2) GET /api/business-scopes/:id/plugins and /:id/mcp-servers return cross-tenant data via raw SQL with no organization predicate; (3) GET /api/data-connectors/scopes/:scopeId/connectors returns another org's connectors and their configurations.

## Evidence

Vitest PoC (/tmp/idor-poc/scope-poc.test.ts, 3/3 passing) with mocked prisma: scopeAccessService.updateMemberRole('membership-in-victim-org','admin') -> prisma.scope_memberships.update({where:{id:'membership-in-victim-org'}}) with no organization_id; removeMember -> delete({where:{id}}). Source: businessScopes.routes.ts:821-833 (plugins raw SQL `WHERE sp.business_scope_id = ${id}::uuid` with orgId captured but unused), :938-953 (mcp-servers raw SQL joining mcp_servers with no org filter), scopeMemberships.routes.ts:125/141 (membershipId passed straight through), :168-171 (business_scopes.update by {id} only), connectors.routes.ts:127 + data-connector.service.ts:117-119 + data-connector.repository.ts:106-113 (findScopeConnectors by business_scope_id only).

## Impact

Cross-tenant privilege escalation (attacker scope-admin elevates their own or any account's role in a victim org's restricted scope, gaining access to that scope's agents, data connectors, document groups and chat workflows), cross-tenant data disclosure (MCP server host addresses and scope configs, plugin git URLs, connector configurations), and cross-tenant state tampering (visibility changes and membership removal).

## Counterevidence

Checked whether the requireScopeAccess('admin') preHandler on PATCH/DELETE :id/members/:membershipId verifies the target membership's org: the middleware's defaultExtractor reads only params.id/params.scopeId, and scopeAccessService.getAccessLevel scopes the check to the user's own org — so passing a victim-org scopeId in :id correctly fails, which is why the attack targets :membershipId instead. The raw-SQL GET endpoints have no scopeAccessService call at all (contrast with /:id/agents and /:id/skills which call it), confirming these were simply missed.

## What Would Change This Severity

Confirmation that restricted scopes hold regulated data or that scope_config embeds credentials for MCP servers would raise impact; a database-level tenant RLS policy would lower it.

## Technical Analysis

Root cause 1 — scopeMemberships.routes.ts:122-127 and 137-142 call `scopeAccessService.updateMemberRole(membershipId, role)` / `removeMember(membershipId)`, which delegate to `scopeMembershipRepository.updateRole` (scopeMembership.repository.ts:86-91) and `.delete` (:96-98). Both issue `prisma.scope_memberships.update/delete({ where: { id } })` with no organization predicate. The requireScopeAccess('admin') guard only validates the `:id` scope param against the attacker's org — the `:membershipId` row is never tied back to that scope or org. Root cause 2 — businessScopes.routes.ts GET '/:id/plugins' (:815-833) and GET '/:id/mcp-servers' (:935-953) execute raw SQL filtering only on `business_scope_id`; the sibling endpoints '/:id/agents' and '/:id/skills' do call scopeAccessService.requireAccess, these two do not. Root cause 3 — scopeMemberships.routes.ts:150-171 `business_scopes.update({ where: { id } })` for visibility has no org predicate (unlike the adjacent raw-SQL config_version bump which includes organization_id). Root cause 4 — connectors.routes.ts:126-129 passes scopeId to `getScopeConnectors` which queries `scope_data_connectors` by business_scope_id only (data-connector.repository.ts:106-113), including the full connector record.

## Proof of Concept

1. Authenticate as a scope-admin in Org A (admin of any scope in your org to pass requireScopeAccess('admin')). 2. PATCH /api/business-scopes/:myScopeId/members/:victimMembershipId with {role:'admin'} — updateMemberRole updates scope_memberships by {id} with no org predicate, elevating the attacker's account to admin of the victim org's restricted scope. 3. DELETE the same endpoint with a victim membership id to evict members from another org's scope. 4. GET /api/business-scopes/:victimScopeId/plugins and /:victimScopeId/mcp-servers — raw SQL selects by business_scope_id only, returning the victim org's MCP server host addresses, configs and plugin git URLs. 5. GET /api/data-connectors/scopes/:victimScopeId/connectors returns the victim org's connectors including scope_config. 6. PATCH /api/business-scopes/:victimScopeId/visibility flips another org's scope between open/restricted.

## Remediation

Resolve the membership row (or scope) first and verify its organization_id equals request.user.orgId inside updateMemberRole/removeMember/visibility handlers; add organization_id join predicates to the raw SQL plugin/MCP-server listings and to findScopeConnectors; scope the scope_mcp_servers delete/config updates by joining business_scopes.organization_id rather than only checking scope ownership on a separate statement.

## Assumptions

Assumes an authenticated member of one organization who is scope-admin of at least one business scope in their own org (for the membership-write paths) or simply any authenticated user (for the raw-SQL read paths), plus a victim scope/membership UUID.
