# Cross-tenant IDOR in knowledge-base service: all operations keyed by primary key without organization scoping

**ID:** vuln-0016
**Severity:** HIGH
**Found:** 2026-11-21 04:10:49 UTC
**Target:** super-agent/backend (local repository /workspace/agentcore-superagent-update)
**CWE:** CWE-639
**CVSS:** 8.3
**Confidence:** High
**Fix Effort:** Medium

## Description

The knowledge-base service queries and mutates knowledge bases, knowledge files, and scope-knowledge bindings strictly by primary key with no organization_id predicate, while the routes pass only the attacker-supplied id. Any authenticated member of any organization can read, rename, soft-delete, or re-bind another tenant's knowledge bases and delete their files by ID.

## Evidence

Vitest PoC (/tmp/idor-poc/kb-poc.test.ts, 5/5 passing) with a mocking proxy recording Prisma where-clauses: kb.findUnique where={id:'kb-belongs-to-victim'} (no organization_id), kb.update where={id:'kb-belongs-to-victim'} data={name:'pwned'}, bindings.findMany where={scope_id:'scope-victim'}, bindings.create data={scope_id:'scope-victim', knowledge_base_id:'kb-victim'}, file.delete where={id:'file-victim'}. The mocked findUnique returned organization_id 'ORG-VICTIM' and the service returned it to the caller unchanged, demonstrating cross-tenant disclosure. Output: "Test Files 1 passed (1) Tests 5 passed (5)".

## Impact

Cross-tenant (cross-organization) read of knowledge base metadata and file listings, unauthorized rename/soft-delete of other orgs' knowledge bases, deletion of other orgs' knowledge files, and binding of another org's knowledge base to an arbitrary scope — integrity and confidentiality violation of tenant data.

## Counterevidence

Verified no route-level org predicate wraps these calls: the /:id, PUT/DELETE, /scope/:scopeId/* handlers in knowledge-base.routes.ts call the service with only the raw id. Checked whether any global Fastify hook adds scoping (routes/index.ts registers route-level preHandlers only) and whether the service applies org filtering in a wrapper — it does not; org-scoped methods (listByOrganization, create) are separate. Knowledge of a victim UUID is required (not returned by the attacker-org list endpoint), which limits blind enumeration but not targeted attacks.

## What Would Change This Severity

Confirmation that knowledge file records embed S3 object keys or file content in responses would confirm broader data exfiltration; conversely a global tenant row-level-security policy on the database would reduce exploitability.

## Technical Analysis

Knowledge base service methods accept a bare id and issue Prisma calls with only that key. `knowledge-base.service.ts:69-71` — `findById` runs `prisma.knowledge_bases.findUnique({ where: { id } })`; `:80-88` — `update` runs `update({ where: { id } })`; `:91-97` — `delete` soft-deletes by id; `:103-117` — `bindToScope`/`unbindFromScope` create/delete scope_knowledge_bindings rows keyed only by scope_id/knowledge_base_id; `:119-124` — `getScopeBindings` lists by scope_id with the full knowledge_base included; `:277-302` — `updateFile`/`deleteFile`/`batchDeleteFiles` operate on knowledge_files by id only. Routes in `knowledge-base.routes.ts` (GET/PUT/DELETE `/:id` at lines 59-89, GET `/:id/files` at 337, GET `/scope/:scopeId/bindings` at 94-97, POST `/scope/:scopeId/bind` at 109-120, DELETE `/scope/:scopeId/unbind/:kbId` at 128-133, PUT/DELETE `/:id/files/:fileId` at 370-396) pass only the path id plus the caller's user id for audit fields — the caller's `orgId` is never supplied to the service. Only the list (`listByOrganization`) and create paths are org-scoped. Root cause: the knowledge-base module was written without the BaseRepository tenant pattern used everywhere else in the codebase.

## Proof of Concept

1. Authenticate as a member of Org A. 2. Call GET /api/knowledge-bases/:id with the UUID of a knowledge base belonging to Org B — the handler calls knowledgeBaseService.findById(id) which runs prisma.knowledge_bases.findUnique({where:{id}}) with no org filter, returning the victim record. 3. Call PUT /api/knowledge-bases/:id with {name:'pwned'} — prisma update by {id} only. 4. Call DELETE /api/knowledge-bases/scope/:victimScopeId/bindings/:kbId to strip another org's bindings, or POST .../bind with arbitrary scope and KB ids to cross-link tenants. 5. DELETE /api/knowledge-bases/:victimKbId/files/:victimFileId deletes the victim file by primary key.

## Remediation

Thread the caller's organization_id through knowledgeBaseService.findById/update/delete/bindToScope/unbindFromScope/getScopeBindings and the file operations, and enforce it as a predicate in every Prisma where clause (mirroring BaseRepository.findById). At the route layer, reject ids that do not belong to request.user.orgId before any read or write.

## Assumptions

Assumes an authenticated low-privilege member of one organization and knowledge of a victim knowledge base / file / scope UUID (obtainable from exports, logs, or prior membership).
