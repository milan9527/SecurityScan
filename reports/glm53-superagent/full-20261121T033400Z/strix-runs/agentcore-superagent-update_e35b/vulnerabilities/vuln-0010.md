# Unrestricted SSRF via MCP server connection test endpoint

**ID:** vuln-0010
**Severity:** MEDIUM
**Found:** 2026-11-21 04:07:28 UTC
**Target:** super-agent/backend
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Low

## Description

The MCP server connection test (`POST /api/mcp/servers/:id/test`) performs a server-side `fetch()` to a fully user-controlled URL (the server's `host_address` or `config.url`) with no SSRF protections: no internal-IP denylist, no scheme restriction, and redirects followed by default. This gives any authenticated user a server-side request primitive to internal networks and cloud metadata.

## Evidence

Local PoC executed in the sandbox (isolated local analysis only):

```js
// /tmp/ssrf-poc/mcp_service_poc.test.js — vitest
import { describe, it, expect } from 'vitest';
import http from 'node:http';
import { McpServerService } from '/workspace/agentcore-superagent-update/super-agent/backend/src/services/mcp.service.js';

describe('MCP testMcpServerConnection SSRF', () => {
  it('HEAD-fetches arbitrary internal URL from user input', async () => {
    let hit = null;
    const srv = http.createServer((req, res) => {
      hit = { method: req.method, path: req.url };
      res.writeHead(200); res.end();
    });
    await new Promise(r => srv.listen(0, '127.0.0.1', r));
    const port = srv.address().port;

    const svc = new McpServerService();
    const fakeServer = {
      id: 'srv-1', organization_id: 'org-1',
      host_address: `http://127.0.0.1:${port}/internal/metadata`,
      config: null, headers: { 'X-Internal-Auth': 'backend-trusts-itself' },
    };
    const repo = await import('/workspace/agentcore-superagent-update/super-agent/backend/src/repositories/mcp-server.repository.js');
    const orig = repo.mcpServerRepository.findById;
    repo.mcpServerRepository.findById = async () => fakeServer;
    try {
      const result = await svc.testMcpServerConnection('srv-1', 'org-1', 3000);
      expect(result.success).toBe(true);
      expect(hit).toEqual({ method: 'HEAD', path: '/internal/metadata' });
    } finally {
      repo.mcpServerRepository.findById = orig;
      srv.close();
    }
  });
});
```

Result: the local "internal" server received a HEAD request for the attacker-chosen path with the attacker-set header; `result.success` was true, and the round-trip latency is returned to the caller. This proves the backend fetches arbitrary user-supplied internal URLs with zero validation. Local reproduction does not by itself prove production exploitability.

## Impact

Authenticated users can probe internal networks from the backend's network position: reach cloud metadata endpoints (169.254.169.254), map internal services via status/latency oracles, and reach internal admin endpoints. The response body is not returned directly, but error messages (e.g. connection failures, status codes) distinguish open/closed services, forming an internal port scanner. The same `config.url`/`host_address` may also be fetched by other MCP client code paths with more request control.

## Counterevidence

Checked the full mcp.service.ts and mcp.routes.ts for any URL validation before the fetch — none exists (no allowlist, denylist, scheme check, or IP pinning). Guard present: creation and test routes require `authenticate` (+ `requireModifyAccess` for create), so this is authenticated SSRF. Mitigating constraint: the test endpoint performs only a HEAD request and returns only latency/status to the caller, not the response body, which limits direct data exfiltration through this specific route — though status/latency differences still form a usable internal port/service scanner, and other code paths that invoke MCP servers may send more.

## What Would Change This Severity

Confirmation that other code paths invoke MCP servers with full request bodies/methods and return response bodies to the caller would raise this to high.

## Technical Analysis

`src/routes/mcp.routes.ts:362-401` (`POST /servers/:id/test`, authenticated) calls `mcpServerService.testMcpServerConnection(id, orgId)`. In `src/services/mcp.service.ts:276-310`, the URL is taken directly from `config?.url` or `server.host_address` — both stored from user input at server creation (mcp.routes.ts create handler) — and passed to `fetch(url, { method: 'HEAD', headers: server.headers })`. There is no validation of scheme, host, or IP range anywhere in the path. `server.headers` are also stored user input, so attacker-controlled headers reach the internal target. Node fetch follows redirects by default.

## Proof of Concept

1. Start a local HTTP server on 127.0.0.1 simulating an internal-only service.
2. Instantiate McpServerService and stub the repository to return a server entity whose host_address points at that local URL, with a custom header.
3. Call testMcpServerConnection; observe the internal server receives the HEAD request and the method returns success with latency.

## Remediation

Validate the resolved IP of `config.url` / `host_address` against a blocklist (loopback, link-local including 169.254.169.254, RFC1918, IPv6 equivalents) before every server-side fetch of user-supplied URLs; pin the scheme to http(s); do not follow redirects (or re-validate each hop); resolve DNS once and connect to the validated IP to prevent DNS rebinding. Apply the shared validation utility across all fetch sites in the codebase.

## Assumptions

Authenticated org member with MCP server creation rights. No egress filtering or SSRF guard present on the path.
