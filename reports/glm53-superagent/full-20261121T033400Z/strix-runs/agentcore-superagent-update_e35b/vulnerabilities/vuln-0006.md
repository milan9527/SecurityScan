# Cognito first-login email binding enables account takeover via unverified email claim

**ID:** vuln-0006
**Severity:** MEDIUM
**Found:** 2026-11-21 04:06:48 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent/backend
**CWE:** CWE-284
**CVSS:** 6.8
**Confidence:** Medium
**Fix Effort:** Medium

## Description

On first Cognito login, the backend binds a verified id_token to an existing local profile by matching the token's email claim against `profiles.username` and reassigns all of that profile's rows (memberships, chats, API keys, workflows) to the Cognito sub. If the user pool permits accounts whose email claim is not verified or is attacker-controlled, an attacker can take over any existing profile — including the admin — without knowing its password.

## Evidence

Source: `src/middleware/auth.ts:196-224` — email binding plus raw SQL row reassignment (memberships, chat_sessions, tasks, workflows, workflow_executions, api_keys, skill_votes, profiles.id). Verifier config (auth.ts:17-21) does not check `email_verified`. Not dynamically reproducible in this isolated assessment (would require a configured Cognito pool).

## Impact

Pre-authentication account takeover of any profile whose username equals an email the attacker can claim in the Cognito pool — including the seeded `admin@example.com` owner — inheriting all memberships, roles, chat history, and API keys.

## Counterevidence

`aws-jwt-verify` is used correctly for signature, issuer, audience, and tokenUse (auth.ts:17-21), so the token itself must be legitimately issued by the pool. The takeover depends on the pool's email-verification setting — if the pool requires verified emails and forbids duplicate emails, the binding is safe. `adminCreateUser` (cognito-admin.service.ts:51-52) sets email_verified=true, suggesting the intended config does verify emails. The migration also runs only when no profile with the Cognito sub exists (first login). Impact is therefore conditional on pool configuration, which could not be verified in this isolated assessment.

## Confidence Rationale

Static-only trace of the binding flow; no live Cognito pool was available to test whether unverified or attacker-controlled emails can produce valid id_tokens in the actual deployment's pool configuration.

## What Would Change This Severity

Confirmation of the deployed pool's email-verification and uniqueness settings would settle this: a pool requiring verified unique emails drops it to no-issue; a pool allowing unverified or self-set emails confirms account takeover.

## Technical Analysis

In `authenticate` (src/middleware/auth.ts:196-224), when no profile exists for the Cognito `sub`, the code looks up a profile by `username == claims.email` and, if found, migrates ownership of memberships, chat sessions, tasks, workflows, workflow executions, API keys, and skill votes to the new Cognito sub via raw SQL. The Cognito verifier (auth.ts:13-23) checks signature/audience/tokenUse but does not check the `email_verified` claim. Additionally, JWT claims `custom:orgId` and `custom:role` are trusted as fallbacks for org/role when no membership exists (auth.ts:242-243) — these attributes are set via AdminCreateUser (cognito-admin.service.ts:53-54) but are user-attributes in the pool; if the pool allows users to edit their own custom attributes, this is another claim-injection path (unverified).

## Proof of Concept

Not executed — requires a live Cognito pool. Code path: register a Cognito user with email `admin@example.com` (unverified), complete a token-issuing login, then call any authenticated API with the resulting id_token; `authenticate` finds the local profile by username (auth.ts:198), reassigns its rows to the attacker's sub (auth.ts:202-221), and authenticates the attacker as the admin.

## Remediation

Only bind by email when the id_token's `email_verified` claim is true (reject otherwise), require the pool to enforce unique verified emails, and require an explicit invitation/admin confirmation before migrating rows to a new identity. Consider replacing row reassignment with a stable identity mapping table.

## Assumptions

Cognito user pool configured to allow self-registration or where an attacker can control the `email` claim of a valid id_token (e.g. pool with email-based aliases and non-verified email, or any flow where the verifier does not enforce email_verified). Verified Cognito verifier is `aws-jwt-verify`, which validates signature but not email_verified.
