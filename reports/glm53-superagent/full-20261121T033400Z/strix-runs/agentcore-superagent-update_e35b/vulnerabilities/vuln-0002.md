# Hardcoded default JWT secret enables unauthenticated token forgery in local auth mode

**ID:** vuln-0002
**Severity:** CRITICAL
**Found:** 2026-11-21 04:06:05 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent/backend
**CWE:** CWE-798
**CVSS:** 9.8
**Confidence:** High
**Fix Effort:** Trivial

## Description

The local-mode JWT signing secret defaults to the hardcoded string `super-agent-local-dev-secret-change-in-production` when `JWT_SECRET` is not set. There is no runtime guard rejecting this default (or the `CHANGE_ME` placeholder) in production, so any deployment that omits the variable lets an unauthenticated attacker forge valid JWTs for arbitrary users, organizations, and roles.

## Evidence

Offline PoC output (using the repo's own `jsonwebtoken` module):

```
[1] local JWT forged+verified with default secret; claims accepted: {"sub":"...","email":"attacker@evil.example","orgId":"any-org-id","role":"owner","iat":...,"exp":...}
```

`jwt.sign(..., 'super-agent-local-dev-secret-change-in-production')` / `jwt.verify(...)` — the exact operations of `createLocalJwt` (auth.ts:49-56) and `verifyLocalToken` (auth.ts:61-74) — round-trip successfully, proving the default secret produces accepted tokens.

## Impact

Complete authentication bypass in local auth mode: a forged JWT with an existing user's `sub` (profile lookup at auth.ts:194 succeeds) grants the attacker that user's identity, organization, and role. Forging an `owner`-role member's sub yields full administrative access. Note the attacker needs a valid existing profile `sub`/`username`; in default seeded deployments these are known (`admin@example.com` / `admin123` per prisma/seed-local-auth.ts:32-33).

## Counterevidence

No guard forces a strong secret: the zod schema at config/index.ts:30 makes JWT_SECRET optional with a hardcoded default, and no startup check rejects weak values in production. The CDK deploy script generates a strong random secret (infra/scripts/ci/merge-env.sh:9, deploy.sh:239) and the bootstrap template marks it CHANGE_ME, so a correctly-executed CDK deployment is not vulnerable — the risk is the unguarded default (config/index.ts:30) combined with local-mode deployments, the EC2 bootstrap path, and any deployment where the placeholder or default survives. A 48-byte base64 HMAC comparison is infeasible to brute-force remotely; exploitation requires the secret to actually be default/placeholder.

## What Would Change This Severity

Confirmation that no deployment path can start with the default secret (e.g. after the schema is made mandatory) would reduce this to non-exploitable hardening; conversely, discovery of an internet-reachable deployment running the default secret confirms full impact.

## Technical Analysis

`src/config/index.ts:30` defines `JWT_SECRET: z.string().optional().default('super-agent-local-dev-secret-change-in-production')`. `createLocalJwt` (src/middleware/auth.ts:49-56) signs all local-mode login tokens with this value, and `verifyLocalToken` (auth.ts:61-74) verifies with it. No production-mode validation exists anywhere in the startup path (`src/index.ts`, `src/app.ts` contain no `isProduction` secret check). The same secret also keys `INTERNAL_TOKEN_SECRET` in local mode (auth.ts:79-81). The EC2 bootstrap script writes a placeholder (`infra/scripts/user-data.sh:241`, `JWT_SECRET=CHANGE_ME`) which — like the default — is a publicly known value in the repository; the CDK deploy path generates a random secret (`infra/scripts/deploy.sh:239`) but only when that path is used.

## Proof of Concept

1. Sign a JWT with HS256 using the hardcoded default secret `super-agent-local-dev-secret-change-in-production`, with claims `sub=<existing user id>`, `email`, `orgId`, `role=owner`, expiry 24h. 2. Send `Authorization: Bearer <token>` to any protected route. `verifyLocalToken` accepts it and the request executes as the forged user.

```gdscript
// Offline unit-level PoC (no network)
const jwt = require('/workspace/agentcore-superagent-update/super-agent/backend/node_modules/jsonwebtoken');
const DEFAULT = 'super-agent-local-dev-secret-change-in-production';
const token = jwt.sign(
  { sub: 'existing-user-id', email: 'admin@example.com', orgId: 'target-org', role: 'owner' },
  DEFAULT, { expiresIn: '24h' }
);
console.log('forged token accepted by verifyLocalToken:', !!jwt.verify(token, DEFAULT)); // -> true
```

## Remediation

Remove the default: make `JWT_SECRET` a required field with a minimum length (e.g. 32+ bytes) in the zod schema at `src/config/index.ts:30`, so the process refuses to start when it is unset or set to known placeholder values such as `CHANGE_ME`. Apply the same check to `INSFORGE_JWT_SECRET` (config/index.ts:145), which has the same hardcoded default pattern.

## Assumptions

A deployment where JWT_SECRET is left unset (default) or left at the placeholder `CHANGE_ME` value from the bootstrap .env. Applies to local mode (default AUTH_MODE) and the EC2 bootstrap path.
