# Default admin credentials (admin@example.com / Admin1234!) baked into production deploy scripts and public docs

**ID:** vuln-0005
**Severity:** CRITICAL
**Found:** 2026-11-21 04:06:35 UTC
**Target:** /workspace/agentcore-superagent-update (super-agent deployment infrastructure)
**CWE:** CWE-798
**CVSS:** 9.8
**Confidence:** High
**Fix Effort:** Low

## Description

The production deployment scripts hardcode a default administrator account (`admin@example.com` / `Admin1234!`) and set its bcrypt password hash directly in the database. The credential is publicly documented in the repository's deployment README and fork guide. Combined with the security group default that allows HTTP/HTTPS from `0.0.0.0/0` and a self-signed TLS certificate, any deployment produced by these scripts is trivially loggable by anyone who reads the public documentation, until an operator manually changes the password.

## Evidence

infra/scripts/deploy.sh:420-422:
```
ADMIN_HASH=$(node -e 'require("bcryptjs").hash("Admin1234!", 10).then(h => process.stdout.write(h))')
psql "$PSQL_URL" -c "UPDATE profiles SET password_hash = '${ADMIN_HASH}' WHERE username = 'admin@example.com' AND password_hash IS NULL;" 2>/dev/null || true
echo "  Admin login: admin@example.com / Admin1234!"
```
infra/README.md:97 publishes the same credential, and infra/lib/super-agent-stack.ts:58-61 defaults AllowedCidr to 0.0.0.0/0.

## Impact

Full administrative takeover of a deployed instance: the seeded admin is the platform's initial privileged account (agent configuration, credential vault, org/user management). An unauthenticated internet user who reads the public docs can log in as admin on any deployment where the operator has not changed the default, obtaining the same access as the legitimate administrator.

## Counterevidence

The repo acknowledges the risk and tells the operator to change the password after first login (document/fork-deploy-guide.md:276, and a warning printed by prisma/seed-local-auth.ts:91), so an operator who follows the docs is not exposed. The UPDATE only runs when the admin row exists and password_hash IS NULL, and it is skipped entirely when agents already exist (deploy.sh:413-415), so re-deploys over existing data do not reset a changed password. The instance also has no SSH ingress (access is via SSM), which limits local attack paths but does not affect the remote login issue. No first-login forced password change, password-expiration flag, or admin-user-disabled-until-changed mechanism was found anywhere in backend/src/routes/auth.routes.ts or the auth service.

## Confidence Rationale

Deterministic static evidence: the deploy scripts hardcode the bcrypt hash of a fixed password and apply it to a well-known username, and the password is published in three repository documents. No runtime validation was possible or needed for the misconfiguration itself; exploitability depends only on the operator not rotating the credential, which nothing in the code enforces.

## What Would Change This Severity

Confirmation that the seeded admin account is limited in privilege (not a platform-wide administrator), or that a first-login forced password change exists in a deployed build, would lower this to medium; evidence that deployments commonly remain on the default password (e.g. scan of live instances, out of scope here) would confirm the full rating.

## Technical Analysis

`infra/scripts/deploy.sh` line 420 computes `bcryptjs.hash("Admin1234!", 10)` and line 421 applies it via `UPDATE profiles SET password_hash = ... WHERE username = 'admin@example.com'` as the final step of production seeding; the identical logic exists in `infra/scripts/ci/remote-deploy.sh` lines 50-51. The same plaintext credential is published in three user-facing documents: `infra/README.md` lines 87 and 97, and `document/fork-deploy-guide.md` line 274, so it is effectively public knowledge for anyone with read access to the repository. The deployment stack (`infra/lib/super-agent-stack.ts` lines 58-61) defaults the `AllowedCidr` parameter to `0.0.0.0/0` for HTTP/HTTPS ingress, and `user-data.sh` serves TLS with a self-signed certificate, so the platform is deployed directly internet-facing. The backend's local-auth login (`backend/src/routes/auth.routes.ts` lines 63-77) performs an ordinary bcrypt compare — there is no forced password-change on first login, no `must_change_password` flag, and no password policy beyond a minimum length of 8 on explicit resets. The only mitigation is a documentation note asking the operator to change the password after first login; nothing in code or deploy tooling enforces it, and the deploy script itself prints the credential to the console. This is a use-of-hardcoded/default credentials issue (CWE-798) that is exploitable by an unauthenticated network attacker against any deployment whose operator has not yet rotated the password.

## Proof of Concept

1. Read the repository's public deployment docs (infra/README.md line 87/97, document/fork-deploy-guide.md line 274), which state the first-deploy administrator credentials: admin@example.com / Admin1234!.
2. Run infra/scripts/deploy.sh (or the CI variant infra/scripts/ci/remote-deploy.sh): after seeding, line 420 computes a bcrypt hash of the literal string "Admin1234!" and line 421 writes it into the profiles table for username admin@example.com. The script itself prints the credential at line 422.
3. Deploy without an operator-initiated password change, and observe that the CDK stack's AllowedCidr parameter defaults to 0.0.0.0/0 (super-agent-stack.ts line 58-61), so the login endpoint is reachable from any network.
4. POST /api/auth/login (or equivalent local-auth login route) with those credentials authenticates as the seeded admin; no code path forces or verifies a password change on first login.

```bash
# Static proof: the deployed system deterministically contains a known admin password.

# 1. The hash the deploy script installs:
node -e 'require("bcryptjs").hash("Admin1234!", 10).then(h=>console.log(h))'
# → bcrypt hash of the literal documented password

# 2. Verification that the documented credential matches the deployed hash:
node -e 'require("bcryptjs").compare("Admin1234!", process.argv[1]).then(v=>console.log(v))' \
  "$HASH_FROM_DB"

# 3. Login against a deployed instance (illustrative; not executed against any live system):
curl -k -X POST https://<deployed-host>/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin@example.com","password":"Admin1234!"}'
```

## Remediation

Generate a random admin password at deploy time and deliver it out-of-band instead of using a fixed documented value (e.g. `openssl rand -base64 16` written only to a root-readable file or AWS Secrets Manager, never echoed or committed). Better: create the initial admin with a must-change-password flag and block API access until the password is changed on first login. At minimum, remove the credential from all public documentation and have deploy.sh abort if the admin password has not been rotated.

## Assumptions

Assumes a deployment following infra/scripts/deploy.sh (or CI remote-deploy.sh) with AUTH_MODE=local and the default AllowedCidr=0.0.0.0/0, where the operator does not change the default password after first login. A deployment that sets a strong password before exposure, restricts AllowedCidr, or uses Cognito mode without the local admin seed is not affected.
