## Description

js-yaml 4.1.1, a direct production dependency used to parse user-supplied OpenAPI/Swagger specs, is covered by 2026 advisories for denial of service via crafted YAML documents (CVE-2026-59869, fixed 4.3.0) and YAML-parsing DoS (CVE-2026-84375, fixed 4.3.2), plus quadratic CPU consumption in !!omap resolution (GHSA-5p4m-2wfm-xmqj).

## Evidence

**Advisory evidence:** `CVE-2026-59869` applies to `js-yaml` at installed version `4.1.1`. The advisory is fixed in `4.3.2`.

**Dependency chain:** `js-yaml@4.1.1`

**Usage analysis:** the advisory's vulnerable code runs in this codebase. Source-to-sink trace: POST /api/business-scopes (integrations.routes.ts:39 preHandler [authenticate]) -> API spec upload handler -> apiSpecParserService.parse(content) -> parseContent (api-spec-parser.service.ts:180-184) -> yamlLoad(trimmed) at :183 — the attacker-controlled spec body reaches the vulnerable js-yaml parse function directly.

## Impact

An authenticated user can submit a maliciously crafted YAML API spec that causes excessive CPU/memory consumption in the backend process, degrading or denying service for all tenants sharing the process.

## Contextual CVSS

js-yaml 4.1.1 is a direct dependency of the backend and is invoked on user-uploaded OpenAPI/Swagger specs: src/services/api-spec-parser.service.ts:8 imports `load as yamlLoad` and :183 calls it on the trimmed spec content passed to the parser. The route chain is POST /api/business-scopes/... (integrations.routes.ts) with preHandler [authenticate] — an authenticated org member uploads the spec, so privileges_required:L. The DoS requires resource exhaustion of the parse call, which runs on the main event loop, so availability:L; no confidentiality/integrity impact demonstrated.

## Remediation

Upgrade js-yaml to >= 4.3.2 and add size/complexity limits on uploaded spec documents before parsing.

## Assumptions

Version from package-lock.json (offline trivy). js-yaml is a direct production dependency.
