# Output sanitizer redaction gaps: Bearer tokens, connection strings, generic API keys and Windows paths pass through to clients

**ID:** vuln-0024
**Severity:** LOW
**Found:** 2026-11-21 04:11:42 UTC
**Target:** super-agent/backend
**CWE:** CWE-532
**CVSS:** 3.1
**Confidence:** Medium
**Fix Effort:** Low

## Description

The `output-sanitizer` that scrubs agent responses before they are streamed to clients only redacts a narrow set of patterns: POSIX-style server paths, the workspace base dir, home directory, and `AUTH_TOKEN`/AWS key-value strings. Bearer tokens in `Authorization` headers, database connection strings, generic API keys (e.g. `sk-ant-...`), `ANTHROPIC_API_KEY`-style env assignments, and Windows paths pass through unredacted into SSE responses rendered to chat clients.

## Evidence

Local execution of the sanitizer's pattern set (extracted verbatim from src/services/output-sanitizer.ts):

```text
home leaked      => Reading ~ now
bearer token     => call with Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.real.token.here   [PASSED THROUGH]
db url           => postgres://sa_user:P@ssw0rd@db.internal:5432/prod                      [PASSED THROUGH]
windows path     => C:\Users\admin\secrets\aws-keys.txt                                     [PASSED THROUGH]
api key inline   => sk-ant-api03-ABCDEFG123456789 was used                                  [PASSED THROUGH]
env var generic  => ANTHROPIC_API_KEY=sk-ant-xyz123 use it                                  [PASSED THROUGH]
```

## Impact

If an agent (via tool output, file read, or error message) echoes a credential in one of the uncovered forms — an Authorization header, a connection string, a raw API key, or a non-POSIX path — it is delivered verbatim to the chat client. This widens credential-exposure blast radius when agents read config files or invoke authenticated tools.

## Counterevidence

The sanitizer does cover its stated scope well within Linux deployments: home-dir and workspace-base paths are redacted (verified locally), and AUTH_TOKEN/AWS key=value strings are redacted. The gap is incomplete coverage rather than absence of sanitization. Real exploitation also requires the agent to echo a secret in a form matching the uncovered patterns.

## Confidence Rationale

Static analysis of the sanitizer's regex set plus a local reproduction of its filtering behavior; no live agent output containing real secrets was produced, so leakage of an actual secret is inferred from the gap, not observed end-to-end.

## What Would Change This Severity

Demonstrating a live agent workflow that echoes a real credential into a chat stream would raise severity; confirming that agent outputs never contain such forms would lower it to informational.

## Technical Analysis

`buildPatterns()` in src/services/output-sanitizer.ts:25-79 constructs only: workspace-base and home-dir path regexes, one POSIX path regex (`/\/(?:Users|home|var|tmp|opt)\/...`), `AUTH_TOKEN=`, and AWS key=value patterns. No pattern matches `Authorization: Bearer ...`, connection strings with embedded credentials, raw API keys, other env-var secret names, or Windows paths. `sanitizeString()` (line ~95) applies only these patterns, and `sanitizeEvent` applies it only to assistant text/tool_use/tool_result blocks of SSE events.

## Proof of Concept

1. Feed representative secret strings through `sanitizeString()` from `src/services/output-sanitizer.ts` (local copy, no network).
2. Observe that only workspace/home paths are redacted; Bearer tokens, `postgres://` URLs, `sk-ant-...` keys, `ANTHROPIC_API_KEY=` assignments, and Windows paths are returned unchanged.

```js
// Local harness replicating buildPatterns() + sanitizeString() from
// src/services/output-sanitizer.ts (same regexes, same order).
const samples = [
  'call with Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.real.token.here',
  'postgres://sa_user:P@ssw0rd@db.internal:5432/prod',
  'sk-ant-api03-ABCDEFG123456789 was used',
  'ANTHROPIC_API_KEY=sk-ant-xyz123 use it',
];
// ... apply each pattern with .replace as in sanitizeString()
// Result: all four samples returned unchanged (no pattern matches).
```

## Remediation

Extend the pattern set: redact `Bearer\s+\S+`, common API-key prefixes (`sk-ant-`, `sk-`, `AKIA`, `ghp_`, `xoxb-`), connection-string credentials (`\w+://[^:/\s]+:[^@\s]+@`), generic `*_API_KEY=`/`*_TOKEN=` assignments, and Windows drive-letter paths (`[A-Za-z]:\\`). Prefer an allowlist-style scrub of anything resembling a secret over the current narrow denylist.

## Assumptions

Assumes agent outputs occasionally echo secrets/paths, which the sanitizer's own existence and targeted patterns acknowledge.
