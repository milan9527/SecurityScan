# Unrestricted SSRF in workflow api_call action node (ActionExecutor and workflow-orchestrator)

**ID:** vuln-0009
**Severity:** MEDIUM
**Found:** 2026-11-21 04:07:13 UTC
**Target:** super-agent/backend
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Medium

## Description

The workflow engine's `api_call` action node (both the legacy orchestrator and the V2 node-executor) fetches a user-authored URL with Node's global `fetch()` and no SSRF validation: no denylist for loopback/link-local/RFC1918 addresses, no scheme pinning, and redirects are followed by default. An authenticated org member who can author or edit a workflow — or anyone who can hit a public webhook trigger for such a workflow — can direct the backend to make arbitrary requests to internal services and cloud metadata endpoints.

## Evidence

Local PoC executed in the sandbox (isolated local analysis only):

```js
// /tmp/ssrf-poc/api_call_poc.test.js — vitest
import { describe, it, expect } from 'vitest';
import http from 'node:http';

function mockContext() {
  return { variables: new Map(), organizationId: 'org-test', workflowId: 'wf-test' };
}

describe('api_call action node SSRF', () => {
  it('fetches an arbitrary internal URL with no validation', async () => {
    let hit = null;
    const srv = http.createServer((req, res) => {
      hit = { path: req.url, secretHeader: req.headers['x-internal-auth'] };
      res.writeHead(200, { 'Content-Type': 'application/json' });
      res.end(JSON.stringify({ secret: 'internal-only-data' }));
    });
    await new Promise(r => srv.listen(0, '127.0.0.1', r));
    const port = srv.address().port;

    const { ActionExecutor } = await import(
      '/workspace/agentcore-superagent-update/super-agent/backend/src/services/node-executors/action-executor.ts'
    );
    const executor = new ActionExecutor();
    const result = await executor.execute({
      actionType: 'api_call',
      url: `http://127.0.0.1:${port}/admin`,
      method: 'GET',
      headers: { 'X-Internal-Auth': 'backend-trusts-itself' },
    }, mockContext());

    expect(hit).not.toBeNull();
    expect(hit.path).toBe('/admin');
    expect(hit.secretHeader).toBe('backend-trusts-itself');
    expect(JSON.parse(result.output)).toEqual({ secret: 'internal-only-data' });
    srv.close();
  });
});
```

Result: the local "internal" server (standing in for 169.254.169.254 / internal services) received the request, including attacker-set headers that internal services may trust, and the response body was returned into the workflow output. No URL validation occurred anywhere on the path. This demonstrates the missing control in the exact code that runs in production; the local reproduction does not by itself prove production exploitability.

## Impact

An authenticated user (or an unauthenticated caller of a public webhook trigger for an existing workflow) can reach internal-only endpoints from the backend server: cloud metadata (169.254.169.254) to steal role credentials, internal admin panels, and unauthenticated internal services. Attacker-supplied headers and body are passed through to the fetch, and the response body is stored in workflow execution logs/output, so responses from internal endpoints can be exfiltrated back to the attacker. Redirect-following defeats first-hop allowlists and enables DNS-rebinding-style pivots.

## Counterevidence

I searched the entire backend for SSRF guards (`rg "allowlist|denylist|127.0.0.1|169.254|redirect"` across all fetch sites): no IP filtering, scheme pinning, or redirect opt-out exists at any of the fetch call sites (mcp.service.ts, action-executor.ts, workflow-orchestrator.ts, a2a-client.service.ts). Fetches run with default Node semantics (redirects followed). Guard present: authoring routes require `authenticate` + `requireModifyAccess`. Mitigating constraint: variable substitution is a simple `{{name}}` regex replace, so full URL control at design time requires authoring the node; however, when a workflow author parameterizes the URL with a variable, the public unauthenticated webhook trigger lets any caller knowing the webhook ID control the substituted value (both name and value are attacker-chosen in the POST body) — verified statically but not executed end-to-end against a live database.

## What Would Change This Severity

Demonstrating on a live deployment a workflow whose api_call URL uses a webhook-supplied variable (turning this into unauthenticated SSRF with response exfiltration via the public call-status endpoint) would raise this to high/critical, as would a confirmed default-credential internal service reachable from the backend.

## Technical Analysis

In `src/services/node-executors/action-executor.ts:103-127`, `execute()` takes `apiConfig.url` (attacker-authored via the workflow editor), substitutes `{{variable}}` placeholders, and calls `fetch(url, ...)` directly. The identical pattern exists in `src/services/workflow-orchestrator.ts:554-560` (`executeActionNode` → `fetch(url, {method, headers, body})`). No URL validation library, IP-range check, or scheme restriction appears anywhere in the call path; Node's default `fetch` (undici) follows redirects by default, enabling redirect-based bypass of any first-hop check and DNS rebinding.

Reachability: (a) any authenticated user with workflow authoring rights can create an api_call node; (b) workflows with a webhook can be triggered unauthenticated via `POST /api/v1/webhook/:webhookId/trigger` (src/routes/webhooks.routes.ts:315), and `webhook.service.ts` `executeWebhookAsync` maps attacker-supplied `variables` into the workflow plan, feeding variable substitution. The api_call headers are also attacker-controlled, so internal services that trust headers are directly impersonatable, and the response body is stored in webhook call-record logs retrievable via the API.

## Remediation

Introduce a shared URL validation utility for all server-side fetches of user-influenced URLs: resolve the hostname and reject loopback (127.0.0.0/8, ::1), link-local (169.254.0.0/16, fe80::/10), RFC1918 ranges, and cloud metadata endpoints before connecting; pin the scheme to https (and http only if explicitly required); disable or re-validate redirects (fetch option `redirect: 'manual'` with the same validation applied to each hop); consider resolving DNS once and connecting to the validated IP to prevent DNS rebinding. Apply the same utility to the MCP server test connection, a2a remote endpoints, and any other user-supplied URL fetch.

## Assumptions

Attacker is any authenticated org member who can create workflows/action nodes, or a webhook triggerer who knows a webhook ID whose workflow contains an api_call node. Assumes default Node fetch behavior (redirect following) which is not overridden at any call site.
