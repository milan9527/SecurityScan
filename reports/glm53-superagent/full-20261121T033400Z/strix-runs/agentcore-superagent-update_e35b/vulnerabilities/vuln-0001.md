# Internal service tokens signed with public Cognito user pool ID allow full authentication bypass

**ID:** vuln-0001
**Severity:** CRITICAL
**Found:** 2026-11-21 04:05:53 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent/backend
**CWE:** CWE-798
**CVSS:** 9.8
**Confidence:** High
**Fix Effort:** Low

## Description

In Cognito auth mode, internal service tokens (`internal.<data>.<sig>`) are HMAC-signed with the Cognito user pool ID, which is a public, non-secret identifier. Anyone who knows the pool ID (exposed in Cognito hosted-UI URLs and returned by the unauthenticated `GET /api/auth/config` endpoint) can forge an internal token impersonating any user, organization, and role, bypassing all authentication.

## Evidence

Offline PoC output (no network, no real credentials, synthetic data):

```
[2] internal token forged with PUBLIC userPoolId and accepted: {"sub":"victim-admin-sub","email":"admin@example.com","orgId":"victim-org","role":"owner","exp":...}
[3] internal token forged with default dev secret and accepted: {...}
```

The PoC replicated `verifyInternalToken` character-for-character from `src/middleware/auth.ts:115-129` and the token was accepted, confirming the signing path requires only the public pool ID.

## Impact

Complete authentication bypass in Cognito mode: an unauthenticated attacker becomes any user in any organization with any role (e.g. `owner`), gaining read/write access to all tenant data, agent execution, and administrative operations the platform offers. The forged principal is fully trusted by `authenticate()` — no profile lookup or membership check is applied to internal tokens.

## Counterevidence

The userPoolId must be known to the attacker; it is not secret by design (Cognito hosted-UI login URLs embed it) and is additionally disclosed by the unauthenticated GET /api/auth/config endpoint (auth.routes.ts:33). Exploitation still requires network reachability of the backend. The non-constant-time comparison does not itself enable forgery (HMAC preimage is infeasible); it is a defense-in-depth gap only.

## What Would Change This Severity

If deployed behind a private network with no external reachability, the attack vector narrows (adjacent/local), reducing severity accordingly.

## Technical Analysis

`INTERNAL_TOKEN_SECRET` is set to `config.cognito.userPoolId` when `AUTH_MODE=cognito` (`src/middleware/auth.ts:79-81`). `createToken` (auth.ts:94-110) signs the payload with HMAC-SHA256 over this secret, and `verifyInternalToken` (auth.ts:115-129) validates it. When validation succeeds, `authenticate` (auth.ts:178-188) trusts the payload's `sub`, `orgId`, and `role` **without any database profile or membership lookup** — the internal-token path skips the profile check applied to JWTs (auth.ts:194-244). The Cognito user pool ID is public by design: it appears in the hosted-UI domain/login URLs and is returned by the unauthenticated `GET /api/auth/config` endpoint (`src/routes/auth.routes.ts:30-37`). Additionally, the HMAC comparison at auth.ts:121 uses `!==` rather than `crypto.timingSafeEqual` (minor, not the root cause).

## Proof of Concept

1. Obtain the user pool ID from the Cognito hosted-UI login URL or from `GET /api/auth/config` (unauthenticated). 2. Construct payload `{"sub":"<victim-user-id>","email":"victim@example.com","orgId":"<org>","role":"owner","exp":<now+3600>}`, base64url-encode it. 3. Compute HMAC-SHA256 over the encoded data keyed with the user pool ID. 4. Send `Authorization: Bearer internal.<data>.<sig>` to any protected API route. The token is accepted and the request executes as the victim.

```gdscript
// Offline unit-level PoC (no network) — replicates auth.ts createToken/verifyInternalToken
const crypto = require('node:crypto');
const PUBLIC_USER_POOL_ID = 'ap-northeast-1_XXXXXXXXX'; // known/attacker-derivable
const payload = {
  sub: 'victim-admin-sub', email: 'admin@example.com',
  orgId: 'victim-org', role: 'owner',
  exp: Math.floor(Date.now() / 1000) + 3600,
};
const data = Buffer.from(JSON.stringify(payload)).toString('base64url');
const sig = crypto.createHmac('sha256', PUBLIC_USER_POOL_ID).update(data).digest('base64url');
const token = `internal.${data}.${sig}`;
// verifyInternalToken (auth.ts:115-129) accepts this:
const parts = token.split('.');
const expected = crypto.createHmac('sha256', PUBLIC_USER_POOL_ID).update(parts[1]).digest('base64url');
console.log('accepted:', parts[2] === expected); // -> true
```

## Remediation

Replace the internal-token secret with a high-entropy secret independent of the user pool ID — generate a dedicated random secret at deploy time (as deploy.sh already does for JWT_SECRET) and inject it via environment variable. Reject any token whose secret material is missing or equals a known non-secret value. Additionally, replace the `!==` HMAC comparison at auth.ts:121 with `crypto.timingSafeEqual`, and consider binding internal tokens to the issuing host/session so they cannot be replayed from outside.

## Assumptions

Cognito mode deployment where the user pool ID is discoverable (hosted UI, tenant configuration, or the unauthenticated /api/auth/config endpoint). No other credentials or access required.
