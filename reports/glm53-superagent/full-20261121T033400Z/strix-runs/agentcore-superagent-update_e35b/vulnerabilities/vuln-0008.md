# A2A routes compare raw API key against stored SHA-256 hash — feature always rejects valid keys (reliability defect)

**ID:** vuln-0008
**Severity:** INFO
**Found:** 2026-11-21 04:07:10 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent/backend
**CWE:** CWE-665
**Confidence:** High
**Fix Effort:** Trivial

## Description

The A2A protocol routes validate bearer tokens by comparing the raw token value against the `key_hash` column, which stores a SHA-256 hash of the key. Every legitimate API key is therefore rejected, disabling the A2A feature. This is a functional/reliability defect, not an exploitable vulnerability.

## Evidence

Source: `src/routes/a2a.routes.ts:41-57` — `prisma.api_keys.findFirst({ where: { key_hash: token } })` with the raw bearer token, while `src/services/apiKey.service.ts:37-43` stores `sha256(key)` in `key_hash`. Offline demonstration: `sha256('sk_<64 hex>') !== 'sk_<64 hex>'` for every generated key.

## Impact

No security impact demonstrated: A2A endpoints (agent card, task send, task status) reject all valid keys and cannot be used. If "fixed" naively by storing raw keys, it would become one; the correct fix preserves hashing. This is a reliability/usability defect in an advertised feature.

## Counterevidence

Not exploitable: a 256-bit SHA-256 preimage is computationally infeasible, and the correct raw key never matches the stored hash, so the only possible "match" is a value that already equals a stored hash — which an attacker cannot produce. The endpoint stays denial-free because all keys are uniformly rejected. No data exposure results.

## What Would Change This Severity

None — this is a correctness defect; if the "fix" ever stores raw keys in the database, it would become a plaintext-credential-at-rest vulnerability.

## Technical Analysis

`validateApiKey` in `src/routes/a2a.routes.ts:41-57` queries `prisma.api_keys.findFirst({ where: { key_hash: token } })` using the raw bearer token. Keys are created with `key_hash = sha256(key)` (`src/services/apiKey.service.ts:37-43`), so the raw token never matches. All A2A routes (`/api/a2a/agents/:agentId/card`, `/tasks/send`, `/tasks/:taskId`) are consequently unusable with legitimate keys.

## Proof of Concept

1. Create an API key via POST /api/api-keys. 2. Call GET /api/a2a/agents/:id/card with `Authorization: Bearer <key>`. 3. The request is rejected with 401 because the raw key never equals its stored SHA-256 hash. Not executed against a live service; demonstrated by code trace and hash computation.

```gdscript
// Offline demonstration of the mismatch (a2a.routes.ts:46 vs apiKey.service.ts:40)
const crypto = require('node:crypto');
const key = 'sk_' + crypto.randomBytes(32).toString('hex');       // generated key
const stored = crypto.createHash('sha256').update(key).digest('hex'); // what apiKeyService stores
console.log('raw key equals stored key_hash?', key === stored);   // -> false, always
```

## Remediation

In `validateApiKey` (src/routes/a2a.routes.ts:41-57), hash the bearer token with SHA-256 before querying `key_hash`, matching `apiKeyService.validateApiKey` (or reuse that service, which also handles expiry, caching, and rate limiting).

## Assumptions

None.
