# CORS wildcard origin combined with credentials:true

**ID:** vuln-0007
**Severity:** MEDIUM
**Found:** 2026-11-21 04:06:57 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent/backend
**CWE:** CWE-942
**CVSS:** 4.2
**Confidence:** High
**Fix Effort:** Trivial

## Description

CORS is configured with `credentials: true` together with a wildcard origin policy (default `CORS_ORIGIN=*` reflects any Origin with `Access-Control-Allow-Origin: <origin>` plus `Access-Control-Allow-Credentials: true`), violating the CORS specification's intent and enabling credentialed cross-origin access if any cookie-based or ambient-credential flow is ever introduced.

## Evidence

Source: `src/app.ts` CORS registration — `origin: config.corsOrigin === '*' ? true : ...` with `credentials: true`; default at `src/config/index.ts:64` (`CORS_ORIGIN: z.string().default('*')`). A cross-origin `fetch(..., {credentials:'include'})` receives `Access-Control-Allow-Origin: <attacker-origin>` and `Access-Control-Allow-Credentials: true` for any attacker origin.

## Impact

With the current Bearer-token architecture the practical impact is limited. It becomes a real credential/data leakage vector the moment any cookie-based session, HTTP Basic, TLS-client-cert, or ambient-credential mechanism is added. It also allows any origin to read non-credentialed responses, which matters for any future unauthenticated endpoints returning tenant data.

## Counterevidence

The application uses Bearer tokens in JavaScript, not cookies, so browser-credentialed cross-origin reads are not possible by construction: `credentials: true` only attaches cookies/HTTP auth, and the frontend stores tokens in JS memory/localStorage where cross-origin scripts cannot read them. No `setCookie` usage exists anywhere in src/. With per-route tokens (Authorization header), CSRF-style abuse is also infeasible. The misconfiguration is therefore defense-in-depth weakness and spec violation rather than a demonstrated data-theft vector.

## What Would Change This Severity

Introduction of any cookie or ambient-credential authentication would raise this to high (cross-origin credentialed reads).

## Technical Analysis

`src/app.ts` registers `@fastify/cors` with `origin: config.corsOrigin === '*' ? true : <allowlist>` and `credentials: true`. The `origin: true` setting reflects any request Origin, and combined with `credentials: true` produces a permissive credentialed-CORS response for every origin. `CORS_ORIGIN` defaults to `*` (`src/config/index.ts:64`), so out-of-the-box deployments ship this state. No cookie-based sessions were found (`rg setCookie` returns only the redact entry), which limits current exploitability.

## Proof of Concept

Not executed (isolated assessment). Configuration: when CORS_ORIGIN is unset, any origin sending a preflight receives `Access-Control-Allow-Origin: <origin>` and `Access-Control-Allow-Credentials: true` because the `origin: true` Fastify-CORS option reflects the request origin while credentials are enabled.

```scilab
// Static config demonstrating the reflection (from src/app.ts):
// app.register(cors, { origin: config.corsOrigin === '*' ? true : ..., credentials: true, ... })
// origin:true reflects ANY request Origin; credentials:true adds Allow-Credentials:true.
// Default CORS_ORIGIN='*' (src/config/index.ts:64).
console.log('CORS: reflect any origin + credentials:true');
```

## Remediation

Default `CORS_ORIGIN` to an empty/strict value instead of `*`, refuse wildcard/reflection when `credentials: true` is set, and require an explicit origin allowlist in production. Add a startup validation that fails when `NODE_ENV=production` and `CORS_ORIGIN` is `*`.

## Assumptions

Default deployment posture: local auth mode, no cookies used by the frontend (auth is Bearer-header based), CORS_ORIGIN unset (defaults to `*`).
