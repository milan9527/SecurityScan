# Plaintext IM signing secrets exposed to any org member via GET /api/business-scopes/:scopeId/im-channels (config not redacted)

**ID:** vuln-0027
**Severity:** MEDIUM
**Found:** 2026-11-21 04:13:23 UTC
**Target:** super-agent/backend
**CWE:** CWE-200
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Low

## Description

GET /api/business-scopes/:scopeId/im-channels returns each IM channel binding with its full `config` object included, exposing plaintext platform secrets — Slack `signing_secret`, DingTalk `signing_secret`, Feishu `verification_token`/`encrypt_key`, Telegram `secret_token`, WhatsApp `app_secret`, Discord `public_key`, WeCom `token`/`encoding_aes_key` — to any authenticated member of the organization, while only `bot_token_enc` is masked.

## Evidence

Code path confirmed: im.routes.ts:67-82 — `imChannelRepository.findByScope(request.user!.orgId, request.params.scopeId)` then `bindings.map(b => ({ ...b, bot_token_enc: '***' }))`; `config` is spread unmodified. Repository scoping is correct (im-channel.repository.ts:45-53, where: { organization_id, business_scope_id }) — org members of the owning org only, not cross-tenant. The same plaintext `config` is consumed server-side at im.routes.ts:243-260 (signing secrets injected for verification), proving real secret material lives in `config`. Binding creation stores operator-provided `config` verbatim (im.routes.ts:106-113).

## Impact

Any member-role user (not just admins) of the organization can read the raw platform verification secrets for every IM binding in the scope. These secrets are exactly the values the inbound webhook signature checks rely on (CWE-312 exposure of the verification credential); possession lets a member forge or validate webhook traffic, and for platforms where the secret is also an outbound credential (e.g. WeCom `encoding_aes_key`, DingTalk app secret) enables impersonation of the bot towards the platform. Confidentiality impact is limited to the organization's own secrets — no cross-tenant access, no server-side state change.

## Counterevidence

The bot access token IS masked (`bot_token_enc: '***'` at im.routes.ts:75-78), which shows the developer considered credential redaction but missed the `config` JSON — the most likely copy-paste source for the full-duplication answer, and the strongest evidence this is unintended. Org scoping is correctly applied (repository where-clause), so there is no cross-tenant dimension. No route-level sanitization or serializer strips `config`. Only defense is obscurity of scope UUIDs, which the authenticated member can enumerate from their own org's scope list.

## What Would Change This Severity

Evidence that these secrets grant authority beyond the org's own channels (e.g. a shared Slack signing secret usable to forge requests accepted by other systems) would raise severity; a deployment with no IM bindings would lower it.

## Technical Analysis

`imChannelAdminRoutes` is registered with prefix `/api/business-scopes` (routes/index.ts:218). The list handler (im.routes.ts:67-82) requires only `authenticate` — no role check — and spreads each binding (`...b`) into the response, replacing only `bot_token_enc` with `'***'`. The `config` JSON column is where the admin routes store platform secrets: `POST /:scopeId/im-channels` and `PUT .../:bindingId` persist the caller-supplied `config` verbatim (im.routes.ts:106-113, 130-133), and the webhook verification path reads them back from the same field (im.routes.ts:243-260: `cfg.signing_secret`, `cfg.verification_token`, `cfg.secret_token`, `cfg.public_key`; wecom `cfg.token`/`cfg.encoding_aes_key` at im.routes.ts:504-507; whatsapp `cfg.app_secret` at im.routes.ts:712). Because the list endpoint does not redact `config`, every secret an operator entered for webhook verification is returned in plaintext to any authenticated member of the org. Org scoping itself is correct: `findByScope` filters by `organization_id` and `business_scope_id` (im-channel.repository.ts:45-53), so exposure is confined to the caller's own organization.

## Proof of Concept

Authenticate as any member of the org, GET /api/business-scopes/&lt;scopeId&gt;/im-channels for a scope containing an IM binding, and observe each binding's `config` object in the response containing the plaintext `signing_secret` (Slack/DingTalk), `app_secret` (WhatsApp), `secret_token` (Telegram), etc., while only `bot_token_enc` is masked as `***`.

```carbon
GET /api/business-scopes/<scopeId>/im-channels

// Response (abridged):
// { "data": [ { "id": "...", "channel_type": "slack",
//     "bot_token_enc": "***",
//     "config": { "signing_secret": "8f7a...plaintext...",
//                 "channel_id": "C0123456789" }, ... } ] }
```

## Remediation

Redact secret-bearing keys from `config` before returning bindings in the list endpoint (and in the create/update responses), the same way `bot_token_enc` is masked: strip or mask keys such as `signing_secret`, `app_secret`, `secret_token`, `verification_token`, `encrypt_key`, `encoding_aes_key`, `token`, `client_secret` unless the caller has an admin role with a documented need. Server-side consumers (verifyAndLookupBinding, adapters) should read the secrets from the database rather than from API responses.

## Assumptions

Attacker holds any authenticated account in the organization that owns the scope (member role suffices — only `authenticate` is required). A Slack/DingTalk/Feishu/Telegram/WhatsApp/Discord binding with secret material in `config` must exist in that scope.
