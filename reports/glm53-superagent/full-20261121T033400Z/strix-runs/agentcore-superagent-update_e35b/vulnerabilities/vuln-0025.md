# Cross-tenant leader manipulation in PUT /api/chat/rooms/:roomId/members/:agentId/leader (missing org scoping on raw updateMany)

**ID:** vuln-0025
**Severity:** MEDIUM
**Found:** 2026-11-21 04:13:05 UTC
**Target:** super-agent/backend
**CWE:** CWE-639
**CVSS:** 4.2
**Confidence:** High
**Fix Effort:** Low

## Description

The "set room leader" endpoint updates `chat_room_members` with raw Prisma `updateMany` filtered only by `session_id` and `agent_id` — no organization scoping and no room-ownership check — so any authenticated member-role user who knows a room's session UUID can change leader assignment and leader instructions on another organization's room.

## Evidence

Route preHandler is `[authenticate, requireModifyAccess]` only (role check, no object check); the handler runs `updateMany({ where: { session_id: roomId } })` and `updateMany({ where: { session_id: roomId, agent_id: agentId } })` with no `organization_id` predicate and no prior room lookup (chatRooms.routes.ts:177-206). Contrast with sibling handler `removeMember` (line 159) which passes `request.user!.orgId` into the service, and the follow-up read `memberRepo.findBySession(roomId)` (chat-room-member.repository.ts:35) which also takes no org filter. Verified against the project's own adapters and Prisma semantics in an isolated local sandbox; no network or real database was contacted. Room IDs are `@default(uuid())` (schema.prisma:480), so exploitation requires a known room UUID.

## Impact

A member of organization A can promote or demote the leader agent of organization B's room and set the leader's `leader_instructions`, changing which agent coordinates the room and the instructions it follows — an unauthorized cross-tenant state change on the target room's coordination logic. The response also discloses the foreign room's agent membership and roles.

## Counterevidence

Prehandlers authenticate and enforce role but add no object check. No global hook in this file or route registration adds an org predicate. The only org-aware code on the route is the follow-up memberRepo.findBySession read. Verified no `organization_id` filter exists in the where clauses by direct inspection of all three updateMany calls. Mitigating: UUID room IDs make blind targeting impractical — requires a leaked/observed roomId, and updateMany with a non-matching filter is a no-op, so probing for valid rooms yields indistinguishable empty member lists. This limits exploitability but not the authorization flaw.

## What Would Change This Severity

A demonstrated path for an attacker to obtain foreign rooms' session UUIDs (e.g. an unscoped list/export endpoint or UUID leak in logs) would raise severity to high; deployment where member accounts cannot be created across orgs would lower it.

## Technical Analysis

In `chatRooms.routes.ts` the `PUT /:roomId/members/:agentId/leader` handler (lines 177–206) demotes the current leader and promotes the requested agent with three raw `prisma.chat_room_members.updateMany` calls whose `where` clauses filter only on `session_id` (and `agent_id`). No middleware on this route performs a room lookup: `authenticate` establishes identity, `requireModifyAccess` (`middleware/auth.ts:280`) checks only the caller's role. The room's owning organization is never resolved, so Prisma applies no org boundary. This diverges from the sibling `DELETE /:roomId/members/:agentId` handler (lines 156–169), which passes `request.user!.orgId` into `chatRoomService.removeMember`. Even the final read, `memberRepo.findBySession(roomId)` (`repositories/chat-room-member.repository.ts:35`), takes no organization filter, so the route's response also discloses the foreign room's agent membership and roles. The room ID is a UUIDv4 (`chat_sessions.id @default(uuid())`, prisma/schema.prisma:480), so the attacker needs a known session UUID; this is the sole practical constraint.

## Proof of Concept

As any authenticated member-role user of organization A, send a PUT to the leader endpoint with the session UUID of organization B's room and a member agent UUID of that room. Confirm that leader flags flip and leader_instructions persist for the foreign room, and that the response lists the foreign room's members.

```css+lasso
PUT /api/chat/rooms/<room-uuid>/members/<agent-uuid>/leader
Content-Type: application/json

{"is_leader": true, "leader_instructions": "attacker-controlled"}

// Expected DB effect (no org predicate):
// UPDATE chat_room_members SET is_leader=false, role='member'
//   WHERE session_id = <room-uuid> AND is_leader = true;
// UPDATE chat_room_members SET is_leader=true, role='leader',
//   leader_instructions='attacker-controlled'
//   WHERE session_id = <room-uuid> AND agent_id = <agent-uuid>;
```

## Remediation

Before updating, load the room through an org-scoped query (e.g. a `findById(orgId, roomId)` on the chat session repository that filters by `organization_id`) and return 404 when it does not belong to the caller's organization; add the `organization_id` to the `updateMany` where clauses as defense in depth. Mirror the pattern used by `removeMember`, which already receives and uses `orgId`.

## Assumptions

Attacker holds a valid member-role account in any organization (self-registered or provisioned) and knows or guesses a target room's UUID. Intended actions by authorized users on their own org's rooms are not in scope.
