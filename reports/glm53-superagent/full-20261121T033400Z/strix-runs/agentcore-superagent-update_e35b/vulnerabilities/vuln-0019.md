# Cross-tenant BOLA: checkpoint resolve/resume and execution detail routes skip organization scoping

**ID:** vuln-0019
**Severity:** MEDIUM
**Found:** 2026-11-21 04:11:01 UTC
**Target:** super-agent/backend
**CVSS:** 6.4
**Confidence:** Medium
**Fix Effort:** Low

## Description

Three workflow checkpoint/execution endpoints perform no organization check: the checkpoint resolve route, the execution status route in checkpoint.routes.ts, and the executor resume path. Any authenticated user of any organization can read another organization's paused execution details, resolve or cancel their human-approval checkpoints, and resume their workflows, by supplying the execution or checkpoint UUID.

## Evidence

Source-level evidence (no DB available in isolated assessment):

```text
checkpoint.routes.ts:113-116  const execution = await prisma.workflow_executions.findUnique({ where: { id: executionId }, include: ... })   // no organization_id
checkpoint.service.ts:135-136  prisma.execution_checkpoints.findUnique({ where: { id: checkpointId } })                                        // no organization_id
workflow-executor-v2.ts:578-579 prisma.workflow_executions.findUnique({ where: { id: executionId } })                                        // no organization_id
```

Contrast with the correctly-scoped sibling: `execution.routes.ts:520-523` filters `organization_id: request.user.orgId` and additionally enforces per-user ownership.

## Impact

Cross-tenant integrity impact on workflow approval flows: a user from organization A can approve or cancel organization B's human-approval checkpoints — the exact control meant to gate destructive workflow segments — and force-resume or steer B's paused executions by supplying an arbitrary `scopeId` (the resume route passes the user-supplied scopeId to workspace provisioning and the executor, `checkpoint.routes.ts:66`). They can also read B's execution state, checkpoint configuration, and inputContext (which contains workflow variable values and prior node outputs). This defeats the tenant isolation invariant of the platform.

## Counterevidence

Neighboring execution routes do scope by organization (`GET /executions/:id`, `/logs`, `/workspace/files` all filter on `organization_id: request.user.orgId`), which shows the codebase intends org scoping here — these three checkpoint routes are the omission. The UUID format parameter makes blind guessing impractical, but UUIDs leak through logs, exports, SSE payloads, and shared integrations. No other control (ownership column, membership check) exists on the resolve path; `checkpointService.resolve` only checks status and expiry.

## Confidence Rationale

Static trace is complete (route → service → ORM query with no org predicate, verified in source), and the identical missing-filter pattern was confirmed exploitable by sibling agents' tenant-isolation PoCs in this scan, but I did not stand up the full Fastify+Prisma stack to replay the cross-org request end-to-end myself.

## What Would Change This Severity

A live cross-tenant replay confirming the resolve/resume path would raise confidence to high and could justify a higher availability/integrity impact rating; conversely, evidence that these routes are mounted behind an org-enforcing gateway (not present in the repository) would rule the finding out.

## Technical Analysis

Three concrete gaps:

1. `src/routes/checkpoint.routes.ts:27-40` — `POST /executions/:executionId/checkpoints/:checkpointId/resolve` uses `preHandler: [authenticate]` only, then calls `checkpointService.resolve(checkpointId, ...)` without passing or checking `request.user.orgId`. `src/services/checkpoint.service.ts:132-136` looks the checkpoint up with `prisma.execution_checkpoints.findUnique({ where: { id: checkpointId } })` — no `organization_id` predicate — and updates it. The route then resumes execution via `workflowExecutorV2.resume(executionId, checkpointId, scopeId)` where `scopeId` is taken verbatim from the request body.
2. `src/services/workflow-executor-v2.ts:574-580` — `resume()` loads the execution with `prisma.workflow_executions.findUnique({ where: { id: executionId } })`, again with no organization filter, and does not verify the checkpoint belongs to that execution or that the caller's org matches.
3. `src/routes/checkpoint.routes.ts:113-118` — `GET /executions/:executionId` (the checkpoint detail route, distinct from the correctly-scoped one in execution.routes.ts) uses `findUnique({ where: { id: executionId } })` with no `organization_id` filter and returns node executions, checkpoint config, and inputContext.

Sibling routes (`execution.routes.ts` GET /executions/:id, /logs, /workspace/files) all scope by `organization_id`, confirming the intended invariant that these three paths violate.

## Proof of Concept

1. As a user of org A, obtain (or guess) a paused execution UUID belonging to org B (UUIDs surface in SSE events, exports, and logs).
2. GET /api/workflows/executions/&lt;executionId&gt; — the handler queries by id only, returning B's execution including checkpoint config and inputContext.
3. POST /api/workflows/executions/&lt;executionId&gt;/checkpoints/&lt;checkpointId&gt;/resolve with {"status":"resolved","scopeId":"&lt;any scope uuid&gt;"} — `checkpointService.resolve` looks up the checkpoint by id with no org predicate and flips it to resolved, then `workflowExecutorV2.resume` loads the execution with no org predicate and continues executing B's workflow nodes in the attacker-chosen scope.

```javascript
// Cross-tenant checkpoint resolve/resume (conceptual — requires running instance):
const tokenA = '<org-A member JWT>';
await fetch(`${BASE}/api/workflows/executions/${bExecutionId}/checkpoints/${bCheckpointId}/resolve`, {
  method: 'POST',
  headers: { Authorization: `Bearer ${tokenA}`, 'Content-Type': 'application/json' },
  body: JSON.stringify({ status: 'resolved', scopeId: attackerChosenScopeId }),
});
// 200 + SSE stream of B's workflow resuming, despite tokenA belonging to another org.
// Static proof of the missing predicate (executed as repo grep, no runtime):
//   checkpoint.service.ts resolve(): findUnique({ where: { id: checkpointId } })          — no organization_id
//   checkpoint.routes.ts GET execution: findUnique({ where: { id: executionId } })        — no organization_id
//   workflow-executor-v2.ts resume(): findUnique({ where: { id: executionId } })          — no organization_id
```

## Remediation

Add organization scoping to all three paths: in `checkpointService.resolve`, look up the checkpoint with `findFirst({ where: { id, organization_id } })` (the org id is returned by the route's user context); in the checkpoint GET execution route and `workflowExecutorV2.resume`, filter `workflow_executions` by `organization_id` (and for resume, derive `scopeId` from the execution record instead of accepting it from the request body). Mirror the pattern already used in execution.routes.ts.

## Assumptions

Assumes a second authenticated user in a different organization and knowledge of (or guessed) a UUID of a paused execution or its checkpoint. No member/admin role needed — plain authentication suffices.
