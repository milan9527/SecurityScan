# No rate limiting or lockout on local login, plus seeded default admin credentials

**ID:** vuln-0003
**Severity:** CRITICAL
**Found:** 2026-11-21 04:06:21 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent/backend
**CWE:** CWE-307
**CVSS:** 9.1
**Confidence:** High
**Fix Effort:** Low

## Description

The local-mode login endpoint performs unauthenticated password attempts with no rate limiting, account lockout, CAPTCHA, or attempt counter. Combined with the seeded default credentials, an attacker can take over the admin account.

## Evidence

Source: `src/routes/auth.routes.ts:63-78` (no rate limiting, no lockout, uniform error message but trivially brute-forceable), `prisma/seed-local-auth.ts:32-39` (default `admin@example.com` / `admin123`), and absence of any brute-force control in `src/middleware/` (only token-quota for LLM usage exists).

## Impact

Account takeover of the seeded admin (`admin@example.com`, owner role) on any deployment that ran the seed script without changing the password, and of any weak local-mode password via online brute force. Owner role grants full administrative control of the platform's data.

## Counterevidence

Credential stuffing is standard behavior for a login endpoint; the finding is the absence of lockout/rate limiting at the application layer, which may be mitigated by an external WAF/reverse-proxy rate limiter not visible in the repository. bcrypt with cost 10 slows offline guessing but does not prevent online attempts. This is a real gap in the application itself, though its production impact depends on external mitigations.

## What Would Change This Severity

Presence of an external WAF or reverse-proxy rate limiter in the deployed environment would lower severity to medium.

## Technical Analysis

`POST /auth/login` (`src/routes/auth.routes.ts:47-102`) validates credentials via bcrypt comparison with no attempt limiting of any kind — no counter, no lockout, no delay, no rate-limit middleware on the route (only `enforceTokenQuota` for LLM usage exists elsewhere). `prisma/seed-local-auth.ts:32-33` seeds `admin@example.com` / `admin123` with owner role and only prints a console warning to change it (seed-local-auth.ts:91). The registration endpoint (`auth.routes.ts:109-197`) also has no password strength policy (any string accepted).

## Proof of Concept

1. Observe `POST /api/auth/login` accepts unlimited attempts. 2. With default seed, submit `admin@example.com` / `admin123` — the server returns a valid JWT and owner-role user. Not executed against a live service (isolated assessment); verified by code trace and bcrypt hash generation matching the seed.

```gdscript
// Offline verification: reproduce the seeded hash for the default credential
const bcrypt = require('/workspace/agentcore-superagent-update/super-agent/backend/node_modules/bcryptjs');
(async () => {
  const hash = await bcrypt.hash('admin123', 10); // same cost as seed-local-auth.ts:39
  console.log('bcrypt.compare("admin123", hash):', await bcrypt.compare('admin123', hash)); // -> true
})();
```

## Remediation

Add per-account and per-IP rate limiting and temporary lockout to `POST /api/auth/login` and `POST /api/auth/register` (e.g. Redis-backed counter, 429 responses). Force a password change on first login for seeded accounts, or generate a random initial password instead of `admin123`. Reject common passwords at registration.

## Assumptions

Local auth mode enabled (the default) with the seed script or default admin credentials in place, or any deployment where profiles are discoverable (registration is open, usernames are emails).
