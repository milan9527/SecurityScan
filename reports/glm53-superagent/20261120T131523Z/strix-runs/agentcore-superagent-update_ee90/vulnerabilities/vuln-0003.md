# Path traversal + git argument injection in plugin installation (installPlugins)

**ID:** vuln-0003
**Severity:** HIGH
**Found:** 2026-11-20 13:43:59 UTC
**Target:** /workspace/agentcore-superagent-update (super-agent backend)
**CWE:** CWE-22
**CVSS:** 7.7
**Confidence:** High
**Fix Effort:** Low

## Description

The scope-plugin installation path (WorkspaceManager.installPlugins) joins an attacker-controlled plugin name into the filesystem without any traversal check, and passes an attacker-controlled git URL into git clone as a positional argument. An authenticated user with modify access on a business scope can make the backend git-clone a repository into an arbitrary directory outside the session workspace (arbitrary file write), and can inject git options such as --upload-pack to execute an arbitrary command.

## Evidence

Local harness replicating the exact sink logic: join('/tmp/wsharness/ws/.claude/plugins', '../../../../../tmp/marker-plugin') as clone target → /tmp/marker-plugin/.git created outside workspace (verified via fs.access). Same argv shape with gitUrl='--upload-pack=touch /tmp/marker-uploadpack' → /tmp/marker-uploadpack created, proving option injection into git. Skill-name variant: join(skillsDir, '../../../../../../tmp/marker-evilskill') + mkdir/writeFile produced /tmp/marker-evilskill/SKILL.md; cp(localPath,…) variant produced /tmp/marker-localskill/SKILL.md.

## Impact

Arbitrary file/directory write outside the session workspace as the backend process user (locally confirmed: repo cloned into /tmp/marker-plugin via a ../-laden plugin name), and arbitrary command execution via git argv injection (--upload-pack=touch /tmp/marker-uploadpack confirmed). Enables overwriting other tenants' session workspaces (cross-tenant integrity) and planting files into paths later executed or read by the backend/agent runtimes.

## Counterevidence

Checked all paths for controls: route schema (businessScopes.routes.ts:839) allows any string; DB stores raw; buildScopeForWorkspace passes raw; installPlugins has no name validation. deleteWorkspaceSkill DOES have a startsWith guard (workspace-manager.ts:1420), proving the pattern was known but not applied here. gitUrl must be a clonable URL for the traversal variant, but the --upload-pack variant needs no valid repo.

## Confidence Rationale

Sink code read in full (complete source→sink trace); escape behavior of join+mkdir/cp and git-clone-into-traversal-path both demonstrated locally with exact code replicated. Only unexecuted step is the full HTTP route round-trip, straight-line code with no intervening sanitization.

## What Would Change This Severity

Confirmation that the backend runs with privileges that make planted files auto-executed (cron, systemd, module resolution paths) would raise this to critical; a read-only container FS would lower impact but not the vulnerability class.

## Technical Analysis

POST /api/business-scopes/:id/plugins (super-agent/backend/src/routes/businessScopes.routes.ts:836) accepts name (only minLength 1 / maxLength 100 — no character or path validation), gitUrl, ref from an authenticated user with modify access, stored raw into scope_plugins. On session provisioning, chat.service.ts buildScopeForWorkspace loads them and WorkspaceManager.ensureSessionWorkspace → installPlugins (src/services/workspace-manager.ts:932) computes `const targetDir = join(pluginsDir, plugin.name)` (line 941) with no containment check, then `execFile('git', ['clone','--depth','1','--branch', plugin.ref, plugin.gitUrl, targetDir])` (lines 949-952). Two primitives: (1) plugin.name containing `../` or an absolute path makes git clone write a full repo tree outside the workspace; (2) plugin.gitUrl is positional but git parses a leading-dash value as an option, so `--upload-pack=<cmd>` or `-o ProxyCommand=…` executes an arbitrary command with backend privileges — execFile's argv-array form does not mitigate option injection. Local replication of the exact sink code confirmed both primitives.

## Proof of Concept

1. POST /api/business-scopes/:id/plugins with name `../../../../../../../tmp/marker-plugin`, gitUrl of any reachable repo, ref main (businessScopes.routes.ts:836; requires only authenticate + requireModifyAccess). 2. Start any chat session in that scope — ensureSessionWorkspace calls installPlugins, which computes targetDir = join(workspace/.claude/plugins, plugin.name) and runs `git clone --depth 1 --branch ref gitUrl targetDir`. 3. Observe the cloned repo written outside the workspace base dir. Command-exec variant: set gitUrl to `--upload-pack=<cmd>`; git parses it as an option and executes it.

```gdscript
// Replicated sink (exact argv/join from workspace-manager.ts:941-952), run locally:
const { execFile } = require('child_process');
const { join } = require('path');
const pluginsDir = join('/tmp/wsharness/ws', '.claude', 'plugins');
// traversal via plugin.name:
execFile('git', ['clone', '--depth', '1', '--branch', 'main',
  'file:///tmp/wsharness/repo',
  join(pluginsDir, '../../../../../tmp/marker-plugin')],
  () => require('fs').access('/tmp/marker-plugin/.git',
    e => console.log(e ? 'failed' : 'TRAVERSAL CONFIRMED')));
// command injection via plugin.gitUrl:
execFile('git', ['clone', '--depth', '1', '--branch', 'main',
  '--upload-pack=touch /tmp/marker-uploadpack',
  'file:///tmp/wsharness/repo', '/tmp/wsharness/ok'], () =>
  require('fs').access('/tmp/marker-uploadpack',
    e => console.log(e ? 'failed' : 'GIT ARG INJECTION CONFIRMED')));
// Result (this sandbox): both markers created.
```

## Remediation

Validate plugin.name and plugin.ref against a strict allowlist (e.g. ^[A-Za-z0-9._-]+$, no leading dash, no path separators) at the POST /plugins route and again in installPlugins before the join; reject any resolved target whose relative() from pluginsDir escapes it. Reject gitUrl/ref values beginning with a dash and pass them only after a `--` argument separator; allowlist the URL scheme to https/ssh. Apply the same validation to the DELETE plugin cleanup path, which rm -rf's join(sessionsDir, sess.name, '.claude', 'plugins', plugin.name).

## Assumptions

Assumes an authenticated org user with modify access on a scope (default member-level permission) and one chat session start to trigger provisioning; no other privileges needed.
