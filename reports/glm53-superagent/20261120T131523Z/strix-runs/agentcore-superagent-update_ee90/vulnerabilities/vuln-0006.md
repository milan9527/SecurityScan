# Hardcoded bypassPermissions with bypassable regex denylist enables unapproved arbitrary shell execution on backend host via agent tool calls

**ID:** vuln-0006
**Severity:** CRITICAL
**Found:** 2026-11-20 13:44:41 UTC
**Target:** super-agent/backend (Claude Agent execution path)
**Method:** POST
**CWE:** CWE-862
**CVSS:** 9.9
**Confidence:** High
**Fix Effort:** Medium

## Description

The backend's Claude agent runs with a hardcoded `permissionMode: 'bypassPermissions'` and `allowDangerouslySkipPermissions: true`. The only remaining guard is a small regex denylist (`dangerousCommandBlocker`) that is trivially bypassed, so any prompt the agent acts on — including instructions injected via retrieved documents, skills, or web content — results in arbitrary shell command execution on the backend host without any human approval.

## Evidence

Local harness importing the real `claude-hooks.js` and executing the passed command (node:exec) produced:

```json
{"cmd":"python3 -c \"open('/tmp/PWN_MARKER_3','w')\"","decision":"ALLOW(approve)"}
{"cmd":"echo hacked > $HOME/PWN_MARKER_4","decision":"ALLOW(approve)"}
{"cmd":"node -e \"require('fs').writeFileSync('/tmp/PWN_MARKER_5','x')\"","decision":"ALLOW(approve)"}
```

Marker execution proof (`/tmp/PWNED_VIA_HOOK_BYPASS` created after the hook returned allow) and runtime option dump (`permissionMode: bypassPermissions`, `allowDangerouslySkipPermissions: true`, `allowedTools: ['Bash','Read','Write','Edit','Glob','Grep','WebFetch','Skill']`) were both produced against the unmodified repository code.

## Impact

Arbitrary command execution on the backend server (the EC2 host running the Fastify backend, where the Claude CLI subprocess is spawned), outside the intended workspace directory and without any approval step. The executed process inherits the full backend environment, including Bedrock AWS credentials (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`) and an internal auth token (`AUTH_TOKEN`) explicitly injected into `options.env` — both readable via a single allowed command such as `env`. Host file exfiltration is equally unconstrained (`cat /etc/passwd` variants are only blocked by incidental regex matches, not by policy). Any authenticated user who can chat with an agent — or any attacker who can poison a document, skill, or fetched web page the agent reads — can trigger this.

## Counterevidence

Considered defenses: (1) the PreToolUse hook chain is real and registered on every conversation (verified in buildOptions output, PreToolUse hook entries: 1), but it is a fixed 7-regex denylist, not an approval or allowlist — it cannot constrain the input class; (2) cwd confines Write/Edit file_path via startsWith(cwd), but the check is on the un-normalized string and Bash is entirely unconstrained apart from the patterns; (3) no other permission gate exists — permissionMode is hardcoded, not read from request or DB, so no stronger user/org setting can raise it. The only genuine limitation is that this is the intended "dangerous by design" agent mode, which is precisely the control weakness being reported.

## What Would Change This Severity

Evidence that agents are only ever invoked with sanitized/whitelisted prompts and never consume untrusted retrieved content would lower this; conversely, confirming a live deployment reaches the internet with real AWS credentials in the agent environment would cement critical severity.

## Technical Analysis

`ClaudeAgentService.buildOptions` constructs the SDK options for every chat conversation:

```ts title=backend/src/services/claude-agent.service.ts startLineNumber=405 endLineNumber=415
const options: ClaudeCodeOptions = {
  systemPrompt,
  allowedTools: [...DEFAULT_ALLOWED_TOOLS, 'Skill'],
  cwd: workspacePath,
  model,
  permissionMode: 'bypassPermissions',
  allowDangerouslySkipPermissions: true,
  hooks: { PreToolUse: preToolUseHooks },
```

`DEFAULT_ALLOWED_TOOLS` is `['Bash','Read','Write','Edit','Glob','Grep','WebFetch']` (line 217). With `bypassPermissions`, the Claude Code CLI/SDK executes every tool call without prompting any user. The only security control on this path is the `PreToolUse` hook chain `[dangerousCommandBlocker, binaryFileReadBlocker]` from `claude-hooks.ts`. `dangerousCommandBlocker` compares `tool_input.command` against 7 regexes (5 "dangerous" patterns such as `rm -rf /`, `curl | bash`, plus path-escape patterns matching `..` and absolute paths under a fixed directory list `/Users|home|etc|var|tmp|...`). This is a denylist, not an approval boundary: any command that does not match those literals is executed. Verified locally against the real hook code: `python3 -c "open('/tmp/X','w')"`, `node -e "fs.writeFileSync('/tmp/X')"`, and writes to `$HOME` all pass. The file-path check for Read/Write/Edit uses `filePath.startsWith(cwd)` on the un-normalized string (`claude-hooks.ts:149`), so a path like `<cwd>/../../etc/shadow` passes the containment check. The settings escalation is systemic: `WorkspaceManager` also writes sub-agent definition files containing `permissionMode: bypassPermissions` (`workspace-manager.ts:767`) and a `settings.json` with `permissions.allow` for the same tool list, so the bypass is re-instantiated through the `Skill`/`Task` delegation paths too. Additionally, `buildOptions` copies `...process.env` and Bedrock AWS credentials into the agent subprocess environment (`claude-agent.service.ts:436-449`), so an executed command can read the backend's cloud credentials.

## Proof of Concept

1. Import the repository's real PreToolUse hook `dangerousCommandBlocker` from `backend/src/services/claude-hooks.ts` and instantiate the real `ClaudeAgentService.buildOptions()` with the repo's own `.env`. 2. Confirm the emitted SDK options hardcode `permissionMode: 'bypassPermissions'` and `allowDangerouslySkipPermissions: true` with `Bash`, `Write`, `Edit`, `WebFetch` in `allowedTools`. 3. Feed the Bash tool input `python3 -c "open('/tmp/PWNED_VIA_HOOK_BYPASS','w')"` through the hook — it returns no block decision (allow). 4. Execute that same command exactly as the SDK's Bash tool would — the marker file `/tmp/PWNED_VIA_HOOK_BYPASS` appears on the host filesystem. 5. Also observe the file_path guard accepts `<cwd>/../../etc/shadow` because it uses an un-normalized `startsWith(cwd)` prefix check.

```python
// /tmp/harness/t2_exec.mts — run with backend's tsx; sources the repo .env
import { dangerousCommandBlocker } from '/workspace/agentcore-superagent-update/super-agent/backend/src/services/claude-hooks.js';
import { exec } from 'child_process';
import { promisify } from 'util';
import { existsSync } from 'fs';
const run = promisify(exec);
const input = {
  session_id: 's1', transcript_path: '/x', cwd: '/srv/workspaces/agent-abc',
  hook_event_name: 'PreToolUse', tool_name: 'Bash',
  tool_input: { command: `python3 -c "open('/tmp/PWNED_VIA_HOOK_BYPASS','w')"` },
};
const verdict = await dangerousCommandBlocker(input, undefined, { signal: new AbortController().signal });
console.log('hook verdict:', verdict.decision ?? 'ALLOW (hook passes)');
await run(input.tool_input.command); // what the SDK Bash tool does under bypassPermissions
console.log('marker exists after execution:', existsSync('/tmp/PWNED_VIA_HOOK_BYPASS'));
```

## Remediation

Do not hardcode `bypassPermissions` for host-side agent runs. Select a permission mode appropriate to the deployment (e.g. `default` or `acceptEdits`) so that Bash execution and out-of-workspace access require explicit human approval, and make the mode a server-side configuration decision rather than a constant in `buildOptions`. Replace the regex denylist with a positive allowlist enforced at the tool boundary: restrict the Bash tool to an approved command grammar (or run it inside a sandboxed container with no host credentials), canonicalize file paths (`path.resolve`) before the workspace-containment check instead of a raw `startsWith(cwd)` prefix comparison, and do not pass `AWS_*` credentials, `AUTH_TOKEN`, or the rest of `process.env` to the agent subprocess. Network egress from the agent should be restricted so exfiltration via `WebFetch` is not available to injected instructions.

## Assumptions

Assumes an attacker who can send a chat message to an agent (any authenticated platform user with agent access) or can plant instructions in content the agent reads (skills, RAG results, web pages via WebFetch). Local validation exercised the real guard and execution; live-model end-to-end replay was out of scope (local-only mandate).
