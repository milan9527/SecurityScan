# AgentCore runtime executes all agent tool calls with no approval or PreToolUse security hook (bypassPermissions, unfiltered Bash/WebFetch/Write)

**ID:** vuln-0007
**Severity:** CRITICAL
**Found:** 2026-11-20 13:45:00 UTC
**Target:** super-agent/agentcore (AgentCore runtime container)
**Method:** POST
**CWE:** CWE-862
**CVSS:** 9.9
**Confidence:** High
**Fix Effort:** Medium

## Description

The AgentCore container runtime (`agentcore/src/agent-runner.ts`) runs the Claude agent with hardcoded `permissionMode: 'bypassPermissions'` and registers **no security hook at all** — its only hooks are S3 file-sync observers. Every tool call, including shell commands, web fetches, and arbitrary file writes, executes with zero approval or filtering, so injected instructions in restored workspace files, RAG results, or fetched web content translate directly into unapproved execution inside the runtime container.

## Evidence

Static trace of the unmodified runtime (verified by full file read):

```ts title=agentcore/src/agent-runner.ts startLineNumber=283 endLineNumber=320
const baseOptions: Record<string, unknown> = {
  systemPrompt: payload.system_prompt ?? undefined,
  allowedTools: payload.allowed_tools ?? DEFAULT_TOOLS,
  cwd: '/workspace',
  permissionMode: 'bypassPermissions',
  allowDangerouslySkipPermissions: true,
  settingSources: ['project'],
};
...
if (bucket && prefix) {
  baseOptions.hooks = {
    PostToolUse: [ { matcher: 'Write|Edit', hooks: [createFileChangeHook(bucket, prefix)] } ],
    Stop: [ { hooks: [createStopHook(bucket, prefix)] } ],
  };
}
```

No PreToolUse entry exists anywhere in `agentcore/src/`. Contrast with the backend runtime, which at least registers `dangerousCommandBlocker`.

## Impact

Arbitrary unapproved shell command execution, arbitrary file write, and unrestricted network egress (WebFetch/WebSearch) inside the AgentCore runtime container for any instruction the model acts on — including instructions from prompt-injection sources: workspace files restored from S3 (skills, sub-agent definitions, `CLAUDE.md`), knowledge/RAG results fetched via the injected backend token, and fetched web pages. The container holds the workspace, the `AUTH_TOKEN` backend credential, and any container-resident credentials; the Stop-hook full S3 sync (`syncWorkspaceToS3`) then mirrors attacker-created or modified files back into the organization's persistent S3 workspace, persisting the compromise across sessions.

## Counterevidence

Considered: the runtime does register hooks (PostToolUse S3-sync, Stop full sync), but neither intercepts tool execution; `payload.allowed_tools` could theoretically narrow the tool list, but no backend caller sets it (grep shows no producer), so the default full list applies; the container is a microVM, which limits host blast radius relative to the backend-host finding, but the workspace, the injected backend token, and any credentials placed in the container remain fully exposed; `WebFetch`/`WebSearch` have no egress restriction anywhere in the runtime. No control was found that gates or inspects a tool call before execution.

## What Would Change This Severity

Evidence that `payload.allowed_tools` is populated with a restrictive list by the backend in real deployments would lower this; confirmation that microVM isolation plus IAM blocks all credential and S3 reachability would lower confidentiality/integrity impact.

## Technical Analysis

`runAgent()` in `agentcore/src/agent-runner.ts` builds the SDK options for every AgentCore invocation:

```ts title=agentcore/src/agent-runner.ts startLineNumber=283 endLineNumber=289
const baseOptions: Record<string, unknown> = {
  systemPrompt: payload.system_prompt ?? undefined,
  allowedTools: payload.allowed_tools ?? DEFAULT_TOOLS,
  cwd: '/workspace',
  permissionMode: 'bypassPermissions',
  allowDangerouslySkipPermissions: true,
```

`DEFAULT_TOOLS` (line 23) includes `Bash`, `Write`, `Edit`, `WebSearch`, `WebFetch`, `Task`, `Skill`. Hooks are registered **only** when S3 workspace sync is configured, and those hooks are `PostToolUse` (matcher `Write|Edit`, uploads the file the tool already wrote) and `Stop` (full workspace upload). A repository-wide search of `agentcore/src/` shows zero `PreToolUse` registrations — unlike the backend runtime (`claude-agent.service.ts`), which at least installs `dangerousCommandBlocker`. So in the AgentCore path there is no security inspection of any tool invocation: the model's tool call goes straight to execution. The prompt itself is attacker-influenceable through several untrusted channels: (a) `restoreWorkspaceFromS3` (`index.ts:46-53`) copies every object under the org/session S3 prefix — including skill `SKILL.md` files, sub-agent `.md` definitions, and `CLAUDE.md` — into `/workspace` before the run, all of which the SDK loads via `settingSources: ['project']`; (b) `index.ts:73-75` sets `process.env.AUTH_TOKEN` from the payload so the agent can query the backend RAG; (c) `WebFetch`/`WebSearch` pull arbitrary web content mid-run. Any instruction embedded in those sources is executed with no approval step, and attacker-written files persist via `syncWorkspaceToS3`.

## Proof of Concept

1. Read `agentcore/src/agent-runner.ts` `runAgent()` and `agentcore/src/index.ts`: confirm `permissionMode: 'bypassPermissions'` + `allowDangerouslySkipPermissions: true` with `DEFAULT_TOOLS` including `Bash`, `Write`, `Edit`, `WebSearch`, `WebFetch`, `Task`, `Skill`. 2. Enumerate all hook registrations: only `PostToolUse` (S3 sync of Write/Edit results) and `Stop` (full workspace sync) exist — there is no `PreToolUse` security hook in the entire `agentcore/src/` tree. 3. Note the untrusted-content entry points: `restoreWorkspaceFromS3` restores organization-controlled/S3-restored skill and agent files into `/workspace` before the run, and `index.ts` sets `AUTH_TOKEN` from the payload so the agent can call the backend RAG API. Under `bypassPermissions` the SDK executes any Bash tool call derived from these sources immediately — no human approval step exists in this code path. Local-only constraint prevented invoking a live Bedrock AgentCore runtime; the absence of the control is a complete static fact of the executed code path.

## Remediation

Port the PreToolUse guard chain from the backend runtime into `agent-runner.ts` as a baseline, then move beyond a denylist: default the container runtime to a permission mode requiring approval for Bash and out-of-workspace access (or restrict `allowedTools` per deployment), register a PreToolUse hook that enforces workspace containment via canonicalized path comparison, and restrict outbound network access from the container so injected instructions cannot exfiltrate data or fetch additional payloads via WebFetch/WebSearch. Ensure the injected `AUTH_TOKEN` is scoped to the minimum API surface (read-only RAG search) rather than a full member-role token.

## Assumptions

Assumes an attacker who can send a chat message to an agent routed to the AgentCore runtime (deployment configured with AGENT_RUNTIME=agentcore), or who can plant instructions in content the agent retrieves (S3-restored skills, RAG results via backend_api_key, WebFetch/WebSearch pages). Consequence boundary (no approval/no PreToolUse filter on Bash/Write/WebSearch) was verified by reading the unmodified runtime code; live end-to-end replay through Bedrock AgentCore was out of scope (local-only mandate, no AWS contact).
