# Cross-tenant IDOR in support agent-group member removal (no org scoping)

**ID:** vuln-0011
**Severity:** HIGH
**Found:** 2026-11-20 13:47:11 UTC
**Target:** super-agent/backend (local repo /workspace/agentcore-superagent-update)
**Method:** DELETE
**CWE:** CWE-639
**CVSS:** 7.1
**Confidence:** High
**Fix Effort:** Low

## Description

The support-settings agent-group member removal endpoint deletes group members by bare group and user IDs with no organization scoping, allowing an authenticated user of one tenant to remove members from another tenant's support agent groups.

## Evidence

support-settings.service.ts:

```sql
async removeGroupMember(groupId: string, userId: string) {
  await prisma.agent_group_members.deleteMany({
    where: { agent_group_id: groupId, user_id: userId },
  });
}
```
Sibling addGroupMember verifies organization_id; removeGroupMember does not.

## Impact

Cross-tenant integrity: removal of members from a foreign tenant's support agent groups, disrupting their support routing and escalation workflows.

## Counterevidence

The sibling addGroupMember in the same service DOES verify group ownership (agent_groups.findFirst where id + organization_id) before inserting — the check exists in the file but was omitted only from removeGroupMember. Routes require authenticate.

## Confidence Rationale

Source-to-sink trace with the where clause read verbatim from service code; local repo, no live deployment for HTTP-level reproduction.

## What Would Change This Severity

A live two-tenant deployment test would confirm end-to-end; unguessable group IDs in practice would raise attack_complexity.

## Technical Analysis

routes/support.routes.ts DELETE /agent-groups/:id/members/:userId (line ~246) calls supportSettingsService.removeGroupMember(request.params.id, request.params.userId) — no orgId passed. support-settings.service.ts removeGroupMember (line 59-63) runs deleteMany with where { agent_group_id, user_id } only. The route-level caller supplies orgId to updateAgentGroup/deleteAgentGroup and addGroupMember but not to the remove path.

## Proof of Concept

1. Authenticate as any user in Org A. 2. DELETE /api/support/settings/agent-groups/:id/members/:userId with Org B's group id — removeGroupMember deletes by bare agent_group_id + user_id. Contrast with POST members (addGroupMember), which verifies organization_id and returns 404 for foreign groups.

```scdoc
DELETE /api/support/settings/agent-groups/<orgB-group-id>/members/<victim-user-id>
// prisma.agent_group_members.deleteMany({ where: { agent_group_id, user_id } })  // no organization_id
```

## Remediation

In support-settings.service.ts removeGroupMember, replicate the ownership check already present in addGroupMember (agent_groups.findFirst where id + organization_id, 404 when not found) before the deleteMany.

## Assumptions

Authenticated user; agent-group member rows targeted by ID obtainable from group listings.
