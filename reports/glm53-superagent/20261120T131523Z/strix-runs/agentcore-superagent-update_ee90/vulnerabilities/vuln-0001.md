# Cross-tenant IDOR on all knowledge-base routes (read/write/delete of other organizations' KBs and files)

**ID:** vuln-0001
**Severity:** HIGH
**Found:** 2026-11-20 13:43:30 UTC
**Target:** /workspace/agentcore-superagent-update (super-agent/backend)
**Endpoint:** /api/knowledge-bases/*
**Method:** GET/PUT/DELETE/POST
**CWE:** CWE-639
**CVSS:** 8.3
**Confidence:** High
**Fix Effort:** Low

## Description

All knowledge-base management routes (`/api/knowledge-bases/*`) perform authentication but no organization-scoping on object lookups. `knowledgeBaseService` queries Prisma by bare record ID, so an authenticated user from any organization can read, modify, and delete another organization's knowledge bases, folders, and uploaded files.

## Evidence

Local unit-level PoC executed against the real route plugins with a faithful in-memory Prisma mock (`tests/unit/kb-idor.poc.test.ts`): all 9 assertions passed, including cross-org read (200 + org-B data returned), cross-org file update (`PWNED-BY-ORG-A` written to org-B row), cross-org file delete, and KB rename/soft-delete. vitest output: `Test Files 2 passed, Tests 12 passed`.

## Impact

Cross-tenant breach of knowledge-base confidentiality and integrity: an authenticated member of organization A can enumerate knowledge-base IDs and read org B's knowledge bases (names, descriptions, file listings), rename/soft-delete them, and modify or delete org B's uploaded knowledge files. Knowledge bases aggregate a tenant's RAG document corpus, so this exposes another tenant's content metadata and allows destructive modification.

## Counterevidence

Checked for mitigations: no `requireScopeAccess`/`requireAgentAccess` on these routes, no org filter in `knowledge-base.service.ts` read/update/delete/findById calls, and no global authz hook in route registration (`src/routes/index.ts` registers `knowledgeBaseRoutes` with a bare prefix). Only `listByOrganization` and `create` scope by org. No WAF or gateway-layer tenant filter exists in this codebase. The local repro follows production Prisma `where`-clause semantics exactly.

## What Would Change This Severity

If knowledge-base IDs were unguessable and never leaked this would not reduce the demonstrated IDOR; only confirmation of an upstream gateway tenant filter (none exists in this codebase) would lower severity.

## Technical Analysis

Route `src/routes/knowledge-base.routes.ts` guards every endpoint only with `[authenticate, requireModifyAccess]` — a role check, not a tenant check. Handlers call `knowledgeBaseService.findById(request.params.id)` etc. without passing `request.user.orgId`. In `src/services/knowledge-base.service.ts`:
- `findById` (line 69): `prisma.knowledge_bases.findUnique({ where: { id } })` — no `organization_id` filter.
- `update` (line 80) and `delete` (line 91): `update({ where: { id } })` — mutates any org's KB.
- `renameFolder` (200), `deleteFolder` (215), `listFolders` (190): unscoped by organization.
- File handlers in the route operate on `knowledge_files` by bare id.

Contrast with the correctly-scoped pattern in `credential-vault.repository.ts:37` (`findFirst({ where: { id, organization_id } })`), which shows the missing control.

## Proof of Concept

1. Authenticate as a member of org A. 2. GET /api/knowledge-bases/:id with an org B knowledge-base ID — 200 with org B data (organization_id of org B returned). 3. PUT /api/knowledge-bases/:id — renames org B's KB. 4. GET /api/knowledge-bases/:id/files — lists org B file records; PUT .../files/:fileId changes display metadata; DELETE .../files/:fileId removes org B's file record. 5. DELETE /api/knowledge-bases/:id soft-deletes org B's KB.

```ecl
# Reproduce (repo-local, no network):
cd super-agent/backend && npx vitest run tests/unit/kb-idor.poc.test.ts
# Key assertions from that PoC:
# - GET    /api/knowledge-bases/<ORG_B_KB_ID>          -> 200, data.organization_id == ORG_B
# - PUT    /api/knowledge-bases/<ORG_B_KB_ID>          -> 200, name renamed by org-A user
# - DELETE /api/knowledge-bases/<ORG_B_KB_ID>          -> 204, status='deleted'
# - PUT    /api/knowledge-bases/<ORG_B_KB_ID>/files/<ORG_B_FILE_ID> -> 200, display_name overwritten
# - DELETE /api/knowledge-bases/<ORG_B_KB_ID>/files/<ORG_B_FILE_ID>  -> 204, org-B row removed
```

## Remediation

Add organization scoping at the service layer: `findById(id, organizationId)` must use `findFirst({ where: { id, organization_id } })` (the pattern already used by `credential-vault.repository.ts`), and `update`/`delete`/folder/file operations must verify the parent record's organization before mutating. Alternatively, enforce org checks in the routes and pass `request.user.orgId` into every service call.

## Assumptions

Any authenticated platform user with a valid membership in any organization (role `member` suffices — `requireModifyAccess` is a role check only).
