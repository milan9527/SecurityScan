# Cross-tenant IDOR in userGroups member removal and skill/MCP access-grant endpoints (no org scoping)

**ID:** vuln-0008
**Severity:** HIGH
**Found:** 2026-11-20 13:46:39 UTC
**Target:** super-agent/backend (local repo /workspace/agentcore-superagent-update)
**Method:** DELETE, PUT, GET
**CWE:** CWE-639
**CVSS:** 7.6
**Confidence:** High
**Fix Effort:** Low

## Description

The user-group member and access-grant endpoints operate on bare group/skill/MCP IDs with no organization scoping. An authenticated user of any tenant can remove members from another tenant's user group and rewrite the full access-grant list (skill and MCP server group access) for another organization's skills and MCP servers.

## Evidence

Local vitest harness (mocked Prisma) against the real repositories — 3/3 passed:

```
✓ userGroup.removeMember deletes by bare group_id+user_id
  where = { group_id: 'grp-OTHERORG', user_id: 'victim-user' }   // no organization_id
✓ userGroup.grantSkillAccess rewrites skill access by bare skill_id
  deleteMany where = { skill_id: 'skill-OTHERORG' }               // no organization_id
  createMany data[0] = { skill_id, group_id, granted_by }         // no organization_id
```

## Impact

Cross-tenant integrity: arbitrary removal of members from a foreign tenant's user groups (access revocation/DoS on their workflows), and full rewrite of skill_group_access / mcp_group_access rows for foreign tenants' skills and MCP servers — granting or revoking cross-org access to sensitive skills and MCP tool servers, a lateral-movement primitive.

## Counterevidence

Checked for controls: requireModifyAccess runs on mutating routes but is a role gate, not an object-ownership check — it never inspects orgId against the target row. Repository has no org filter on removeMember/grantSkillAccess. The same repository's findById/update/delete DO filter by organization_id, confirming org scoping is the intended pattern and is absent only on these sinks.

## Confidence Rationale

Complete source-to-sink trace with executed local PoC against real route code with mocked Prisma; no live multi-tenant deployment exists to run the HTTP request end-to-end (local-only scope).

## What Would Change This Severity

A live two-tenant deployment test would confirm end-to-end; if group/skill/MCP IDs proved unguessable in practice, exploitability (attack_complexity) would rise and severity could drop.

## Technical Analysis

Route handlers (`routes/userGroups.routes.ts:147` DELETE /:id/members/:userId, `:160` PUT /skills/:skillId/access, `:182` PUT /mcp/:mcpId/access) pass raw path params straight to the repository. `userGroup.repository.ts` scopes findById/update/delete by organization_id (line 48), but `removeMember` (line 94-98) deletes `user_group_members` by bare `group_id`+`user_id`, `grantSkillAccess` (line 112-120) deletes and re-creates `skill_group_access` by bare `skill_id`, and `grantMcpAccess` (line 144-151) does the same for `mcp_group_access` by bare `mcp_server_id`. `getSkillGroupIds`/`getMcpGroupIds` (lines 122, 153) also leak cross-org group IDs unscoped. No organization_id appears anywhere in these where clauses, so a caller from Org A operating on Org B's IDs succeeds.

## Proof of Concept

1. Authenticate as any user in Org A. 2. DELETE /api/user-groups/:id/members/:userId with a foreign org's group id — userGroupRepository.removeMember deletes by bare group_id+user_id with no org filter. 3. PUT /api/user-groups/skills/:skillId/access (and /mcp/:mcpId/access) with a foreign skill/MCP id — grantSkillAccess/grantMcpAccess first deleteMany by bare skill_id/mcp_server_id then re-create grants, cross-tenant. Local unit PoC (vitest, mocked Prisma) confirms the Prisma where clauses contain no organization scoping.

```scilab
// /tmp/poc/idor-sweep.test.ts — executed, 3/3 passed against real repository code with mocked Prisma
await userGroupRepository.removeMember('grp-OTHERORG', 'victim-user');
// prisma.user_group_members.deleteMany where = { group_id: 'grp-OTHERORG', user_id: 'victim-user' }

await userGroupRepository.grantSkillAccess('skill-OTHERORG', ['g1'], 'me');
// prisma.skill_group_access.deleteMany where = { skill_id: 'skill-OTHERORG' }
// prisma.skill_group_access.createMany data = [{ skill_id, group_id: 'g1', granted_by: 'me' }]
```

## Remediation

Add organization_id to every where clause in userGroup.repository.ts (addMember, removeMember, grantSkillAccess, grantMcpAccess, getSkillGroupIds, getMcpGroupIds) and have route handlers pass request.user.orgId through, matching the pattern already used by findById/update/delete in the same repository.

## Assumptions

Authenticated user in any organization; object IDs (groups, skills, MCP servers) obtainable via other list endpoints or leaks.
