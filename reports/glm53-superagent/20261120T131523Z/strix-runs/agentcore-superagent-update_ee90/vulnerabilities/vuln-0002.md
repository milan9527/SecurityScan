# Cross-tenant IDOR on briefing routes (read/mark-read/archive other organizations' scope briefings)

**ID:** vuln-0002
**Severity:** MEDIUM
**Found:** 2026-11-20 13:43:41 UTC
**Target:** /workspace/agentcore-superagent-update (super-agent/backend)
**Endpoint:** /api/business-scopes/:scopeId/briefings*
**Method:** GET/PATCH/DELETE
**CWE:** CWE-639
**CVSS:** 5.4
**Confidence:** High
**Fix Effort:** Low

## Description

Briefing routes under `/api/business-scopes/:scopeId/briefings` filter only by `business_scope_id` and never by organization or caller membership. Any authenticated user can read another organization's scope briefings (titles, summaries, importance, agent identity) and mark them read or archive them.

## Evidence

Local PoC (`tests/unit/kb-idor.poc.test.ts`, describe 'C4'): org-A user requests org-B scope briefings — GET returns `SECRET-BRIEFING`; PATCH read flips `is_read` on the org-B row; DELETE sets `is_archived` on the org-B row. All 3 assertions passed (vitest: 12 tests passed).

## Impact

Cross-tenant confidentiality and integrity breach on AI-generated business-scope briefings: another tenant's briefing content (titles, summaries, event metadata, agent display names) is disclosed, and read/archive state can be tampered with. Impact limited to briefing objects, hence lower than the KB finding.

## Counterevidence

Checked for mitigations: routes carry only `authenticate` (no `requireScopeAccess`, whose default extractor reads `params.scopeId` and would have enforced scope membership). No organization_id filter exists in any briefing query, and the schema has `organization_id` available on `scope_briefings` for enforcement. PoC used faithful Prisma where-clause semantics on real route plugins.

## What Would Change This Severity

If briefings were confirmed to contain no sensitive content (marketing-only) severity would drop; if they embed document excerpts severity would rise.

## Technical Analysis

`src/routes/briefing.routes.ts`: all four routes use only `preHandler: [authenticate]`. The GET handler (line ~29) queries `prisma.scope_briefings.findMany({ where: { business_scope_id: scopeId, ... } })` — no organization_id, no scope-membership check. The PATCH/DELETE handlers (lines ~58-84) call `prisma.scope_briefings.update({ where: { id, business_scope_id: scopeId } })` — again no tenant filter; the caller can act on any org's briefing given its scope and briefing IDs. The stats route likewise counts by scope only. Contrast with routes that correctly mount `requireScopeAccess` (e.g. scopeMemberships.routes.ts).

## Proof of Concept

1. Authenticate as member of org A. 2. GET /api/business-scopes/<orgB-scope-id>/briefings — returns org B's briefing list including titles/summaries. 3. PATCH .../briefings/:id/read — flips org B's briefing to read. 4. DELETE .../briefings/:id — archives org B's briefing.

```ecl
# Reproduce (repo-local, no network):
cd super-agent/backend && npx vitest run tests/unit/kb-idor.poc.test.ts
# C4 assertions:
# - GET    /api/business-scopes/<ORG_B_SCOPE>/briefings          -> 200, contains 'SECRET-BRIEFING'
# - PATCH  /api/business-scopes/<ORG_B_SCOPE>/briefings/<id>/read -> 200, org-B is_read=true
# - DELETE /api/business-scopes/<ORG_B_SCOPE>/briefings/<id>      -> 200, org-B is_archived=true
```

## Remediation

Add `organization_id: request.user.orgId` to every `scope_briefings` query, or mount `requireScopeAccess('member')` on these routes so scope membership is verified before the handler runs.

## Assumptions

Any authenticated platform user of any organization.
