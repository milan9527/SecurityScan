# Cross-tenant IDOR in business-scope plugin/MCP delete and list routes (no org scoping)

**ID:** vuln-0010
**Severity:** HIGH
**Found:** 2026-11-20 13:47:03 UTC
**Target:** super-agent/backend (local repo /workspace/agentcore-superagent-update)
**Method:** DELETE, GET
**CWE:** CWE-639
**CVSS:** 7.6
**Confidence:** High
**Fix Effort:** Low

## Description

The business-scope plugin and MCP-server management routes issue DELETE statements scoped only by plugin/assignment ID and scope ID with no organization_id filter, and the plugin/MCP listing routes read cross-org data the same way. An authenticated user of any tenant can delete another tenant's scope plugins (including removing their cloned directories from disk) and detach their MCP server assignments.

## Evidence

Route code (businessScopes.routes.ts):

```sql
-- DELETE /:id/plugins/:pluginId (line ~894)
DELETE FROM scope_plugins WHERE id = ${pluginId}::uuid AND business_scope_id = ${scopeId}::uuid
-- DELETE /:id/mcp-servers/:assignmentId (line ~1011)
DELETE FROM scope_mcp_servers WHERE id = ${assignmentId}::uuid AND business_scope_id = ${scopeId}::uuid
-- GET /:id/plugins (line ~821) and GET /:id/mcp-servers (line ~940): SELECT ... WHERE business_scope_id = ${id}::uuid
```

## Impact

Cross-tenant integrity/availability: delete a foreign tenant's scope plugins (also recursively deletes their cloned plugin directories from session workspaces on disk) and detach their MCP server assignments, disrupting foreign tenants' agent capabilities; and read foreign tenants' plugin git URLs and MCP server configs (including host addresses) via the unscoped GET routes.

## Counterevidence

POST plugin and POST mcp-servers routes DO verify scope ownership via businessScopeService.getBusinessScopeById(id, orgId) before writing — confirming the codebase's intended pattern, absent only on the delete/list routes. requireModifyAccess is a role gate, not an ownership check. Note org_id only appears in the config_version bump UPDATE, which does not restrict the DELETE statements.

## Confidence Rationale

Complete source-to-sink trace verified directly in route code (raw SQL where clauses read verbatim); no live deployment available for HTTP-level reproduction (local-only scope).

## What Would Change This Severity

A live two-tenant deployment test would confirm end-to-end; if the raw DELETE affected 0 rows for foreign scopes due to an unverified DB-level control, severity would drop.

## Technical Analysis

In routes/businessScopes.routes.ts the DELETE /:id/plugins/:pluginId handler (lines ~880-927) executes `DELETE FROM scope_plugins WHERE id = ${pluginId}::uuid AND business_scope_id = ${scopeId}::uuid` with no organization_id in the WHERE, then removes cloned plugin directories for that scope. DELETE /:id/mcp-servers/:assignmentId (lines ~1001-1022) executes `DELETE FROM scope_mcp_servers WHERE id = ${assignmentId}::uuid AND business_scope_id = ${scopeId}::uuid` — also unscoped. GET /:id/plugins (~821) and GET /:id/mcp-servers (~940) SELECT by business_scope_id only, leaking foreign plugin git_urls and MCP server configs (host_address, config JSON). The config_version bump after each mutation is scoped by org but only updates the count, not the deletion.

## Proof of Concept

1. Authenticate as any user in Org A. 2. DELETE /api/business-scopes/:scopeId/plugins/:pluginId with Org B's scope ID and plugin ID — the raw SQL deletes by plugin_id + scope_id only; org_id appears in no WHERE clause of the DELETE. 3. The route then removes cloned plugin directories under workspaceBaseDir/<orgB>/<scopeB>/sessions. 4. DELETE /api/business-scopes/:id/mcp-servers/:assignmentId similarly deletes scope_mcp_servers by assignment_id + scope_id only. GET /:id/plugins and /:id/mcp-servers also leak foreign data (plugin git_urls, MCP configs).

```verilog
DELETE /api/business-scopes/<orgB-scope-id>/plugins/<orgB-plugin-id>
DELETE /api/business-scopes/<orgB-scope-id>/mcp-servers/<orgB-assignment-id>
// Both execute: DELETE ... WHERE id = $X AND business_scope_id = $Y  -- no organization_id
```

## Remediation

In businessScopes.routes.ts, verify the target scope belongs to the caller's organization (businessScopeService.getBusinessScopeById(id, orgId)) before the DELETE/SELECT statements on plugin delete, plugin list, MCP assignment delete, and MCP list — matching the verification already present on the POST routes.

## Assumptions

Authenticated user; business-scope IDs obtainable via listings or shared with the same attacker via showcase packs.
