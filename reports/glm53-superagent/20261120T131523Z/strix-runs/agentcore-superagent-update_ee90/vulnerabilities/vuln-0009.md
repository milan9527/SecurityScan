# Cross-tenant IDOR in business-scope membership role update and removal (no org scoping)

**ID:** vuln-0009
**Severity:** HIGH
**Found:** 2026-11-20 13:46:50 UTC
**Target:** super-agent/backend (local repo /workspace/agentcore-superagent-update)
**Method:** PATCH, DELETE
**CWE:** CWE-639
**CVSS:** 7.1
**Confidence:** High
**Fix Effort:** Low

## Description

Business-scope membership update and removal endpoints operate on bare membership IDs with no organization scoping. An authenticated user who is scope-admin of any scope in their own org can change a member's role to 'admin' on, or delete, a scope membership belonging to another organization, escalating or revoking a foreign tenant's members.

## Evidence

Local vitest harness (mocked Prisma) against the real repository — passed:

```
✓ scopeMembership.updateRole / delete by bare membership id
  prisma.scope_memberships.update where = { id: 'membership-OTHERORG' }
  prisma.scope_memberships.delete where = { id: 'membership-OTHERORG' }
```

## Impact

Cross-tenant integrity: an org-A scope-admin can grant 'admin' role to any user (including the attacker) on an org-B scope, or remove org-B members from their scopes — privilege escalation into a foreign tenant's agent scopes (which control skills, plugins, IM channels).

## Counterevidence

requireScopeAccess('admin') on the mutation routes does verify the caller is an admin of the scope named in the URL path (:id) — but the target row deleted is selected solely by membershipId, which is never checked to belong to that path scope. The enrichment query in the GET members route (profiles.findMany by user_id) is also org-free but only returns public profile fields.

## Confidence Rationale

Complete source-to-sink trace with executed local PoC against real repository code with mocked Prisma; no live multi-tenant deployment exists to run the HTTP request end-to-end (local-only scope).

## What Would Change This Severity

A live two-tenant deployment test would confirm end-to-end; if membership IDs proved unguessable in practice, attack_complexity would rise and severity could drop.

## Technical Analysis

routes/scopeMemberships.routes.ts PATCH /:id/members/:membershipId (line ~115) and DELETE /:id/members/:membershipId (line ~138) call scopeAccessService.updateMemberRole / removeMember with request.params.membershipId only. scopeAccess.service.ts lines 122-128 pass it straight through, and scopeMembership.repository.ts updateRole (line 86-91) and delete (line 96-98) run prisma.scope_memberships.update/delete with where: { id } — no organization_id, and no check that the membership belongs to the scope in the URL path. requireScopeAccess gates on the caller's access to the path scope, not on the target membership's scope or org.

## Proof of Concept

1. Authenticate as a user with admin access to a scope in Org A. 2. PATCH /api/business-scopes/:myScopeId/members/:membershipId with role 'admin', where membershipId belongs to Org B — scopeMembershipRepository.updateRole updates by bare id. 3. DELETE variant removes a foreign membership by bare id. Local unit PoC (vitest, mocked Prisma) confirms the where clause contains only { id } with no organization_id.

```scilab
// /tmp/poc/idor-sweep.test.ts — executed, passed against real repository code with mocked Prisma
await scopeMembershipRepository.updateRole('membership-OTHERORG', 'admin');
// prisma.scope_memberships.update where = { id: 'membership-OTHERORG' }, data = { role: 'admin' }

await scopeMembershipRepository.delete('membership-OTHERORG');
// prisma.scope_memberships.delete where = { id: 'membership-OTHERORG' }
```

## Remediation

In scopeMembership.repository.ts (updateRole line 86, delete line 96) add organization_id scoping — either filter by the caller's org (passing it from the route handler through scopeAccessService) or first verify the membership's business_scope_id resolves to the caller's organization and to the scope named in the URL path, rejecting mismatches.

## Assumptions

Authenticated user with viewer access to at least one scope in their own org (to satisfy requireScopeAccess('viewer'/'admin')); membership IDs are returned in scope member listings.
