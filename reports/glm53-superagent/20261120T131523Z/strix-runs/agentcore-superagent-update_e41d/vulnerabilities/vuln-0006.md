# Members can read other members' chat sessions and history (org-scoped but not user-scoped)

**ID:** vuln-0006
**Severity:** MEDIUM
**Found:** 2026-11-20 13:18:20 UTC
**Target:** super-agent backend (/workspace/agentcore-superagent-update)
**CWE:** CWE-639
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Low

## Description

Chat session endpoints authorize only at organization level, so any member of an organization can read the contents and metadata of any other member's chat session by ID.

## Evidence

Local vitest passes: ChatSessionRepository.findById issues a query with organization_id=orgA and no user_id, returning a session owned by other-user. List endpoint code at chat.routes.ts:291-311 contrasts: members are filtered by request.user!.id in listing but not in by-id reads.

## Impact

Disclosure of other users' chat history within the same organization — conversation content, context payloads and business-scope context — to any member (including viewer-role users).

## Counterevidence

The org filter prevents cross-organization access, and admins legitimately see all sessions — the list endpoint at chat.routes.ts:291-311 explicitly separates admin (all sessions) from member (own sessions), showing the intended model is per-user. No route-level user check exists on the by-id read paths.

## Confidence Rationale

Validated locally: vitest exercises the real ChatSessionRepository.findById and passes where.organization_id=orgA with where.user_id undefined, returning another user's session. The remaining question is only whether product intent treats all org sessions as shared.

## What Would Change This Severity

Product confirmation that org members are intended to share all chat sessions would downgrade this to informational; conversely evidence that session contents include secrets (e.g. agent tool outputs) would raise the confidentiality impact.

## Technical Analysis

`GET /api/chat/sessions/:id` (src/routes/chat.routes.ts:322-373) and `GET /api/chat/history/:sessionId` (src/routes/chat.routes.ts:714-719) call `chatService.getSessionById(id, request.user!.orgId)` / `getChatHistory(orgId, ...)`; both resolve through `chatSessionRepository.findById(sessionId, organizationId)` (src/services/chat.service.ts:126-130, 198-208), whose base-repository query filters only on id + organization_id with no user_id condition. By contrast the sessions-list endpoint explicitly filters members to their own sessions, confirming per-user ownership is the intended model.

## Proof of Concept

As a regular member of org A, GET /api/chat/sessions/<sessionId> and GET /api/chat/history/<sessionId> using a session ID belonging to a colleague. Both call chatService.getSessionById / getChatHistory, which resolve via chatSessionRepository.findById(sessionId, orgId) — org-scoped only.

```http
GET /api/chat/sessions/33333333-3333-3333-3333-333333333333 HTTP/1.1
Authorization: Bearer <member-token-of-orgA>
```

## Remediation

In getSessionById, getChatHistory and the corresponding route handlers, require the session's user_id to equal the caller's id unless the caller is owner/admin (mirror the check used by the sessions list endpoint).

## Assumptions

Authenticated member sharing an organization with the victim; attacker knows a session UUID (exposed via admin lists, logs, or notifications).
