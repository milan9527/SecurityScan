# Session JWT accepted and propagated via ?token= query parameter

**ID:** vuln-0005
**Severity:** LOW
**Found:** 2026-11-20 13:18:12 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent/backend
**CWE:** CWE-598
**CVSS:** 3.4
**Confidence:** High
**Fix Effort:** Medium

## Description

The authentication middleware accepts a full session JWT via the `?token=` query parameter on every authenticated route, and the frontend actively embeds it in URLs for iframes, file previews and downloads. Query strings are routinely captured in browser history, server/proxy access logs, and Referer headers, exposing a 24-hour-lived session token.

## Evidence

Confirmed in a vitest PoC (part of `tests/unit/auth-forgery.poc.test.ts`, passing): a request with empty headers and `query = { token }` returned 200 with `req.user` set. Frontend usage confirmed at `frontend/src/pages/Chat.tsx:528-533,617`, `WorkspaceActions.tsx:178`, `AppRunner.tsx:140`, `ProjectBoard.tsx:194`; server-side support at `src/middleware/auth.ts:143`.

## Impact

Session token disclosure through URL artifacts (history, logs, Referer) allows an observer with access to those artifacts to reuse the token for up to 24 hours and impersonate the user.

## Counterevidence

No logging of query strings was confirmed in the audited code paths (Fastify default request logs do not include URLs with query strings in the inspected handlers); frontend usage is limited to embedded contexts. This is a design weakness rather than a demonstrated credential theft.

## What Would Change This Severity

Evidence of proxy/access logging or Referer leakage of these URLs in a deployment would raise this to medium; a dedicated short-lived token scheme would close it.

## Technical Analysis

`src/middleware/auth.ts:143` reads `const queryToken = (request.query as Record<string, string>)?.token;` and `auth.ts:155-170` uses it as the token whenever the Authorization header is absent — this applies to every route using `authenticate`, not a dedicated file route. The frontend builds URLs containing the raw session token: `frontend/src/pages/Chat.tsx:528-529` (`preview/?token=...`, `file/raw?...&token=...`), `Chat.tsx:617`, `WorkspaceActions.tsx:178`, `AppRunner.tsx:140`, `ProjectBoard.tsx:194`. These URLs land in browser history, server access logs, and can leak via the Referer header to any subresource loaded by the embedded content. The local JWT is valid for 24h (`auth.ts:55`), so a leaked query token is a long-lived credential. `src/routes/apps.routes.ts:839-869` documents the intended iframe use case.

## Proof of Concept

1. Send any authenticated route request with only a query parameter `?token=<JWT>` and no Authorization header.
2. Observe a 200 response with `request.user` populated — confirmed in vitest PoC against the real `authenticate` hook.

```javascript
// Passing vitest case from tests/unit/auth-forgery.poc.test.ts
const req = fakeReq({}, { token }); // no Authorization header
await authenticate(req, reply);
expect(reply.statusCode).toBe(200); // PASSED
expect(req.user).toBeDefined();    // PASSED
```

## Remediation

Restrict query-param authentication to the specific embedded-file routes that require it (e.g. via a dedicated middleware on those routes only), issue short-lived, single-purpose tokens for those cases, and stop embedding session JWTs in URLs in the frontend.

## Assumptions

Assumes a user authenticates and the platform issues a JWT (any auth mode).
