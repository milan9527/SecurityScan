# Agent access control trusts org-unbound agent_permissions records (cross-org agent admin)

**ID:** vuln-0004
**Severity:** HIGH
**Found:** 2026-11-20 13:18:11 UTC
**Target:** super-agent backend (/workspace/agentcore-superagent-update)
**CWE:** CWE-639
**CVSS:** 7.1
**Confidence:** Medium
**Fix Effort:** Low

## Description

Agent-level access control resolves permissions by (agent_id, user_id) only, without any organization binding, so an explicit permission row grants cross-organization access to an agent, including admin-level control of agent configuration and its permissions.

## Evidence

Local vitest passes: `agentAccessService.checkAccess('user-orgA','orgA','agentX','admin')` returns true when the mocked agent_permissions row exists with permission 'admin', before any org check. Trace: routes/agentPermissions.routes.ts PATCH/DELETE :permId handlers fetch by id only.

## Impact

A user with a permission record on an agent belonging to another organization obtains the granted level (up to admin), enabling agent reconfiguration, permission management and access to the agent's chat/data across the tenant boundary.

## Counterevidence

The agent lookup at step 2 filters by organization_id, so a foreign-org attacker who lacks an explicit agent_permissions row is rejected. The exposure requires the attacker's user_id to appear in agent_permissions for the target agent, which in normal single-org operation may not occur — but no schema constraint or code check enforces it.

## Confidence Rationale

Source-to-sink trace is complete and the cross-org grant was demonstrated with a passing mocked-prisma vitest; the unverified part is whether permission rows ever legitimately exist pointing across organizations in real deployments.

## What Would Change This Severity

Demonstrating that agent_permissions rows can be created for cross-org users through a reachable endpoint would raise attack complexity to L and severity to high.

## Technical Analysis

`agentAccessService.checkAccess` (src/services/agentAccess.service.ts:55-62) first consults `(prisma as any).agent_permissions.findUnique({ where: { unique_agent_user_permission: { agent_id, user_id } } })` with no organization_id predicate, and the returned permission level is trusted. The agentPermissions routes `PATCH /:id/permissions/:permId` and `DELETE /:id/permissions/:permId` (src/routes/agentPermissions.routes.ts:158, 188) then fetch the permission record by id alone and update/delete it.

## Proof of Concept

1. Obtain a permission row referencing the attacker's user_id on a foreign-org agent (e.g. via a shared/staging database or any flow writing agent_permissions without org validation). 2. As that user, call PATCH /api/agents/:id/permissions/:permId — requireAgentAccess('admin') resolves via the cross-org agent_permissions row and allows the call; the handler then updates the permission by id with no org filter.

```http
PATCH /api/agents/<foreign-agent-id>/permissions/<permId> HTTP/1.1
Authorization: Bearer <attacker-token>
Content-Type: application/json

{"permission":"admin"}
```

## Remediation

Add organization_id to the agent_permissions lookup keys (filter by the caller's orgId in checkAccess/getEffectiveLevel), and in the :permId handlers verify the fetched permission row's organization_id and agent_id match the authorized agent and the caller's org before updating or deleting.

## Assumptions

Authenticated user; a shared or leaked agent_permissions row pointing at the attacker's user_id. agent_id values are exposed in agent listings.
