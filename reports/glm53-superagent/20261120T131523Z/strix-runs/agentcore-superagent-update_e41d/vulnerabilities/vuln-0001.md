# Hardcoded default JWT secret enables authentication bypass and role forgery in local auth mode

**ID:** vuln-0001
**Severity:** HIGH
**Found:** 2026-11-20 13:17:49 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent/backend
**CWE:** CWE-798
**CVSS:** 8.1
**Confidence:** High
**Fix Effort:** Low

## Description

When `JWT_SECRET` is not set in the environment, the backend falls back to a hardcoded, publicly-known default secret (`super-agent-local-dev-secret-change-in-production`) with no startup guard. In local auth mode, any attacker who can reach the API can forge a valid JWT authenticating as any user with any role (including `owner`) and any organization ID.

## Evidence

Executed vitest PoC (4/4 passing) against the real `src/middleware/auth.ts` with mocked Prisma:

```text
✓ tests/unit/auth-forgery.poc.test.ts (4 tests) 25ms
  - config falls back to the hardcoded default when JWT_SECRET is unset
  - a JWT forged with the public default secret authenticates as an arbitrary user/role
  - accepts ?token= query param as auth (leakage vector)
  - internal token forged with userPoolId accepted as any user/role
```

The forged-token assertion verified `reply.statusCode === 200`, `req.user.role === 'owner'`, `req.user.orgId === 'attacker-org'` (attacker-chosen), with the membership lookup returning null so the token claim is trusted verbatim.

## Impact

Complete authentication bypass on any deployment that does not set `JWT_SECRET`: the attacker authenticates as an arbitrary existing user (profile lookup by `sub`) with full `owner` role and an attacker-chosen `orgId`, granting read/write access to all organizations' data, agents, workflows, API keys, and admin functions.

## Counterevidence

Checked for a startup guard rejecting or warning on the default secret: none exists in `src/config/index.ts`, `src/app.ts`, or `src/index.ts` (only a CORS comment in app.ts:78). Deployment scripts `infra/scripts/deploy.sh:239` and `user-data.sh:241` do set a generated/placeholder JWT_SECRET, which limits exposure to deployments that omit it. Test setup (`tests/setup.ts`) sets its own secret. No other validation of `config.jwtSecret` exists anywhere (rg over src shows only the two use sites).

## What Would Change This Severity

Confirmation that a production deployment runs with the default secret would raise this to critical; a startup guard that refuses the default would effectively close it.

## Technical Analysis

`src/config/index.ts:30` defines `JWT_SECRET: z.string().optional().default('super-agent-local-dev-secret-change-in-production')` — the default applies silently whenever the env var is unset, and no code path in `src/config/index.ts`, `src/app.ts`, or `src/index.ts` rejects or even warns about the default value.

`src/middleware/auth.ts:62` (`verifyLocalToken`) verifies tokens with `config.jwtSecret`, and the `authenticate` hook (`src/middleware/auth.ts:157` onwards) then looks up a profile by `claims.sub` and, when no membership row exists for that `sub` (`auth.ts:230-236`), trusts the token's `role` and `orgId` claims verbatim: `role: (membership?.role as UserRole) ?? claims.role ?? 'owner'`. So a token signed with the well-known default yields a fully-authenticated `owner` user in an attacker-chosen org, for any `sub` that matches an existing profile. In local mode the only other check is profile existence.

`src/routes/auth.routes.ts:47` (`POST /api/auth/login`) issues tokens signed with the same secret, confirming the value is the sole trust anchor in local mode.

## Proof of Concept

1. Ensure `JWT_SECRET` is unset in the backend environment (config default applies).
2. Forge a JWT signed with the literal string `super-agent-local-dev-secret-change-in-production` containing `sub` of any existing profile, `role: owner`, and an arbitrary `orgId`.
3. Call any authenticated API route with `Authorization: Bearer <forged>` — `authenticate` verifies it with the default secret and installs the claims as `request.user`.
4. Executed as a vitest test importing the real `src/middleware/auth.ts` with a mocked Prisma client; all assertions passed.

```javascript
// tests/unit/auth-forgery.poc.test.ts (excerpt — executed, passing)
delete process.env.JWT_SECRET; // config default applies
const { authenticate } = await import('../../src/middleware/auth.ts');
const jwt = require('jsonwebtoken');
const token = jwt.sign(
  { sub: '00000000-0000-0000-0000-000000000001', email: 'attacker@evil.example',
    orgId: 'attacker-org', role: 'owner' },
  'super-agent-local-dev-secret-change-in-production',
  { expiresIn: '24h' });
const req = { headers: { authorization: `Bearer ${token}` }, query: {},
  id: 'req-1', log: { info(){}, error(){} } };
const reply = { status(c){ this.statusCode = c; return this; }, send(b){ this.body = b; return this; } };
await authenticate(req, reply);
// PASSED: reply.statusCode === 200, req.user.role === 'owner',
//         req.user.orgId === 'attacker-org' (attacker-chosen)
```

## Remediation

Remove the default value for `JWT_SECRET` in the zod schema and fail startup when it is unset (or when it equals the known default) in production; require an operator-provided secret of sufficient entropy.

## Assumptions

Requires a deployment running local auth mode with JWT_SECRET unset (e.g. defaulting .env.example usage or manual deploys); the bundled EC2 deploy scripts do generate a random secret, so exposure depends on operator configuration.
