# Unauthenticated WebSocket execution gateway: any client can subscribe to any org's workflow execution events (/ws/executions)

**ID:** vuln-0010
**Severity:** MEDIUM
**Found:** 2026-11-20 13:20:23 UTC
**Target:** super-agent backend (/workspace/agentcore-superagent-update/super-agent/backend)
**CVSS:** 5.3
**Confidence:** Medium
**Fix Effort:** Medium

## Description

The workflow-execution WebSocket endpoint `GET /ws/executions` accepts connections and subscriptions with no authentication and no organization check: any unauthenticated client can subscribe to any execution ID and receive all of that execution's workflow events — including node status, logs, and output data belonging to other users and organizations.

## Evidence

Static trace (no branches skipped): `execution.gateway.ts:133-139` — `fastify.get('/ws/executions', { websocket: true }, (socket, _request) => { this.handleConnection(socket); })` — the request (headers/cookies/query) is never inspected; `handleConnection` (line 145) and `handleSubscribe` (~line 232) contain no identity checks, only `executionId` type validation; `broadcastEvent` (lines 352-371) sends the full `WorkflowEvent` JSON to every subscriber socket of that executionId. `src/setup/event-websocket-bridge.ts:48` forwards every `workflow:event` (node:started/completed/failed etc.) from `workflowExecutionService` to this gateway.

## Impact

An unauthenticated attacker who learns or guesses an execution ID can passively observe another organization's workflow execution in real time: node status, execution logs, and event payloads that may contain node output data, intermediate results, or prompt/response content. This is a cross-tenant information disclosure requiring zero credentials.

## Counterevidence

Checked for any global authentication hook (app.ts adds only an onResponse audit hook; routes/index.ts applies authenticate per-route, and this route is registered outside route registration, bypassing it). The subscribe handler contains no org/user/ownership validation — the only validation is that executionId is a non-empty string. Possible mitigations outside this repo (an authenticating gateway/proxy in front of /ws) could not be verified.

## Confidence Rationale

Complete static trace from connection to sink: route registered with no auth handler, request object discarded, subscribe accepts any executionId, and broadcastEvent delivers full workflow events to all subscribers. Not executed end-to-end as a live WebSocket PoC; the code path contains no branch where credentials are checked, but a live cross-org replay was not demonstrated.

## What Would Change This Severity

Executing the PoC against a live instance with a real execution and observing cross-org event data (especially node outputs/logs containing sensitive content) would confirm C:L and could raise severity; if execution events are confirmed to carry no data beyond opaque status codes, severity drops to low.

## Technical Analysis

`src/app.ts:208` registers `executionWebSocketGateway.register(app)` outside of `registerRoutes`, where every other route applies `authenticate` per-route. `ExecutionWebSocketGateway.register` (`src/websocket/execution.gateway.ts:125-142`) registers `fastify.get('/ws/executions', { websocket: true }, (socket, _request) => this.handleConnection(socket))` — the FastifyRequest is explicitly discarded, so headers/cookies/query tokens are never read. `handleConnection` (line 145) admits any socket into `this.clients` unconditionally. `handleMessage` dispatches on JSON type; `handleSubscribe` validates only that `executionId` is a non-empty string, then adds the socket to `this.subscriptions.get(executionId)`. `broadcastEvent` (line 352) sends the full `WorkflowEvent` payload to every subscriber of that executionId, and `initializeEventWebSocketBridge` (`src/setup/event-websocket-bridge.ts:48`) forwards all `workflow:event` emissions from the execution service — node status changes, logs, and node output — into this broadcast. There is no org, user, or ownership check anywhere on the path.

## Proof of Concept

1. Connect to `ws://<host>/ws/executions` with no authentication headers.
2. Send `{"type":"subscribe","executionId":"<any execution id>"}`.
3. Receive `{"type":"subscribed"}` confirmation.
4. While that workflow runs, receive every `workflow_event` message for it, regardless of which org/user owns the execution.

```js
// node script (ws package)
const WebSocket = require('ws');
const ws = new WebSocket('ws://localhost:3000/ws/executions'); // no auth
ws.on('open', () => ws.send(JSON.stringify({ type: 'subscribe', executionId: process.argv[2] })));
ws.on('message', (d) => console.log(d.toString())); // streams another org's execution events
```

## Remediation

Apply the existing `authenticate` middleware as a `preValidation` hook on the WebSocket route (Fastify preHandler hooks run on WebSocket GET upgrades), and inside `handleSubscribe` verify that the authenticated user's organization matches the organization that owns the execution record (look up the execution by ID and compare org ownership) before adding the subscription. Reject unknown execution IDs with an error indistinguishable from the not-authorized case to avoid an enumeration oracle.

## Assumptions

Assumes the backend is network-reachable and executions occur (workflow executions emit events). Attacker needs a valid execution ID, which may be observed/brute-forced or leaked; no account is required.
