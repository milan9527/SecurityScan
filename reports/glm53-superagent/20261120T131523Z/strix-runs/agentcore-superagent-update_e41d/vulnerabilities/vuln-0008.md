# Hardcoded default INSFORGE_JWT_SECRET allows forging InsForge access tokens

**ID:** vuln-0008
**Severity:** HIGH
**Found:** 2026-11-20 13:20:04 UTC
**Target:** super-agent backend (local_code: /workspace/agentcore-superagent-update)
**CWE:** CWE-798
**CVSS:** 8.7
**Confidence:** High
**Fix Effort:** Low

## Description

The InsForge integration's JWT signing secret defaults to the hardcoded value `spike-test-secret-key-must-be-32-chars-long` when `INSFORGE_JWT_SECRET` is unset. Anyone with source access can mint valid InsForge access tokens (role `authenticated`, issuer `super-agent`) for any deployment that runs with the default.

## Evidence

`src/config/index.ts:145` sets the default `spike-test-secret-key-must-be-32-chars-long`; `src/routes/apps.routes.ts:453` reads `process.env.INSFORGE_JWT_SECRET || config.insforge.jwtSecret` and uses it in `createHmac('sha256', jwtSecret)` to build the injected token.

## Impact

When InsForge is enabled, an attacker who knows the committed secret can independently forge InsForge PostgREST access tokens (role `authenticated`) and query/mutate the tenant data exposed through InsForge, bypassing the app-controlled token issuance entirely — a cross-component auth bypass (scope change: backend → InsForge service).

## Counterevidence

INSFORGE_ENABLED defaults to 'false', so the vulnerable path is dormant unless an operator enables InsForge integration; the secret is also only used for the InsForge JWT (not the main platform auth), limiting blast radius to InsForge-backed data. No strength check or random generation exists, so nothing else neutralizes the default when the feature is on.

## What Would Change This Severity

Confirmation that InsForge is enabled in a real deployment with the default secret would raise exploitability from conditional to confirmed; the feature remaining disabled everywhere would reduce it to a latent config hygiene issue.

## Technical Analysis

`src/config/index.ts:145` declares `INSFORGE_JWT_SECRET: z.string().optional().default('spike-test-secret-key-must-be-32-chars-long')`. In `src/routes/apps.routes.ts:452-457`, the app-build route reads `process.env.INSFORGE_JWT_SECRET || config.insforge.jwtSecret` and manually constructs an HS256 JWT with claims `{role:'authenticated', iss:'super-agent', exp:4102444800}` (year 2100), injecting it into the app's `.env` so Vite inlines it into the built frontend. The same secret is what the InsForge PostgREST layer uses to verify request tokens, so knowing the committed default allows minting equivalent tokens directly without going through the backend. The long expiry (fixed 2100 timestamp) amplifies exposure of any leaked token.

## Proof of Concept

1. Compute `header.payload.signature` where header is `{"alg":"HS256","typ":"JWT"}` base64url, payload is `{"role":"authenticated","iss":"super-agent","exp":4102444800}` base64url, and signature is HMAC-SHA256 over `header.payload` with key `spike-test-secret-key-must-be-32-chars-long`.
2. Use the resulting token against the InsForge PostgREST endpoint (`http://<insforge-host>:15430`) as a valid authenticated-role token, reproducing exactly what `src/routes/apps.routes.ts:452-457` generates.

```python
import { createHmac } from 'crypto';
const jwtSecret = 'spike-test-secret-key-must-be-32-chars-long';
const header = Buffer.from('{"alg":"HS256","typ":"JWT"}').toString('base64url');
const payload = Buffer.from(JSON.stringify({ role: 'authenticated', iss: 'super-agent', exp: 4102444800 })).toString('base64url');
const signature = createHmac('sha256', jwtSecret).update(`${header}.${payload}`).digest('base64url');
const token = `${header}.${payload}.${signature}`; // accepted by InsForge PostgREST when default secret is in use
```

## Remediation

Remove the hardcoded default for INSFORGE_JWT_SECRET and require an explicit, randomly generated value whenever the InsForge integration is enabled; fail startup if it is enabled without a secret. Rotate the secret on any environment that may have used the default.

## Assumptions

Requires INSFORGE_ENABLED=true (default is false) and InsForge auth mode; impact is confined to that subsystem's tenant data.
