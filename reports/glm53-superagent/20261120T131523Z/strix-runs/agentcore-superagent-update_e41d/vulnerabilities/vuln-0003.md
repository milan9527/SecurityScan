# Internal service token HMAC uses public Cognito userPoolId as secret, enabling unauthenticated token forgery in cognito mode

**ID:** vuln-0003
**Severity:** CRITICAL
**Found:** 2026-11-20 13:18:02 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent/backend
**CWE:** CWE-346
**CVSS:** 9.8
**Confidence:** High
**Fix Effort:** Low

## Description

When `AUTH_MODE=cognito`, internal service tokens are HMAC-signed with the Cognito `userPoolId` — a public identifier that the backend itself returns on the unauthenticated `GET /api/auth/config` endpoint. Any attacker who can read that endpoint can forge internal tokens authenticating as any user with any role, bypassing profile and membership lookups entirely.

## Evidence

Executed vitest PoC (cognito-mode test in `tests/unit/auth-forgery.poc.test.ts`, passing): forged `internal.<base64url>.<HMAC(userPoolId)>` token accepted, `reply.statusCode === 200`, `req.user = { role: 'owner', orgId: 'any-org', id: 'any-cognito-sub' }` with prisma never consulted. Full derivation also independently verified with a standalone node/crypto script.

## Impact

In cognito mode, full authentication bypass as an arbitrary identity/role/org with no database lookups, on every route protected by `authenticate`. The same primitive is what agent subprocesses legitimately use, so the bypass is indistinguishable from a trusted internal caller.

## Counterevidence

Only reachable in cognito mode (AUTH_MODE=cognito); in local mode the HMAC key is config.jwtSecret which is not disclosed by /auth/config. Default auth mode is 'local', so deployments using the default mode are not exposed to this specific path. Could not test against a live deployed instance (out of scope for this run).

## What Would Change This Severity

Confirmation that a production deployment runs in cognito mode would confirm critical; evidence that no cognito-mode deployment exists would lower practical severity though the code flaw remains.

## Technical Analysis

`src/middleware/auth.ts:79-80` sets the internal token HMAC key: `const INTERNAL_TOKEN_SECRET = config.authMode === 'cognito' ? config.cognito.userPoolId : config.jwtSecret;`. The `userPoolId` is not a secret — `src/routes/auth.routes.ts:29-40` (`GET /api/auth/config`, registered unauthenticated in `src/routes/index.ts`) returns `userPoolId` (and clientId, region, domain) to any caller in cognito mode, since the frontend needs it.

`verifyInternalToken` (`auth.ts:94-108`) only recomputes `HMAC-SHA256(userPoolId, data)` and compares, then `authenticate` (`auth.ts:160-171`) installs the payload's `sub/email/orgId/role` directly as `request.user` **before any Cognito verification or profile/membership lookup** — the internal-token branch returns early. So in cognito mode the entire authorization decision can rest on a value the server publishes to anonymous users.

## Proof of Concept

1. Fetch `GET /api/auth/config` (unauthenticated) and read `userPoolId`.
2. Build payload `{sub, email, orgId, role: 'owner', exp: now+3600}`, base64url-encode it, HMAC-SHA256 it with the `userPoolId`, and assemble `internal.<data>.<sig>`.
3. Send it as a Bearer token to any authenticated route — `authenticate` accepts it before any Cognito or profile verification.
4. Executed as a vitest test against the real `src/middleware/auth.ts` in cognito mode with mocked Prisma; token accepted, `req.user` set to the forged claims, `role: owner`.

```javascript
const crypto = require('crypto');
// userPoolId is public: GET /api/auth/config -> { userPoolId: 'ap-northeast-1_ABCDEF123', ... }
const userPoolId = 'ap-northeast-1_ABCDEF123';
const payload = { sub: 'any-cognito-sub', email: 'attacker@evil.example',
  orgId: 'any-org', role: 'owner', exp: Math.floor(Date.now()/1000) + 3600 };
const data = Buffer.from(JSON.stringify(payload)).toString('base64url');
const sig = crypto.createHmac('sha256', userPoolId).update(data).digest('base64url');
const token = `internal.${data}.${sig}`;
// GET /api/agents, Authorization: Bearer <token>  ->  200 as owner
```

## Remediation

Use a dedicated, operator-provided high-entropy secret (independent of JWT_SECRET and of any Cognito identifier) as the internal token HMAC key, loaded from the environment with no default. Long term, prefer an asymmetric scheme so the API only holds a public key.

## Assumptions

Deployment runs AUTH_MODE=cognito (non-default). Requires knowing the userPoolId, which the application itself publishes via the unauthenticated /api/auth/config endpoint.
