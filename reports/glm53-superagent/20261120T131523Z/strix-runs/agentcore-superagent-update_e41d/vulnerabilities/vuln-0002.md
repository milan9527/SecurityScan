# Cross-scope membership manipulation via unvalidated membershipId in scope-membership routes

**ID:** vuln-0002
**Severity:** MEDIUM
**Found:** 2026-11-20 13:18:00 UTC
**Target:** super-agent backend (/workspace/agentcore-superagent-update)
**CWE:** CWE-639
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Low

## Description

The scope-membership management routes authorize on the scope in the URL path but mutate a membership record chosen by an unvalidated :membershipId parameter, allowing an authenticated user who is an admin of any one scope to change or remove members of any other business scope (including cross-organization scopes).

## Evidence

Local vitest (`tests/unit/tenant-isolation.audit.test.ts`) passes: `requireScopeAccess('admin')` proceeds without any 403 when params/body/query contain no scopeId. Repository audit shows `updateRole`/`delete` operate on membershipId with no scope/org binding.

## Impact

Unauthorized cross-scope membership manipulation: an attacker can escalate or remove another user's role in a restricted business scope they do not administer, altering who can access that scope's agents, documents and data.

## Counterevidence

The middleware does correctly enforce access when a scopeId is present, and the scope-membership add-member endpoint verifies same-org membership; the bypass relies on the guard checking a different object (path :id) than the one mutated (:membershipId). No scope-membership-route-specific control was found covering the membershipId path.

## Confidence Rationale

Validated by a passing local vitest exercising the real middleware logic with mocked prisma: no rejection emitted when scopeId absent, confirming fail-open.

## What Would Change This Severity

Evidence that membership IDs are enumerable (e.g. sequential rather than UUID) would raise exploitability; confirmation that all deployments use non-UUID membership IDs unchanged.

## Technical Analysis

`requireScopeAccess` (src/middleware/scopeAccess.ts:36-41) fails open when no scopeId is extractable, and even when present it only validates the path `:id`. The handlers `PATCH /:id/members/:membershipId` and `DELETE /:id/members/:membershipId` (src/routes/scopeMemberships.routes.ts:113-142) call `scopeAccessService.updateMemberRole(request.params.membershipId, role)` and `removeMember(membershipId)`, which delegate to `scopeMembershipRepository.updateRole`/`delete` — queries on the membership row alone, with no check that the membership belongs to the authorized scope or to the caller's organization. The guard authorizes scope A while the mutation targets scope B's membership (broken object-level authorization / validated-vs-consumed mismatch).

## Proof of Concept

As an authenticated user who is scope admin of scope A, send PATCH /api/business-scopes/<scopeA>/members/<membershipId-of-scope-B> with body {"role":"admin"} (or DELETE the same path). The requireScopeAccess('admin') guard authorizes on scopeA (path :id) and passes; updateMemberRole then updates the scope-B membership row directly. The same works for removal via DELETE.

```http
PATCH /api/business-scopes/11111111-1111-1111-1111-111111111111/members/22222222-2222-2222-2222-222222222222 HTTP/1.1
Authorization: Bearer <attacker-token-admin-of-scope-1111>
Content-Type: application/json

{"role":"admin"}
```

## Remediation

In the membership update/remove handlers, resolve the membership record first and verify its business_scope_id equals the authorized path :id (and its organization_id equals the caller's org) before updating or deleting; alternatively pass scopeId into scopeAccessService.updateMemberRole/removeMember and enforce it there.

## Assumptions

Authenticated user with a member role; attacker must know or enumerate a membership ID (UUID) of the target scope.
