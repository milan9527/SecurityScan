# Workflow webhook trigger ignores generated secret — unauthenticated workflow execution

**ID:** vuln-0003
**Severity:** HIGH
**Found:** 2026-11-20 13:38:28 UTC
**Target:** /workspace/agentcore-superagent-update (super-agent/backend)
**CWE:** CWE-306
**CVSS:** 7.0
**Confidence:** High
**Fix Effort:** Low

## Description

The public webhook trigger endpoint `POST /v1/webhook/:webhookId/trigger` never verifies the per-webhook secret. A secret is generated and its hash stored on creation, but the trigger path ignores it entirely, so any caller who knows a webhook ID can execute the workflow with attacker-chosen variables, without any signature or shared secret.

## Evidence

Code trace: webhooks.routes.ts:315 (public trigger route, no preHandler authenticate; registered under /api at routes/index.ts:209); webhook.service.ts:137-186 triggerWebhook checks only existence, isEnabled, optional IP allowlist; secretHash generated at :50-53, stored at :93, mapped at :524 — repo-wide search shows no comparison site; no timestamp/nonce replay protection.

Executable PoC (vitest, real route + service, mocked prisma/redis/executor) at tests/unit/webhook-trigger-authz.poc.test.ts — `npx vitest run` passes 3/3:
- POST /api/v1/webhook/<id>/trigger with NO secret header -> 200 {received:true, callRecordId}
- Request with `x-webhook-secret: totally-wrong-value` -> also accepted
- Identical request replayed 3x -> 200 each time, 3 call records + 3 executions created (no replay protection)

## Impact

Unauthenticated triggering of tenant workflows with attacker-controlled variables (which become workflow variable values in the V2 plan), including agent and action node execution. Also public status endpoint /v1/webhook/status/:callRecordId leaks execution status and logs without auth.

## Counterevidence

Webhook ID is 24 random hex chars (96 bits) — unguessable without leak. IP allowlist applies when configured. Secret verification may be a deliberately deferred feature (secretHash only stored, never read).

## Confidence Rationale

Executable local PoC: vitest suite registering the real webhooks.routes.ts under the production /api prefix (mocked prisma/redis/executor) shows POST with no secret header returns 200 received:true, wrong secret header is ignored, and identical replays succeed without limit. Only deployment exposure of the URL is inferred.

## What Would Change This Severity

WebhookId leakage (e.g. via history responses or URLs) would lower complexity and raise severity.

## Technical Analysis

src/routes/webhooks.routes.ts:278-320 registers the trigger route with no authenticate preHandler; src/services/webhook.service.ts triggerWebhook (lines ~140-192) validates only existence, isEnabled, and optional IP allowlist. The secretHash generated in createWebhook (webhook.service.ts:75-84) is never read or compared anywhere in the trigger path — grep shows secretHash only set and mapped. No signature, timestamp, or nonce checks exist, so replay is also unrestricted.

## Proof of Concept

1. Run `npx vitest run tests/unit/webhook-trigger-authz.poc.test.ts` in super-agent/backend — it registers the real route plugin under the production /api prefix with mocked prisma/redis/executor and a webhook record carrying a non-null secret_hash. 2. The suite proves: a POST with no secret header returns 200 received:true; a wrong x-webhook-secret header is ignored; identical replays succeed without limit (3 replays = 3 call records created). Equivalently on a live deployment: POST /api/v1/webhook/<id>/trigger with arbitrary variables and no signature headers executes the workflow.

```bash
cd super-agent/backend
npx vitest run tests/unit/webhook-trigger-authz.poc.test.ts
# ✓ service layer: triggerWebhook accepts a wrong secret header without complaint
# ✓ route layer: POST with NO secret header returns 200 received:true
# ✓ route layer: identical replay also returns 200 received:true (no replay protection)
#   3 triggers => 3 call records created, 3 executions attempted
```

## Remediation

When a webhook has a secret_hash, require a signature (e.g. HMAC-SHA256 of the raw body with the secret, compared timing-safely) or a shared-secret header before creating the call record; add timestamp freshness checking.

## Assumptions

A webhook was created with generateSecret=true; attacker knows the webhookId.
