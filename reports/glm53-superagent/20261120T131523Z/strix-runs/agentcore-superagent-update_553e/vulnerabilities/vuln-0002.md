# Unauthenticated generic IM webhook allows arbitrary agent message injection and workflow triggering

**ID:** vuln-0002
**Severity:** HIGH
**Found:** 2026-11-20 13:38:19 UTC
**Target:** /workspace/agentcore-superagent-update (super-agent/backend)
**CWE:** CWE-306
**CVSS:** 7.0
**Confidence:** High
**Fix Effort:** Medium

## Description

The generic IM webhook endpoint `POST /api/im/webhook/:bindingId` performs no authentication, signature verification, or replay protection. Any network caller who knows a binding UUID can inject arbitrary text into the agent chat pipeline, trigger agent execution, and create chat sessions.

## Evidence

Local PoC against backend on 127.0.0.1:3001 with seeded Slack binding (signing secret in config): `curl -X POST http://127.0.0.1:3001/api/im/webhook/33333333-3333-3333-3333-333333333333 -H 'Content-Type: application/json' -d '{"text":"hello from attacker","user_id":"attacker-1"}'` → request routed to chatService.processMessage; DB shows new chat_sessions row with source='im' created by the unauthenticated request. The signed Slack endpoint rejects signature-less requests, proving the dedicated endpoints enforce verification while the generic one has none.

## Impact

Unauthenticated remote attacker can drive the platform's AI agents with arbitrary prompts under a tenant's identity: create chat sessions (confirmed), inject persistent user messages, trigger agent/LLM execution and downstream agent actions, and consume tenant quota.

## Counterevidence

Requires knowing the bindingId UUID; route checks is_enabled; generic 500 hides detail. No signature header is expected, so no control exists to bypass — verification is simply absent.

## Confidence Rationale

Confirmed dynamically against a local instance of the real backend: unauthenticated request accepted and chat session row created in database.

## What Would Change This Severity

A cheap way to enumerate bindingIds (ID leakage) would lower attack complexity and raise severity to critical.

## Technical Analysis

src/routes/im.routes.ts:733-764 registers POST /webhook/:bindingId with no authenticate preHandler and never calls verifyAndLookupBinding or any adapter verifyRequest. It looks the binding up by ID alone (findBindingById, im.routes.ts:767-771, explicitly "without org context") and builds a NormalizedIMMessage from attacker-supplied text/user_id/thread_id, flowing into imService.handleMessage (im.service.ts:171) → session creation, message persistence, and chatService.processMessage — the same code path as authenticated web chat. Dedicated per-platform endpoints route through verifyAndLookupBinding (im.routes.ts:229); the generic endpoint has no equivalent control.

## Proof of Concept

1. Seed a Slack IM binding with a signing secret. 2. Send an unauthenticated POST to /api/im/webhook/<bindingId> with arbitrary text. 3. Observe the backend accept the request, create a chat session, and route the text into chatService.processMessage.

```bash
curl -s -X POST http://127.0.0.1:3001/api/im/webhook/33333333-3333-3333-3333-333333333333 \
  -H 'Content-Type: application/json' \
  -d '{"text":"hello from attacker","user_id":"attacker-1"}'
```

## Remediation

Require a per-binding authentication secret on the generic webhook endpoint (shared-secret header compared timing-safely, or HMAC over the raw body), validated before imService.handleMessage is invoked. Never allow a binding lookup path that bypasses adapter verifyRequest.

## Assumptions

Attacker knows a valid IM binding UUID; endpoint is network-reachable.
