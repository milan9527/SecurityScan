# Full-response SSRF in workflow api_call action node (no URL validation, redirects followed)

**ID:** vuln-0001
**Severity:** HIGH
**Found:** 2026-11-20 13:36:44 UTC
**Target:** /workspace/agentcore-superagent-update (super-agent/backend)
**CVSS:** 7.7
**Confidence:** High
**Fix Effort:** Medium

## Description

The workflow engine's api_call action node fetches an arbitrary attacker-supplied URL with no scheme, host, or IP validation, and returns the full response body to the caller. The fetch client follows redirects, allowing allowlist-free pivoting to loopback/link-internal targets. A related sink exists in the MCP server "test connection" endpoint, which HEADs an attacker-registered host_address with no validation (blind).

## Evidence

Local PoC (tsx against the real executor, loopback-only): mock internal server on 127.0.0.1:47777 returned `SECRET-INTERNAL-DATA`; a redirector on 127.0.0.1:46666 answered with `302 -> http://127.0.0.1:47777/`. Executing an api_call node with url `http://127.0.0.1:46666/` produced a success result whose output contained `SECRET-INTERNAL-DATA` — i.e. the client followed the redirect to the internal address and returned the body. Direct loopback URL (`http://127.0.0.1:47777/`) likewise returned the body. Source trace: `executeApiCall` calls `fetch(url, ...)` (action-executor.ts:137) with `url` from `apiConfig.url` (line 117), then returns `response: parsedResponse` (line 157). No validation anywhere between route input and sink.

## Impact

An authenticated low-privilege user who can create/edit a workflow (api_call node) makes the backend issue requests to arbitrary internal addresses (loopback, RFC1918, link-local/cloud metadata) and reads the full response body back through workflow execution results/logs — full (non-blind) SSRF. Redirect-following defeats any future allowlist unless re-validated per hop.

## Counterevidence

Checked: no URL validation, allowlist, scheme check, IP/host restriction, or redirect handling exists in either executor path (action-executor.ts executeApiCall, workflow-orchestrator.ts executeActionNode). Node `nodes`/`metadata` accepted without schema validation in workflow create/execute routes. The only nearby control is org-scoped workflow lookup (workflowRepository.findById with organizationId), which gates who may run the workflow but never inspects the URL. Impact limited to internal network read (response is returned to caller); no write primitive demonstrated.

## What Would Change This Severity

Confirmation that the deployed backend can reach cloud metadata or internal admin services from the fetch sink would confirm network-level impact; conversely an egress-blocking network policy at deployment would reduce severity.

## Technical Analysis

Root cause: `ActionNodeExecutor.executeApiCall` (super-agent/backend/src/services/node-executors/action-executor.ts:114-162) takes `apiConfig.url` from the workflow node's `data.metadata` (line 117-118: `metadata?.apiConfig`), substitutes variables, and passes it directly to `fetch()` (line 137) with no URL validation whatsoever. The parsed response body is placed into the success result (`response: parsedResponse`, line 157), which flows into workflow execution records/logs visible to the caller. Node's global `fetch` follows redirects by default, so an attacker-controlled external URL can 302 to `http://169.254.169.254/...` or any internal host. Reachability: workflow nodes (including `metadata` with `apiConfig`) are supplied via `POST /api/workflows` (routes/workflows.routes.ts:275, `authenticate + requireModifyAccess`, `nodes: {type:'array'}` with no per-node schema) and executed via `POST /api/workflows/:id/execute-v2` (line 967, `authenticate`), via the public unauthenticated webhook trigger path (webhook.service.ts executeWebhookAsync builds the same plan and runs workflowExecutorV2), and via workflow-execution.service.ts:1027 (nodeExecutorRegistry.execute). A duplicate sink exists in `WorkflowOrchestrator.executeActionNode` (services/workflow-orchestrator.ts:536-565) with the same unvalidated `fetch(url, ...)` at line 554 and response returned at line 567. Additional sink: `McpServerService.testMcpServerConnection` (services/mcp.service.ts:245-248) fetches `config.url || server.host_address` (user-registered via POST /api/mcp/servers, authenticated) with attacker-controlled headers — blind SSRF (only status/latency/error returned).

## Proof of Concept

1. Start a mock "internal" HTTP server on 127.0.0.1:47777 returning a secret, and a redirector on 127.0.0.1:46666 that 302s to it. 2. Instantiate ActionNodeExecutor and execute a node with data.metadata.actionType='api_call' and apiConfig.url='http://127.0.0.1:46666/'. 3. Observe the node result's output contains the internal server's body, proving redirect-following SSRF with full response disclosure. Repeat with the internal URL directly.

```ts
// Run from super-agent/backend with: npx tsx poc.mts
import http from 'http';
import { ActionNodeExecutor } from './src/services/node-executors/action-executor.js';
const internal = http.createServer((req, res) => res.end('SECRET-INTERNAL-DATA'));
await new Promise<void>(r => internal.listen(47777, '127.0.0.1', r));
const redirector = http.createServer((req, res) => { res.writeHead(302, { Location: 'http://127.0.0.1:47777/' }); res.end(); });
await new Promise<void>(r => redirector.listen(46666, '127.0.0.1', r));
const exec = new ActionNodeExecutor();
const mk = (id: string, url: string) => ({
  node: { id, type: 'action', data: { title: id, metadata: { actionType: 'api_call', apiConfig: { url, method: 'GET' } } } },
  context: { executionId: 'e', organizationId: 'o', nodeOutputs: new Map(), variables: new Map() },
});
const r1 = await exec.execute(mk('n1','http://127.0.0.1:46666/') as any);
const r2 = await exec.execute(mk('n2','http://127.0.0.1:47777/') as any);
console.log('REDIRECT_FOLLOWED=', JSON.stringify(r1).includes('SECRET-INTERNAL-DATA')); // true
console.log('LOOPBACK_BODY_RETURNED=', JSON.stringify(r2).includes('SECRET-INTERNAL-DATA')); // true
internal.close(); redirector.close(); process.exit(0);
```

## Remediation

Introduce a shared SSRF guard for all outbound URL fetches driven by user input: validate scheme (https/http only), resolve DNS and reject loopback, RFC1918, link-local (169.254/16, metadata ranges), and IPv6-mapped variants; use `redirect: 'manual'` and re-validate each hop before following (or disable redirects entirely); cap response size. Apply the guard in the workflow api_call executors, the MCP test-connection path, and any future outbound fetch of user-supplied URLs.

## Assumptions

Assumes an authenticated user who can create or edit workflows (api_call action nodes) or an MCP server — both are standard low-priv tenant capabilities behind `authenticate`.
