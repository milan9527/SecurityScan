# Cross-organization IDOR in knowledge-base routes (read/modify/delete of other orgs' KBs, files, folders)

**ID:** vuln-0002
**Severity:** HIGH
**Found:** 2026-11-20 13:28:11 UTC
**Target:** super-agent/backend (local repository: /workspace/agentcore-superagent-update)
**CWE:** CWE-639
**CVSS:** 8.8
**Confidence:** High
**Fix Effort:** Medium

## Description

Knowledge-base routes accept bare resource UUIDs and pass them to service methods that filter only by primary key, with no organization_id constraint. An authenticated member of any organization can read, rename, move, tag, or soft/hard-delete knowledge bases, folders, and files belonging to other organizations.

## Evidence

PoC run (vitest, 9/9 passed): org A member issues GET /api/knowledge-bases/<KB_B> → 200 with organization_id=ORG_B, name='Org B private KB'; GET /api/knowledge-bases/<KB_B>/files → items containing display_name='SECRET-MARKER'; PUT /:id/files/:fileId with {display_name:'PWNED-BY-ORG-A'} → 200 and store mutated; DELETE /:id/files/:fileId → 204 and org B file removed; PUT /:id → KB renamed; DELETE /:id → KB status='deleted'; briefing PoC under separate report. No 403/404 was returned on any cross-org request; the only status codes were 200/204.

## Impact

Cross-tenant disclosure and destruction of another organization's knowledge-base content: file names, tags, sizes and metadata are returned by listFiles; display names/tags/folder assignments can be rewritten (updateFile, batchMoveFiles, batchAddTags); files can be hard-deleted (deleteFile, batchDeleteFiles); entire knowledge bases can be renamed or soft-deleted (update, delete). PoC: 9/9 assertions green.

## Counterevidence

Checked for guards that could neutralize this: (1) authenticate (src/middleware/auth.ts) only verifies identity — it does not bind the request to any resource; (2) requireModifyAccess is requireRole('owner','admin','member') — a plain member of ANY org passes, so it constrains nothing cross-org; (3) no requireScopeAccess preHandler or app-level hook guards these routes (verified src/app.ts registerRoutes wiring); (4) listByOrganization IS correctly org-scoped, so the listing endpoint does not leak foreign IDs directly — an attacker needs the target UUID from another source, and UUIDv4 enumeration is impractical; (5) kb upload route does check existence but not ownership, so upload to a foreign KB also succeeds if the UUID is known. These constraints reduce the attack's ease but do not restore tenant isolation.

## Confidence Rationale

Executed PoC through the real route handlers and real service functions with a where-clause-faithful in-memory prisma; 9/9 tests green. Only the transport (JWT verification) was stubbed, which is upstream of the broken control.

## What Would Change This Severity

Evidence that any UUIDs are exposed cross-org (e.g. in logs, exports, analytics, or the briefings/bindings endpoints) would confirm mass exploitability; conversely nothing observed lowers it.

## Technical Analysis

Every KnowledgeBaseService method that operates on an existing object filters only by primary key and never by organization_id: `findById` (where: {id}), `update` (where: {id}), `delete` (where: {id}), `listFiles` (where: {knowledge_base_id}), `updateFile`/`deleteFile` (where: {id}), `batchMoveFiles`/`batchDeleteFiles`/`batchAddTags` (where: {id: {in: fileIds}}), `listFolders`, `renameFolder`, `deleteFolder`, `getScopeBindings`, `updateStats`. The routes in knowledge-base.routes.ts pass request.params.id/fileId/folderId/scopeId straight into these methods with no ownership check. The only preHandlers are `authenticate` (identity only) and `requireModifyAccess`, which is `requireRole('owner','admin','member')` — a role check with no org binding, so any org's member qualifies. Only `listByOrganization` scopes by `request.user!.orgId`. Prisma's schema has organization_id on all these tables, so the fix is to include it in every where clause.

## Proof of Concept

Run `npx vitest run tests/unit/kb-idor.poc.test.ts` in super-agent/backend. The test mocks prisma with an in-memory store that filters records strictly by the where clause the production code passes, stubs only token verification to install an org-A member identity, then drives the real route handlers via fastify.inject against an org-B KB/file. All six C1 assertions pass: cross-org read (KB + file listing), update, file metadata rewrite, file deletion, KB rename, and KB soft-delete all succeed for the org-A member.

## Remediation

Add organization_id derived from request.user.orgId to every where clause on these paths: change findById/update/delete to filter by {id, organization_id} (findFirst), filter listFiles by organization_id alongside knowledge_base_id, filter updateFile/deleteFile/batchMoveFiles/batchDeleteFiles/batchAddTags/updateStats, and validate that knowledge_base_id-scoped routes (folders, bindings, tags) first load the KB scoped to the caller's org. The only org-scoped method today is listByOrganization.

## Assumptions

Authenticated user of any role in any organization; knowledge of a target KB/file UUID (obtainable from logs, exports, notifications, or the org-scoped listing of one's own org's IDs after a cross-tenant leak).
