# Path traversal in workspace provisioning via unsanitized skill/agent names (workspace-manager.ts)

**ID:** vuln-0004
**Severity:** HIGH
**Found:** 2026-11-20 13:29:55 UTC
**Target:** super-agent backend (local repository)
**CWE:** CWE-22
**CVSS:** 7.6
**Confidence:** High
**Fix Effort:** Low

## Description

Skill and agent names are stored and later used in filesystem path joins (workspace-manager.ts) without any sanitization or containment check. An authenticated org user who creates a skill or agent with a `../`-containing name causes the backend, when provisioning a chat session workspace, to write files (SKILL.md, agent .md, or a copied skill directory) to attacker-chosen locations outside the intended `.claude/skills` and `.claude/agents` directories on the server.

## Evidence

Vitest run (real WorkspaceManager from the repository, mocked S3 client, scratch base dir /tmp/trav-poc/workspaces): 3 tests passed. (1) downloadSkill with name `../../../../../../escaped-skill` and an inline body → log "[downloadSkill] Wrote inline skill \"../../../../../../escaped-skill\" from metadata body"; file `<base>/escaped-skill/SKILL.md` exists and contains the marker; control skill `normal-skill` correctly lands inside `.claude/skills/normal-skill/SKILL.md`. (2) generateAgentSubagentFiles with agent name `../../../../../evil-agent` → `<base>/org1/evil-agent.md` exists containing the marker prompt. (3) installSkillToWorkspace with skillName `../../../../../../copied-out` → `<base>/copied-out/SKILL.md` exists containing the marker. Contrast: readWorkspaceFile (workspace-manager.ts:1474-1476) rejects the same class of input via a prefix containment check.

## Impact

An authenticated org user can make the backend write arbitrary-content files (SKILL.md content / agent markdown with a controlled system prompt, or a full copied skill directory) to arbitrary relative paths reachable from the workspace base directory — e.g. overwriting application configs, other tenants' workspaces, cron/system files writable by the service user, or planting files that a later interpreter loads. File content includes substantial attacker-controlled text (skill body/description, agent systemPrompt). Demonstrated locally with synthetic markers reading the written files back outside the skills/agents roots.

## Counterevidence

Actively searched for controls: (1) skills.routes.ts has no JSON-schema or zod validation on POST / body name — only TypeScript interfaces; skill.service.ts createSkill passes input.name to the repository verbatim; updateSkill cannot change name but create can set any value. (2) The Prisma schema (skills.name VARCHAR(255)) and migration impose no format constraint — slashes and dots are valid characters. (3) The contrast control readWorkspaceFile at workspace-manager.ts:1474-1476 explicitly implements prefix containment, showing the codebase knows this pattern but did not apply it to skill/agent name joins. (4) Notably, document-group symlink names ARE sanitized with .replace(/[/\\:*?"<>|]/g, '-') (workspace-manager.ts:278), another proof sanitization exists elsewhere but not for skill/agent names. (5) Scope-generator-created skills and marketplace skills also feed these paths; I did not audit every name source, but the primary user-controlled route (POST /api/skills) is unvalidated, which alone establishes reachability. Searched for sanitization between service and workspace-manager (scope building in chat.service.ts/agent-runtime-claude.ts) — names are passed through as-is.

## What Would Change This Severity

Demonstrating that session workspaces are provisioned with the process owner able to write to a path that influences execution (e.g. another tenant's workspace, a service config, or a writable autoload directory) would raise confidentiality/availability and potentially the severity to high; if a name-format validation exists in an ingest layer not examined here (e.g. enterprise skill publish or import), reachability of the primary POST /api/skills route would need re-checking.

## Technical Analysis

Root cause is the absence of both input validation at creation time and containment checks at write time.

**Unvalidated creation path.** `POST /api/skills` (skills.routes.ts:50-54) accepts `{ name, display_name, ... }` with only a TypeScript interface — no zod/JSON-schema validation on `name`. `skillService.createSkill` (skill.service.ts:77-89) stores `input.name` verbatim to Postgres (`skills.name VARCHAR(255)`, no format constraint in prisma/schema.prisma:265). Similarly `createAgentSchema` (agent.schema.ts:17-21) enforces only min/max length and non-whitespace — `../../evil` passes. Notably, agent and skill names flow into `ScopeForWorkspace` (chat.service.ts) unmodified.

**Missing containment at the sink.** `WorkspaceManager.downloadSkill` (workspace-manager.ts:968-1044) computes `const skillDir = join(targetDir, skill.name)` with no containment check — unlike `readWorkspaceFile` (workspace-manager.ts:1474-1476), which explicitly rejects paths escaping `workspacePath`. The same unchecked join pattern exists in `generateAgentSubagentFiles` (workspace-manager.ts:756, `join(skillsDir, skill.name)` and :785 `${agent.name}.md`), `installSkillToWorkspace` (workspace-manager.ts:1359-1362, `join(skillsDir, skillName)` + `cp -r`), and `syncSkills` (workspace-manager.ts:862-883, removes/creates skill dirs by name). A `../` sequence in a name escapes the per-session workspace entirely: `join(skillsDir, '../../../../../../x')` resolves above the workspace base directory.

These sinks run during session provisioning (`ensureSessionWorkspace`, workspace-manager.ts:250-307), triggered whenever a chat session is created in a scope whose agents reference the crafted skill, and during workspace refresh on skill sync. Contrast: `createDocGroupSymlinks` (workspace-manager.ts:278) sanitizes document-group names with `replace(/[/\\:*?"<>|]/g, '-')` — the codebase sanitizes this same class of user data elsewhere but not for skills/agents.

## Proof of Concept

1. Create a skill via POST /api/skills with name `../../../../../../escaped-skill` and a body/description (no route/service validation exists). 2. Attach the skill to a business scope/agent so it enters SkillForWorkspace. 3. Start a chat session; ensureSessionWorkspace calls downloadSkill which computes join(skillsDir, skill.name) and writes SKILL.md there. 4. Observe the marker file written outside the skills directory. Repeat with an agent named `../../../../../evil-agent` (generateAgentSubagentFiles writes `${agent.name}.md` into agentsDir) and with installSkillToWorkspace (skillName joined into skillsDir then cp -r).

```python
// /tmp/trav-poc/poc.test.ts — vitest against the real WorkspaceManager
import { describe, it, expect } from 'vitest';
import { mkdir, rm, readFile, access, writeFile } from 'fs/promises';
import { join } from 'path';
import { WorkspaceManager, type SkillForWorkspace, type AgentForWorkspace } from '/workspace/agentcore-superagent-update/super-agent/backend/src/services/workspace-manager.js';

const BASE = '/tmp/trav-poc/workspaces';
const MARKER = 'TRAV-ESCAPE-MARKER-7f3a91';
const exists = async (p: string) => access(p).then(() => true).catch(() => false);

describe('workspace-manager path traversal via skill/agent names', () => {
  it('downloadSkill escapes skills dir', async () => {
    await rm(BASE, { recursive: true, force: true });
    const wm = new WorkspaceManager(BASE, {} as any); // bogus S3 -> inline-body fallback
    const skillsDir = join(BASE, 'org1/scope1/sessions/sess1/.claude/skills');
    const skill: SkillForWorkspace = {
      id: 's1', name: '../../../../../../escaped-skill', hashId: 'h1',
      s3Bucket: 'bogus', s3Prefix: 'skills/h1/', body: `content ${MARKER}`, description: 'desc',
    };
    await wm.downloadSkill(skill, skillsDir);
    const escaped = join(BASE, 'escaped-skill/SKILL.md');
    expect(await exists(escaped)).toBe(true);
    expect(await readFile(escaped, 'utf-8')).toContain(MARKER);
    // control: normal name stays inside
    await wm.downloadSkill({ ...skill, id: 's2', name: 'normal-skill' }, skillsDir);
    expect(await exists(join(skillsDir, 'normal-skill/SKILL.md'))).toBe(true);
  });

  it('generateAgentSubagentFiles escapes agents dir', async () => {
    const wm = new WorkspaceManager(BASE, {} as any);
    const agentsDir = join(BASE, 'org1/scope1/sessions/sess1/.claude/agents');
    await mkdir(agentsDir, { recursive: true });
    await wm.generateAgentSubagentFiles(agentsDir, [{
      id: 'a1', name: '../../../../../evil-agent', displayName: 'Evil', role: 'x',
      skillNames: [], systemPrompt: 'pwned', generatedSkills: [],
    } as any] as AgentForWorkspace[], join(BASE, 'org1/scope1/sessions/sess1/.claude/skills'));
    const escaped = join(BASE, 'org1/evil-agent.md');
    expect(await exists(escaped)).toBe(true);
    expect(await readFile(escaped, 'utf-8')).toContain('pwned');
  });

  it('installSkillToWorkspace copies outside workspace', async () => {
    const wm = new WorkspaceManager(BASE, {} as any);
    const src = '/tmp/trav-poc/src-skill';
    await rm(src, { recursive: true, force: true });
    await mkdir(src, { recursive: true });
    await writeFile(join(src, 'SKILL.md'), MARKER);
    await wm.installSkillToWorkspace('org2', 'scope2', 'sess2', '../../../../../../copied-out', src);
    const escaped = join(BASE, 'copied-out/SKILL.md');
    expect(await exists(escaped)).toBe(true);
    expect(await readFile(escaped, 'utf-8')).toContain(MARKER);
  });
});
// Run: DATABASE_URL=postgresql://fake:fake@localhost:5432/fake AWS_REGION=us-east-1 \
//   npx vitest run poc.test.ts --root /tmp/trav-poc --config /dev/null
// Result: 3 passed
```

## Remediation

Enforce a strict name format at the API boundary: validate skill and agent names with a schema (e.g. `^[A-Za-z0-9][A-Za-z0-9._-]*$`, no `/`, `\`, or leading dots) in the create/update routes and services, and reject existing stored names that violate it before workspace provisioning. Defense in depth: in WorkspaceManager, apply the same containment check used by `readWorkspaceFile` (resolve the joined path and verify it starts with the intended skills/agents directory) in `downloadSkill`, `generateAgentSubagentFiles`, `installSkillToWorkspace`, and when syncing/removing stale skill directories.

## Assumptions

Requires an authenticated org user who can create a skill (POST /api/skills) or agent (POST /api/agents) with a crafted name, plus a chat session to be provisioned in that scope (or, for installSkillToWorkspace, a marketplace skill name containing traversal — route-layer control of that name was not audited end to end). Backend runs with filesystem write access to the workspace base directory and its ancestors.
