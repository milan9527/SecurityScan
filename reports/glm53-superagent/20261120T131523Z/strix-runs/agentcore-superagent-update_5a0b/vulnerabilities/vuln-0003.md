# Cross-organization access on briefing routes (read/mark-read/archive other orgs' briefings)

**ID:** vuln-0003
**Severity:** HIGH
**Found:** 2026-11-20 13:28:22 UTC
**Target:** super-agent/backend (local repository: /workspace/agentcore-superagent-update)
**CWE:** CWE-639
**CVSS:** 7.6
**Confidence:** High
**Fix Effort:** Low

## Description

All four briefing endpoints under /api/business-scopes/:scopeId/briefings filter only by business_scope_id with no organization or scope-membership check. An authenticated user of any organization can read another org's briefing feed (titles, summaries, agent identities) and mutate its state (mark read, archive).

## Evidence

PoC run in the same file as the KB IDOR (tests/unit/kb-idor.poc.test.ts, C4 describe block, 3/3 passed): GET /api/business-scopes/{SCOPE_B}/briefings returned HTTP 200 with a briefing titled 'SECRET-BRIEFING' (organization_id ORG_B) to an org-A member; PATCH .../read set is_read=true; DELETE set is_archived=true. No 403/404 on any cross-org request.

## Impact

Cross-tenant disclosure of another organization's briefing content (titles, summaries, categories, statuses, agent display names) plus unauthorized state changes (mark-read, archive) that suppress those briefings for the victim org's users.

## Counterevidence

Checked: (1) authenticate resolves identity but performs no scope-membership or org check; (2) no requireScopeAccess preHandler is attached to any briefing route (other route files use it, this one does not); (3) scope_briefings carries organization_id in the schema but the queries never reference it; (4) the PATCH/DELETE filters use {id, business_scope_id} — that binds to the scope but the scope itself is unauthenticated, so it adds no tenant protection; (5) UUIDv4 scope IDs make blind enumeration impractical. Severity reflects that briefings are agent-generated summaries (potentially business-sensitive) and the writes are limited to read/archive flags rather than content.

## Confidence Rationale

Same executed-PoC basis as vuln-0002: real route handlers and prisma where clauses against a faithful in-memory store; only token verification stubbed.

## What Would Change This Severity

Proof that briefing summaries contain credentials or highly sensitive business data would raise integrity/confidentiality impact; confirmation that scope UUIDs are broadly exposed (logs/exports) would confirm exploitability at scale.

## Technical Analysis

src/routes/briefing.routes.ts queries prisma.scope_briefings with where: {business_scope_id: scopeId, ...} for list/count/groupBy and where: {id, business_scope_id: scopeId} for the mark-read and archive updates. The scope_briefings and business_scopes tables both carry organization_id, but no query references it. The sole preHandler is authenticate, which populates request.user (id/orgId/role) and performs no authorization; unlike several other route files, no scopeAccess middleware is attached here. Therefore request.user.orgId is available but unused, and any org's scope UUID grants full read and state mutation of that scope's briefings.

## Proof of Concept

Run `npx vitest run tests/unit/kb-idor.poc.test.ts` in super-agent/backend — the C4 describe block drives the real briefing route handlers with an org-A member identity against an org-B scope and briefing, using an in-memory prisma whose filtering mirrors exactly the where clauses the production code builds.

```bash
cd super-agent/backend && npx vitest run tests/unit/kb-idor.poc.test.ts
# C4 assertions (all green):
#  GET    /api/business-scopes/{SCOPE_B}/briefings            → 200, contains 'SECRET-BRIEFING'
#  PATCH  /api/business-scopes/{SCOPE_B}/briefings/{id}/read   → 200, is_read=true
#  DELETE /api/business-scopes/{SCOPE_B}/briefings/{id}        → 200, is_archived=true
```

## Remediation

Resolve the business scope first with an organization_id (or scope membership) constraint — e.g. load business_scopes by {id, organization_id: request.user.orgId} (or via scope_memberships) and 404 on miss — and add organization_id to every scope_briefings where clause, including the findMany, counts, groupBy, and the update filters.

## Assumptions

Authenticated user of any org; knowledge of the target business-scope UUID (internal org data, logs, or client bundles; business_scopes uses UUIDv4 so blind enumeration is impractical).
