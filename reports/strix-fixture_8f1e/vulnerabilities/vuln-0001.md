# SQL injection authentication bypass in app.py login()

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-11-20 02:27:34 UTC
**Target:** /home/ec2-user/bedrock/scan/strix-fixture
**Endpoint:** app.py:login()
**Method:** local Python execution (no HTTP)
**CWE:** CWE-89
**CVSS:** 5.1
**Confidence:** High
**Fix Effort:** Trivial

## Description

The **`login(name, password)`** function in `app.py` builds its SQL query by interpolating the caller-supplied username and password directly into the statement text with an f-string, allowing an attacker to alter query logic and authenticate without knowing any valid credential. Five different injection payloads each produced a successful login (`True`) against the seeded `demo` user, while the identical inputs were rejected by the parameterized control function.

## Evidence

## Impact

Complete authentication bypass of the `login()` function: an attacker who can supply a username or password string can authenticate as the seeded `demo` user (or, in a real deployment, as any user, including selecting a specific account via name-only payloads) without knowing any password. For this in-memory fixture with a single seeded row, the demonstrated consequence is unauthorized login as `demo` — confidentiality and integrity impact is limited to this disposable local fixture. In a production analogue, the same flaw grants access to any account's session and any data or actions that account can reach. Availability is not affected.

## Counterevidence

Actively looked for a mitigating control on the `login()` path and found none: the function performs no input validation, escaping, sanitization, or length restriction on either parameter before interpolation; the seeded data contains no characters that would break the payloads; and the query is executed directly with no intermediate layer. The negative control confirms the flaw is specific to interpolation — identical inputs are safe under `login_parameterized()`. Real deployment constraints that could reduce severity (WAF, input filtering upstream, network exposure limits) do not exist here since this is a local in-memory fixture, and the finding is scoped to that fixture as instructed.

## What Would Change This Severity

A deployment context in which `login()` were not reachable with attacker-controlled strings would lower severity; conversely, a demonstrated version of this flaw in a real multi-user deployment (bypassing authentication for arbitrary accounts) would raise it to critical.

## Technical Analysis

**Root cause:** `login()` at `app.py:12-15` constructs its query with an f-string:

```python title=app.py startLineNumber=12 endLineNumber=15
def login(name, password):
    with database() as conn:
        query = f"SELECT name FROM users WHERE name = '{name}' AND password = '{password}'"
        return conn.execute(query).fetchone() is not None
```

Both parameters are spliced into the SQL statement text without any escaping, validation, or parameter binding. `conn.execute()` receives the attacker-influenced string as raw SQL, so attacker input containing quote characters changes the structure of the `WHERE` clause rather than being compared as a literal value.

**Mechanism:** A password of `' OR '1'='1' --` closes the password literal, appends a tautology (`OR '1'='1'`), and comments out the remainder. The rendered statement becomes:

```sql
SELECT name FROM users WHERE name = 'demo' AND password = '' OR '1'='1' --'
```

Because `AND` binds tighter than `OR`, the predicate reduces to `(name='demo' AND password='') OR ('1'='1')`, which matches the seeded `demo` row regardless of the real password. A name payload of `demo' --` comments out the password clause entirely, matching on username alone. Both are textbook CWE-89 authentication bypass.

**Negative control:** `login_parameterized()` at `app.py:18-23` runs the same logical query through SQLite bound parameters:

```python title=app.py startLineNumber=18 endLineNumber=23
def login_parameterized(name, password):
    with database() as conn:
        return conn.execute(
            "SELECT name FROM users WHERE name = ? AND password = ?",
            (name, password),
        ).fetchone() is not None
```

The identical malicious payloads are treated strictly as data there (all returned `False`), which confirms the bypass is caused by the interpolation in `login()` and not by any quirk of the seeded data or query shape.

## Proof of Concept

1. Run the PoC script against the fixture with Python 3: it imports `app.py` and exercises both functions locally (no network, no file modification).
2. Baseline: call `login('demo', 'fixture-password')`, `login('demo', 'wrong')`, and `login('nouser', 'x')`, plus the same three calls against `login_parameterized` — all six behave as expected (valid login true, invalid logins false).
3. Inject five payloads into `login()`: `('demo', "' OR '1'='1' --")`, `('demo', "' OR 1=1 --")`, `("' OR '1'='1' --", 'x')`, `('demo' --`, `'anything')` i.e. name `demo' --`, and `("' OR 1=1 --", 'x')` — every one returns `True` without a valid password.
4. Negative control: run the exact same five payloads against `login_parameterized()` — every one returns `False`.
5. Observe the traced SQL statements executed by `login()` (captured via `sqlite3` trace callback), showing the attacker input rewriting the query structure.
6. Replay one rendered bypass query directly against an identical in-memory table and observe it returns the seeded `('demo',)` row.

## Remediation

Replace the f-string construction in `login()` with bound parameters exactly as the sibling function `login_parameterized()` already does: keep the statement as the constant `SELECT name FROM users WHERE name = ? AND password = ?` and pass `(name, password)` as the parameter tuple to `conn.execute`. The parameterized form was verified in this test to reject every malicious payload while accepting the valid credential, so adopting it closes the bypass. Do not build queries by concatenating or interpolating user input anywhere; always send user-supplied values through the driver's parameter-binding mechanism.

## Assumptions

Assumes the attacker can control the `name` and `password` arguments passed to `login()`, which is the function's only purpose as a credential check. Testing was local Python execution against the fixture as instructed; no deployment, network, or multi-user environment exists for this target.
