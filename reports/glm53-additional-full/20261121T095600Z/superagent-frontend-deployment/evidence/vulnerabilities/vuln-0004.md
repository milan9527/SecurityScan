# Cross-organization IDOR on knowledge-base, briefing, and scope plugin/MCP-server routes (missing organization_id scoping)

**ID:** vuln-0004
**Severity:** HIGH
**Found:** 2026-11-21 10:02:23 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent (backend)
**CWE:** CWE-639
**CVSS:** 8.3
**Confidence:** High
**Fix Effort:** Medium

## Description

Knowledge-base, briefing, and business-scope plugin/MCP-server routes in the backend Fastify API perform object lookups solely by primary-key identifier with no organization scoping. Any authenticated user of any tenant can read, modify, or soft-delete another organization's knowledge bases, files, folders, and briefings by supplying the target object's UUID.

## Evidence

Local unit PoC (`backend/tests/unit/kb-idor.poc.test.ts`): two orgs A and B instantiated in an in-memory store; requester is a member of org A; org B's KB, file, and briefing records are returned/modified by every route above (GET /:id returns org B's KB including description; PUT /:id renames it; DELETE sets status='deleted'; GET /:id/files returns the SECRET-MARKER file; DELETE /:id/files/:fileId removes it; GET /api/business-scopes/:scopeId/briefings returns org B's SECRET-BRIEFING record). All pass because the production `where` clauses never reference organization_id.

## Impact

Cross-tenant (cross-organization) read, modification, and deletion of tenant data: full knowledge-base metadata, file listings and metadata, and scope briefings of any organization; soft-deleting or renaming another org's knowledge bases; mutating their files. This breaks the multi-tenant isolation boundary of the platform for an entire resource family.

## Counterevidence

Checked for guards that would close this: (1) route-level `preHandler` arrays on all affected routes contain only `authenticate` / `requireModifyAccess` — the latter is purely role-based (`requireRole('owner','admin','member')`) and contains no org check; (2) the `backend/authorization/` layer (`requirePermission`, `authorizationService.authorize`) is NOT referenced on any of these routes; (3) the service layer applies no organization filter at the cited lines; (4) briefing routes query Prisma with only `business_scope_id`, and scope ownership is never resolved to an org. No compensating control found on any of these paths.

## Confidence Rationale

Complete source trace of routes and service layer showing the missing organization filter on every cited line, plus a local unit PoC against the real route handlers demonstrating cross-org read/write/delete of org B data by an org A user. Not exercised against a live deployment.

## What Would Change This Severity

Evidence that the deployment is effectively single-tenant would lower severity to medium; confirmation of internet-facing multi-tenant deployment is already assumed for this rating.

## Technical Analysis

`knowledge-base.routes.ts` guards every route only with `authenticate` / `requireModifyAccess` (the latter is `requireRole('owner','admin','member')` — a role check, not a tenant check). The handlers pass the raw `request.params.id` / `:fileId` / `:folderId` straight into `knowledgeBaseService`, whose queries contain no `organization_id` predicate: `findById` (knowledge-base.service.ts:69 — `prisma.knowledge_bases.findUnique({ where: { id } })`), `update` (:80), `delete` (:91 — soft-delete by id only), `listFiles` (:224, filters only on knowledge_base_id/folder/tags/search), `updateFile` (:277), `deleteFile` (:294), plus `renameFolder`/`deleteFolder` by folderId. `briefing.routes.ts:24-118` queries `prisma.scope_briefings` filtering only on `business_scope_id` (GET list, PATCH read, DELETE archive, stats) with no verification that the scope belongs to the caller's organization. In `businessScopes.routes.ts`, GET `/:id/plugins` (:821) runs raw SQL `WHERE sp.business_scope_id = ${id}` — it even computes `const orgId = request.user!.orgId` but never uses it — and GET `/:id/mcp-servers` (:940) joins `scope_mcp_servers`/`mcp_servers` scoped only by the scope id, disclosing other tenants' plugin git URLs and MCP server host addresses/config.

## Proof of Concept

1. Authenticate as a low-privilege user of organization A (any role ≥ member). 2. Issue GET /api/knowledge-bases/:id with a knowledge-base UUID belonging to organization B — the full record of org B's KB is returned. 3. Issue PUT/DELETE on the same ID — org B's KB is renamed/soft-deleted. 4. Issue GET /api/knowledge-bases/:id/files and DELETE /:id/files/:fileId to list and delete org B's files. 5. Issue GET /api/business-scopes/:scopeId/briefings with org B's scope ID to read org B briefings, and PATCH/DELETE to alter their read/archived state. 6. Same with GET /api/business-scopes/:id/plugins and /:id/mcp-servers. No 403/404 boundary is hit because the filters never compare organization_id.

## Remediation

Add an organization scoping predicate to every object lookup on these route families. For the knowledge-base service, change `findById`, `update`, `delete`, `listFiles`, `updateFile`, `deleteFile`, `renameFolder`, `deleteFolder`, and the batch operations to accept and filter on `organization_id` (e.g. `findUnique` → `findFirst({ where: { id, organization_id } })`), and pass `request.user.orgId` from every route handler. For briefing and business-scope routes, first resolve the business scope by `id` AND `organization_id`, returning 404 when it is not the caller's tenant, before querying or mutating child resources (briefings, plugins, mcp-servers). Do not rely on role checks (`requireModifyAccess`) as a tenant boundary.

## Assumptions

Authenticated user of any tenant (role `member` or above) with knowledge of or guessed object UUIDs. Production deployment exposure and route prefix registration were not tested against a live server; validation is via local unit PoC against the real route/service code with an in-memory store faithful to the Prisma `where` semantics.
