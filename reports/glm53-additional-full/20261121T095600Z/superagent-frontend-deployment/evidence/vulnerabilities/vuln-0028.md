# Unrestricted server-side fetch (SSRF) with response readback in workflow API-call node

**ID:** vuln-0028
**Severity:** MEDIUM
**Found:** 2026-11-21 10:08:44 UTC
**Target:** super-agent backend (local repository /workspace/agentcore-superagent-update/super-agent/backend)
**CWE:** CWE-918
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Medium

## Description

The workflow API-call node executes server-side fetches to fully attacker-controlled URLs with no allowlist, private-IP, or scheme restriction. Any authenticated organization member (the lowest privilege role) can point a workflow node at internal targets such as the cloud instance metadata service (169.254.169.254), loopback services, or RFC1910 hosts, set arbitrary request headers, and read the full response body back through the execution result.

## Evidence

Local PoC (mocked global fetch — no network contact; scratch under /tmp/ssrfpoc) using the actual compiled ActionNodeExecutor: the fetch sink received `http://169.254.169.254/latest/meta-data/iam/security-credentials/s3-role` after variable substitution of `{{env.role}}`, with the attacker-set header `X-aws-ec2-metadata-token`, and the node result carried the fetched body (`{"secret":"imds-role-credentials"}`) in `result.response`/`result.result`. Second assertion: `http://127.0.0.1:8080/api/health` reached the sink unvalidated. Both tests passed (vitest, 2/2). Source: node.data.metadata.apiConfig flows from the workflow definition authored by any 'member' via POST /api/workflows/:id/execute (execution.routes.ts:154).

## Impact

An authenticated low-privilege org member can exfiltrate the application server's cloud instance metadata credentials (AWS IMDS, GCP/Azure equivalents reachable from the host), probe and read internal services (Redis admin, admin panels, Kubernetes endpoints), and pivot those credentials into the cloud account. Demonstrated: arbitrary internal URL + attacker-chosen method/headers + complete response body returned to the caller via the workflow execution result.

## Counterevidence

Checked for mitigations: no allowlist/denylist/private-IP guard anywhere on the path (action-executor.ts:100-160); execution route does require authentication plus requireModifyAccess, so anonymous exploitation is blocked; requireModifyAccess includes the ordinary 'member' role, so the privilege bar is low, not a control; a 30s default timeout exists but only bounds duration. The feature argument ("API-call node is intended to make arbitrary HTTP calls") is design intent, not a security control — the demonstrated ability of a low-privilege org member to reach link-local metadata and internal RFC1910 services with full readback is the exploitable consequence of shipping that feature with no network-scope restriction.

## What Would Change This Severity

Confirmation that the backend host's cloud metadata service is IMDSv2-only and its role has no permissions, or that the deployment network blocks egress to 169.254.169.254 and internal hosts, would reduce this to internal-network probing; conversely, proof that fetched credentials grant cloud resource access would raise it toward critical.

## Technical Analysis

`executeApiCall` in `src/services/node-executors/action-executor.ts` takes `apiConfig` from the workflow node's `data.metadata` (line 98-100), substitutes workflow variables into the URL (line 103: `this.substituteVariables(apiConfig.url, context)`) and into headers (line 111-114), then performs `fetch(url, { method: apiConfig.method || 'GET', headers: {...attacker headers}, ... })` at line 123 with no URL validation of any kind — no allowlist, no scheme restriction, no private/internal IP filtering. The response body is parsed and returned in the node result (`response`/`result` fields, lines 143-152), and on failure the raw response body is included in the error, so the response is readable either way. Reachability: workflow definitions and their nodes are persisted user content; the execution route `POST /api/workflows/:workflowId/execute` (src/routes/execution.routes.ts:154) requires only `authenticate, requireModifyAccess, enforceTokenQuota`, and `requireModifyAccess` is `requireRole('owner','admin','member')` (src/middleware/auth.ts:280) — i.e. every ordinary member of an organization. Sibling surface: the same unvalidated fetch exists for MCP server health-checks in `src/services/mcp.service.ts` (fetch of `config.url || server.host_address` with server-supplied headers) for org admins, giving a second path with limited readback (success/latency/status only). The skill-marketplace fetch sites (skill-marketplace.service.ts:184,315,605,624,647,661,683,696,731) are constrained to github.com/raw.githubusercontent.com/api.github.com via `parseGitHubUrl` (hostname !== 'github.com' → rejected) or fixed hostnames, and were ruled out.

## Proof of Concept

1. As an authenticated org 'member', create a workflow containing an API-call action node whose apiConfig.url is an internal address (e.g. the instance metadata endpoint) and whose headers include any token the internal service expects. 2. Execute the workflow via the execute endpoint. 3. The node substitutes workflow variables into the URL, performs the server-side fetch with the attacker's headers, and places the full response body in the node result, which the caller reads from the execution output. Validated locally with a mocked global fetch asserting the URL, headers, and response readback.

```python
// Local PoC — mocked fetch, no network. Path: /tmp/ssrfpoc/action-executor.ssr.poc.test.ts
import { describe, it, expect, vi, beforeEach, afterEach } from 'vitest';
import { ActionNodeExecutor } from '/workspace/agentcore-superagent-update/super-agent/backend/src/services/node-executors/action-executor.js';

describe('action-executor SSRF (API call node)', () => {
  const calls: Array<{ url: string; headers: Record<string, string> }> = [];
  beforeEach(() => {
    vi.stubGlobal('fetch', vi.fn(async (url: string, init?: any) => {
      calls.push({ url, headers: init?.headers ?? {} });
      return new Response(JSON.stringify({ secret: 'imds-role-credentials' }),
        { status: 200, headers: { 'Content-Type': 'application/json' } });
    }));
  });
  afterEach(() => { vi.unstubAllGlobals(); calls.length = 0; });

  it('fetches arbitrary internal URL with attacker headers and reads response back', async () => {
    const exec = new ActionNodeExecutor();
    const node: any = { id: 'n1', type: 'action', position: { x: 0, y: 0 },
      data: { title: 'api', metadata: { actionType: 'api_call',
        apiConfig: { url: 'http://169.254.169.254/latest/meta-data/iam/security-credentials/{{env.role}}',
          method: 'GET', headers: { 'X-aws-ec2-metadata-token': 'test' } } } } };
    const result = await (exec as any).execute(
      { node, context: { variables: new Map([['env.role', 's3-role']]) } } as any);
    expect(calls.length).toBe(1);
    expect(calls[0].url).toContain('169.254.169.254');
    expect(calls[0].url).toContain('s3-role');
    expect(JSON.stringify(result)).toContain('imds-role-credentials'); // readback
  });

  it('no host/scheme validation exists: localhost reaches fetch', async () => {
    const exec = new ActionNodeExecutor();
    const node: any = { id: 'n1', type: 'action', position: { x: 0, y: 0 },
      data: { title: 'api', metadata: { actionType: 'api_call',
        apiConfig: { url: 'http://127.0.0.1:8080/api/health', method: 'GET' } } } };
    await (exec as any).execute({ node, context: {} } as any);
    expect(calls.map((c) => c.url)).toContain('http://127.0.0.1:8080/api/health');
  });
});
```

## Remediation

Restrict the API-call node's outbound requests: validate the resolved URL (after variable substitution, at execution time) against a denylist of non-routable ranges (loopback, RFC1910, link-local 169.254.0.0/16 including cloud metadata, IPv6 equivalents, and decimal/hex IP encodings), and optionally an allowlist of approved external hosts per organization. Enforce HTTPS-only unless explicitly opted in. Consider blocking or scrubbing user-settable headers that can bypass IMDSv2 protections. If arbitrary outbound HTTP is a deliberate product capability, gate it behind an explicit admin-configured egress policy rather than the default member role.

## Assumptions

Requires an authenticated org member with workflow modify access (owner/admin/member — requireModifyAccess) who can create or edit a workflow with an API-call node. Deployment must place the backend on a network with reachable internal services (cloud metadata endpoint, internal admin panels), which is the normal deployment posture of this stack.
