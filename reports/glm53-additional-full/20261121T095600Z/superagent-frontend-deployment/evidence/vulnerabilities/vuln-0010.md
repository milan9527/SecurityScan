# PoC app-hosting stack: docker.sock mounts, insecure Traefik dashboard, and hardcoded tenant JWT secrets

**ID:** vuln-0010
**Severity:** CRITICAL
**Found:** 2026-11-21 10:02:52 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent/app-hosting/poc
**CWE:** CWE-798
**CVSS:** 10.0
**Confidence:** Medium
**Fix Effort:** Medium

## Description

The app-hosting PoC stack ships with the Docker socket mounted into two containers, the Traefik dashboard exposed insecurely on all interfaces, and per-tenant JWT signing secrets hardcoded as predictable strings in source and Kubernetes manifests. While the directory is labelled a proof-of-concept, these patterns grant host-level code execution and cross-tenant token forgery on any host where the stack is run.

## Evidence

app-hosting/poc/docker-compose.floci.yml — traefik service:
```
    command:
      - "--api.insecure=true"
      - "--providers.docker=true"
      ...
    ports:
      - "8080:80"
      - "8081:8080"     # Traefik dashboard
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
```
app-host-api service: `volumes: - /var/run/docker.sock:/var/run/docker.sock`.
app-hosting/poc/services/app-host-api/src/insforge.ts:54/64/74: `jwtSecret: 'alpha-jwt-secret-poc-change-me'` (also beta-/gamma- variants).
app-hosting/poc/services/runtime/src/auth.ts:4: `const JWT_SECRET = process.env.JWT_SECRET || 'poc-secret-change-me'`.
app-hosting/poc/k8s/tenants/*.yaml: literal JWT_SECRET values e.g. `"gamma-dash-jwt-secret"`, `"beta-crm-jwt-secret"`, `"alpha-schedule-jwt-secret"`.

## Impact

On a host running this stack: any attacker who can reach port 8081 gets the unauthenticated Traefik dashboard (full routing/service configuration disclosure, ability to observe and manipulate proxies). The docker.sock mounts mean a compromise or SSRF/RCE inside the traefik or app-host-api containers (both reachable from the network) escalates to full host compromise — arbitrary container execution, secret and volume access. The hardcoded, predictable per-tenant JWT secrets allow forging valid tenant tokens (runtime/src/auth.ts falls back to 'poc-secret-change-me' when the env var is unset, so any deployment that relies on the fallback is forgeable).

## Counterevidence

The whole tree sits under app-hosting/poc/ with README/ARCHITECTURE framing it as a demonstration; docker-compose uses providers.docker.exposedbydefault=false (only labelled routes exposed); the tenant-alpha schedule app pulls JWT_SECRET from a secretRef rather than a manifest literal, showing awareness of secret management; and docker.sock mounts plus the insecure dashboard are common (if risky) patterns in local docker-compose labs. However none of these are enforcement controls: the traefik dashboard is still reachable on 0.0.0.0:8081, the JWT secrets are still literal defaults, and the API container still gets full host-level docker control.

## Confidence Rationale

All cited lines verified statically; no running instance was available to confirm exposure, and the PoC labelling plus k8s secretRef usage suggest these manifests may not ship to production. Local-only assessment per mandate.

## What Would Change This Severity

Evidence this PoC stack (or the k8s manifests) is deployed beyond a local demo — e.g. reachable dashboard or API on a shared host — would raise severity to high; confirmation that the PoC is exclusively a disposable local lab with no shared access would lower it to low.

## Technical Analysis

Four independently exploitable patterns in the PoC stack, each verified at its cited line:

1. `/var/run/docker.sock` is bind-mounted into both the `traefik` service and the `app-host-api` service (docker-compose.floci.yml). Both services publish ports to the host (8080/8081 and 3001 respectively), so both are network-reachable processes holding the Docker control socket. Any code execution or SSRF-class issue inside either container — including via the app-host-api's tenant provisioning endpoints — converts directly into arbitrary container execution on the host and access to every other tenant's containers, volumes, and environment secrets.

2. Traefik runs with `--api.insecure=true` and the dashboard entrypoint is published as `"8081:8080"`, so the dashboard and its read/write HTTP API are reachable without authentication on all interfaces of the host.

3. `services/app-host-api/src/insforge.ts` lines 54, 64, 74 hardcode per-tenant `jwtSecret` values ('alpha-jwt-secret-poc-change-me', 'beta-jwt-secret-poc-change-me', 'gamma-jwt-secret-poc-change-me'). These secrets sign tenant tokens used by the app-host API; anyone who knows the repo can forge tokens for any tenant.

4. `services/runtime/src/auth.ts:4` falls back to `process.env.JWT_SECRET || 'poc-secret-change-me'`, and `k8s/tenants/*.yaml` ship literal JWT_SECRET values ('alpha-schedule-jwt-secret', 'beta-crm-jwt-secret', 'gamma-dash-jwt-secret') as plain manifest env entries, so deployments either run with a predictable public secret or rely on a fallback that is itself public.

## Proof of Concept

1. Verify docker-compose.floci.yml mounts /var/run/docker.sock into both the traefik and app-host-api services and runs Traefik with --api.insecure=true, publishing the dashboard on host port 8081.
2. Verify app-host-api/src/insforge.ts:54/64/74 hardcodes tenant JWT secrets ('alpha-jwt-secret-poc-change-me' etc.) and runtime/src/auth.ts:4 falls back to 'poc-secret-change-me'.
3. On any host running the stack: `curl http://<host>:8081/api/http/routers` returns the unauthenticated dashboard API; inside either container, `docker -H unix:///var/run/docker.sock run ...` executes arbitrary containers on the host; with a known tenant secret, forge a JWT for any tenant/app identity.
4. None of these steps were executed against a live host (local-only assessment); each control path is verified from source.

## Remediation

Do not mount docker.sock into containers that accept network traffic; use a socket proxy with restricted operations, or a container-runtime API with least privilege. Disable --api.insecure (or bind the dashboard to 127.0.0.1 behind auth). Replace every hardcoded tenant JWT secret with per-deployment generated secrets sourced from a secret store; remove the runtime fallback default and fail fast when JWT_SECRET is unset. In the k8s manifests, move JWT_SECRET values into Secrets (the schedule-app already uses a secretRef — extend that pattern to all apps).

## Assumptions

Assumes a host running this PoC compose file or applying the k8s/tenants manifests, with the published ports (8081 dashboard, 3001 API, per-tenant DB ports) reachable to the attacker. The directory is labelled POC; no evidence was found of it being deployed beyond local demonstration, and the docker.sock paths require control of that host. Production exploitability is therefore a deployment-context question, not a demonstrated fact.
