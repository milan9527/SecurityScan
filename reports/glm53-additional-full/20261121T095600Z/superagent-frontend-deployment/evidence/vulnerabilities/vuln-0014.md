# agentAccess explicit-permission lookup ignores organization scoping (cross-org permission confusion)

**ID:** vuln-0014
**Severity:** MEDIUM
**Found:** 2026-11-21 10:03:22 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent (backend)
**CWE:** CWE-639
**CVSS:** 6.8
**Confidence:** High
**Fix Effort:** Low

## Description

AgentAccessService.checkAccess() resolves explicit agent permissions by the (agent_id, user_id) pair without verifying that the agent belongs to the caller's organization. A user who holds (or obtains) a permission row for another organization's agent is granted that access level there, bypassing the org-scoped checks that guard the rest of the function.

## Evidence

Local unit PoC `backend/tests/unit/tenant-isolation.audit.test.ts` ("agentAccess cross-org permission confusion"): mocks `agent_permissions.findUnique` to return `{permission:'admin', agent_id:'agentX', user_id:'user-orgA'}` and calls the real `agentAccessService.checkAccess('user-orgA','orgA','agentX','admin')` — returns true even though agentX belongs to another org; the org-scoped agent lookup is never reached because the explicit-permission branch returns first.

## Impact

Cross-organization privilege confusion on agent access: the affected callers include agent invocation (chat.routes.ts:223), agent visibility within business scopes (businessScopes.routes.ts:678), and the agentAccess middleware (middleware/agentAccess.ts:55) — an attacker granted a permission row on a foreign-org agent gains invoke/admin access to that agent, i.e. cross-tenant use of (and potentially data exposure via) the target org's agent.

## Counterevidence

The subsequent checks in checkAccess DO scope by organization: the agent lookup at line 65 filters `{ id: agentId, organization_id: orgId }` and returns false when the agent is not in the caller's org, and scope-membership inheritance is likewise scope-bound. So the vulnerability is confined to the explicit `agent_permissions` branch, which runs FIRST and short-circuits with `return true` before the org-scoped checks. A unique composite index `unique_agent_user_permission` enforces one row per (agent,user) pair but does not constrain the pair to a single organization. If agent_permissions rows can only ever be created through an org-validated flow, real-world exploitability narrows; no such constraint exists at this layer.

## Confidence Rationale

Complete source trace: the explicit-permission lookup at agentAccess.service.ts:56-60 queries only by (agent_id, user_id) with no organization_id, and returns true before any org-scoped query runs. Local unit PoC (tenant-isolation.audit.test.ts) confirms the behavior against the real service. The only unproven element is how often cross-org permission rows exist in real data — stated in assumptions.

## What Would Change This Severity

Evidence that cross-org agent_permissions rows occur in practice (e.g. via a sharing feature that writes them) would raise severity to high with lower attack complexity; evidence that every writer of agent_permissions enforces same-org pairs would lower this to a hardening finding.

## Technical Analysis

`services/agentAccess.service.ts:47-77`: `checkAccess(userId, orgId, agentId, minLevel)` first queries `prisma.agent_permissions.findUnique({ where: { unique_agent_user_permission: { agent_id: agentId, user_id: userId } } })` (lines ~56-60) and, if the permission level meets the minimum, returns true immediately — with no comparison of the agent's owning organization to the caller's `orgId`. Only the fallback paths (creator check, scope membership) consult org-scoped data: the agent is re-fetched with `where: { id: agentId, organization_id: orgId }` (line 65), which is correct but unreachable once the explicit-permission branch has returned. Any agent_permissions row that pairs a user with another organization's agent therefore grants that user access across the tenant boundary.

## Proof of Concept

1. As user U of organization A, obtain an agent_permissions row for agent X of organization B (any flow that writes agent_permissions keyed by user id — e.g. cross-org sharing or imported data). 2. Call an endpoint protected by agentAccess middleware or chat invocation that calls checkAccess(U, orgA, X, 'invoke'). 3. The explicit-permission lookup (agentAccess.service.ts:56-60) matches on (agent_id, user_id) only and returns true before any organization check. 4. The request proceeds against organization B's agent.

```ecl
# Unit PoC: cd super-agent/backend && npx vitest run tests/unit/tenant-isolation.audit.test.ts
# Real agentAccessService.checkAccess with mocked prisma:
agent_permissions.findUnique({ where: { unique_agent_user_permission:
  { agent_id: 'agentX', user_id: 'user-orgA' } } })
  -> { permission: 'admin' }        # row referencing another org's agent
checkAccess('user-orgA', 'orgA', 'agentX', 'admin') === true
# The org-scoped prisma.agents.findFirst is never consulted (short-circuit).
```

## Remediation

In AgentAccessService.checkAccess, validate the resolved explicit permission against the agent's organization before trusting it: either join the permission lookup to agents and require `agent.organization_id === orgId`, or perform the existing org-scoped agent lookup (line 65) first and skip/ignore explicit permissions when the agent is not in the caller's organization. Apply the same fix to any sibling functions in agentAccess.service.ts that read agent_permissions without org context.

## Assumptions

An attacker with an authenticated session in organization A whose user_id appears in an `agent_permissions` record for an agent belonging to organization B (e.g. via cross-org sharing, a data import, an admin mistakenly granting permission to a user id, or the shared-UUID collision scenario the tenant-isolation audit demonstrates). Production exploitability depends on whether cross-org permission rows can realistically arise; the code permits them and trusts them unconditionally. Validated locally against the real service with mocked prisma.
