# Path traversal in agentcore workspace-sync S3 restore and related workspace-manager path containment weaknesses

**ID:** vuln-0027
**Severity:** MEDIUM
**Found:** 2026-11-21 10:07:12 UTC
**Target:** super-agent backend + agentcore (local repository /workspace/agentcore-superagent-update)
**CWE:** CWE-22
**CVSS:** 6.8
**Confidence:** Medium
**Fix Effort:** Low

## Description

Three related path-containment weaknesses in the agentcore workspace layer allow filesystem paths to escape their intended directory when untrusted path components are joined without canonical containment checks. The primary instance is the agentcore workspace-sync S3 restore routine; two sibling weaknesses in the backend workspace-manager share the same root-cause family (missing or incorrect path containment).

## Evidence

Local PoC (mocked S3 listing, real fs/path code): a workspace-sync key of the form <prefix>../../etc/poc_marker produced localPath /etc/poc_marker — the escape succeeds in real path arithmetic. For the sibling: with workspacePath ending in 'sessionA' (no separator), startsWith('sessionA-evil/...') resolves to true, bypassing the containment check in resolveWorkspaceFilePath.

## Impact

Primary: with attacker-controlled S3 keys under the workspace prefix, arbitrary file write (overwrite) anywhere the process can write, including host config, application files, or other tenants' workspace directories. Sibling (a): cross-session file access within the same org/scope when a session ID is a prefix of another. Sibling (b): unvalidated filePath permits cross-tenant S3 reads if any session-scoped path is reachable. Scope is limited by the stated prerequisites of each instance.

## Counterevidence

Traced the primary vector's prerequisites: workspace-sync reads keys from a ListObjectsV2 on a configured prefix, and no tenant-reachable API writes arbitrary keys into that prefix — the write primitive itself is the missing link, making this a shared/compromised-bucket scenario rather than a directly exploitable tenant path. The resolveWorkspaceFilePath check exists and does enforce containment except for the separator defect; readWorkspaceFileFromS3 callers were inspected but the tenant-facing chain for it was not fully traced to a live route. These constraints are stated rather than used to dismiss the finding.

## Confidence Rationale

The path-escape mechanics were validated with real fs operations and mocked S3, and the missing containment checks were confirmed by direct code reading at the cited lines. However, the primary S3-key vector lacks a demonstrated attacker-controlled write path in this codebase, and production reachability of each sibling's caller chain is unverified.

## What Would Change This Severity

Discovery of a tenant-reachable primitive that writes attacker-controlled keys into the workspace S3 prefix would raise this to high/critical; confirmation that the workspace bucket is never shared across trust domains and session IDs cannot prefix one another would lower it.

## Technical Analysis

**Primary — agentcore/src/workspace-sync.ts:77-85 (sink at line 94).** On restore, `relativePath = key.slice(prefix.length)` then `localPath = path.join(WORKSPACE_DIR, relativePath)` with no containment check before `fs.mkdirSync`/write. S3 keys containing `../` segments resolve outside `/workspace`. Prerequisite: attacker-controlled keys under the workspace prefix (e.g. a shared or compromised bucket) — no tenant-reachable write primitive into this prefix was found in this codebase. The path arithmetic was validated locally with mocked S3 and the real `path.join`/fs behavior; no control exists between the join and the write.

**Sibling (a) — backend/src/services/workspace-manager.ts:1547-1555 (resolveWorkspaceFilePath).** `resolved.startsWith(workspacePath)` without a trailing separator: a path like `../sessionA-evil/...` passes the check when the current session ID is a prefix of another (`sessionA` vs `sessionA-evil`), enabling cross-session file access within the same org/scope. The bypass was verified against the real implementation.

**Sibling (b) — backend/src/services/workspace-manager.ts:1495-1530 (readWorkspaceFileFromS3).** The `filePath` parameter is interpolated directly into the S3 key `${orgId}/${scopeId}/${sessionId}/${filePath}` without validation, so `../` segments (or leading `/`) can target keys outside the session prefix on read. Reachability depends on its callers; no validated caller chain to an attacker-controlled `filePath` was demonstrated, so it is recorded as a related weakness, not a standalone confirmed exploit.

All three share one root cause: untrusted path components joined without canonical containment verification.

## Proof of Concept

1. Mock the S3 ListObjectsV2 result to include a key of the form <prefix>../../etc/poc_marker.
2. Run the workspace-sync restore routine.
3. Observe localPath resolves outside /workspace and the marker file is written at the escaped location (confirmed by real path.join arithmetic; no named containment control exists).

````js
// Local PoC (vitest, mocked S3, real fs/path)
import path from 'node:path';
const WORKSPACE_DIR = '/workspace';
const prefix = 'org1/scope1/session1/';
const key = prefix + '../../etc/poc_marker';
const relativePath = key.slice(prefix.length); // '../../etc/poc_marker'
const localPath = path.join(WORKSPACE_DIR, relativePath);
console.log(localPath); // -> '/etc/poc_marker' — escaped WORKSPACE_DIR
```

```js
// Sibling-prefix bypass of resolveWorkspaceFilePath
const workspacePath = '/data/org1/scope1/sessionA';
const filePath = '../sessionA-evil/secret.txt';
const resolved = path.join(workspacePath, filePath);
resolved.startsWith(workspacePath); // -> true (no separator), check passes
// resolved: '/data/org1/scope1/sessionA-evil/secret.txt' — different session
````

## Remediation

After every join with an untrusted path component, canonicalize the result (path.resolve) and verify containment with a separator-aware check (e.g. resolved === root || resolved.startsWith(root + path.sep)). In workspace-sync, reject any key whose sliced relative path begins with '..', resolves to an absolute path, or escapes WORKSPACE_DIR. Apply the separator-aware fix to resolveWorkspaceFilePath, and apply the same canonical containment validation to the filePath used to build S3 keys in readWorkspaceFileFromS3 / readWorkspaceFileFromS3Raw.

## Assumptions

Primary vector (S3 key control) requires the attacker to control object keys under the workspace prefix — no tenant-reachable write primitive into that prefix was found, so it presupposes a shared or compromised bucket scenario. Sibling weaknesses operate through the session/workspace API with authenticated session access. Local validation used mocked S3 against real filesystem/SDK code.
