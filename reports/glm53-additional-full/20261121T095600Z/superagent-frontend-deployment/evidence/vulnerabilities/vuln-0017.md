# axios 1.13.6 in backend (multiple 2026 SSRF/proxy-bypass CVEs, not reachable as used)

**ID:** vuln-0017
**Severity:** INFO
**Found:** 2026-11-21 10:04:01 UTC
**Target:** super-agent (backend)
**Package:** axios
**Ecosystem:** npm
**Installed Version:** 1.13.6
**Fixed Version:** 1.15.2
**Dependency Chain:** @larksuiteoapi/node-sdk@1.60.0 > axios@1.13.6
**CVE:** CVE-2026-42043
**CWE:** CWE-183
**Advisory CVSS:** 7.5
**Contextual CVSS Vector:** CVSS:3.1/AV:A/AC:H/PR:N/UI:N/S:U/C:N/I:N/A:N
**Fix Effort:** Low

## Description

The backend pins `axios` 1.13.6 in `backend/package-lock.json`, pulled transitively by the direct IM-adapter SDKs (`@larksuiteoapi/node-sdk` 1.60.0, `@wecom/aibot-node-sdk` 1.0.7, `dingtalk-stream` 2.1.6-beta.1). axios before 1.15.1 is affected by a family of 2026 SSRF/proxy-handling CVEs (e.g. CVE-2026-42043, the 127.0.0.0/8 NO_PROXY bypass that NVD scores 10.0, and CVE-2026-42264, CRLF/header splitting, 9.1). The application code itself imports axios zero times; the only executions are inside the Lark SDK's client against fixed vendor hosts.

## Evidence

**Advisory evidence:** `CVE-2026-42043` applies to `axios` at installed version `1.13.6`. The advisory is fixed in `1.15.2`.

**Dependency chain:** `@larksuiteoapi/node-sdk@1.60.0 > axios@1.13.6`

**Usage analysis:** the package is loaded, but this advisory's vulnerable code does not run here. Import check: no application code imports axios (rg "from 'axios'" over backend/src returns nothing). Resolution chains: @larksuiteoapi/node-sdk@1.60.0 -> axios ~1.13.3, @wecom/aibot-node-sdk@1.0.7 -> axios ^1.6.7, dingtalk-stream@2.1.6-beta.1 -> axios ^1.4.0 (backend/package-lock.json:6949 pins the resolved 1.13.6). Affected-symbol check: the 2026 axios CVEs (CVE-2026-42043 NO_PROXY 127/8 bypass; CVE-2026-42264 CRLF injection) trigger when an attacker influences the request URL of an axios call or the deployment relies on NO_PROXY. Trace: entry point is a Feishu IM message received via the lark WSClient (backend/src/services/feishu-adapter.ts:320 `new lark.WSClient(...)`) -> the SDK's axios-based API client sends requests only to its own fixed Feishu/Lark API base (feishu-adapter.ts:23 getApiBase returns https://open.feishu.cn or https://open.larksuite.com) -> package call axios.request with vendor-controlled constant URLs. The wecom and dingtalk adapters use Node's global fetch, not axios (wecom-adapter.ts:59, dingtalk-adapter.ts:33). No hop passes attacker-controlled URLs to axios, and no NO_PROXY variable is set anywhere in the repo (rg "NO_PROXY" returns nothing), so the vulnerable proxy-bypass/CRLF paths do not execute under attacker influence.

## Impact

As used here the practical impact is negligible: no application code makes axios requests with attacker-controlled URLs, no NO_PROXY environment is configured, and the SDK targets fixed Feishu/Lark API hosts. The finding documents the supply-chain exposure of shipping an axios version with open CVSS-9/10 proxy-bypass/SSRF advisories; any future code path that passes user-controlled URLs to axios (or a NO_PROXY deployment) would activate them.

## Contextual CVSS

Entry point: Feishu message arrives over the lark WSClient (backend/src/services/feishu-adapter.ts:320), and outbound API replies/calls made by the SDK use the pinned axios 1.13.6 (pulled by @larksuiteoapi/node-sdk@1.60.0, backend/package-lock.json:6949) to fixed Feishu/Lark API hosts (getApiBase, feishu-adapter.ts:23) — not attacker-chosen URLs. None of the application code sets NO_PROXY, no proxy environment is configured in the repo, and every axios request target is the fixed open.feishu.cn/open.larksuite.com base, so the SSRF/proxy-bypass preconditions the CVEs require are absent. All three impact metrics are therefore N: the vulnerable code is present and executes on every Feishu send, but no attacker-controlled input reaches it in a way the advisory's path exploits. Any exploitation would additionally require an adjacent-network proxy position plus environment configuration this codebase does not set.

## Remediation

Add an npm override in backend/package.json ("overrides": { "axios": "^1.15.2" }) so all three IM SDK chains resolve a patched axios, and verify with `npm ls axios`. No code change is required — the usage today is vendor-fixed URLs only.
