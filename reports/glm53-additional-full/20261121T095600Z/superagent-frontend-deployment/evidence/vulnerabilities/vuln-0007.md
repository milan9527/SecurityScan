# Hardcoded Redis password and unset deployment secrets (REDIS_PASSWORD/JWT_SECRET) in provisioning scripts

**ID:** vuln-0007
**Severity:** HIGH
**Found:** 2026-11-21 10:02:35 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent (infra deployment scripts + backend config)
**CWE:** CWE-798
**CVSS:** 8.1
**Confidence:** Medium
**Fix Effort:** Low

## Description

The infrastructure provisioning sets a hardcoded, repository-published Redis password on the EC2 host Redis, while both deployment env-generation paths emit an empty REDIS_PASSWORD for the backend. The CI env template also omits JWT_SECRET, letting the backend fall back to its hardcoded default signing secret. Together these leave the job-queue/cache layer open to anyone who can reach Redis and leave JWTs forgeable on CI-provisioned deployments.

## Evidence

infra/scripts/user-data.sh:73-74:
```
sed -i 's/^# requirepass .*/requirepass super-agent-redis-password/' /etc/redis/redis.conf
sed -i 's/^requirepass .*/requirepass super-agent-redis-password/' /etc/redis/redis.conf
```
infra/scripts/ci/gen-base-env.py:25: `REDIS_PASSWORD=` (empty). infra/scripts/deploy.sh:213: `REDIS_PASSWORD=${REDIS_ENDPOINT:+}` (empty). backend/src/config/index.ts:30: JWT_SECRET default `'super-agent-local-dev-secret-change-in-production'`. backend/src/config/index.ts:145: INSFORGE_JWT_SECRET default `'spike-test-secret-key-must-be-32-chars-long'`.

## Impact

On deployments where local Redis is the active host (the documented ElastiCache fallback), an attacker who can reach port 6379 authenticates with the public 'super-agent-redis-password' and gains read/write access to BullMQ job queues and cached data, including injecting or manipulating queued jobs (agent runs, async work). On CI-provisioned deployments where merge-env.sh does not inject a JWT_SECRET, the backend signs and verifies JWTs with the repository-public default, allowing token forgery. The local docker-compose dev environment (JWT_SECRET 'local-dev-jwt-secret-change-in-production', postgres:postgres, published 5432/6379) is the same root cause at dev severity.

## Counterevidence

Three real mitigations were found: deploy.sh:239 and merge-env.sh:9 both generate a random JWT_SECRET, so deployments using those paths have a strong secret (though only when AUTH_MODE is not Cognito in deploy.sh); local Redis is disabled when ElastiCache is configured, so Redis exposure requires the documented fallback; and user-data.sh:241 places a CHANGE_ME JWT placeholder that deploy.sh's "existing values win" merge does not overwrite — but CHANGE_ME is not a secret, and neither control exists on the CI gen-base-env.py path. No source sets REDIS_PASSWORD anywhere; the empty value in both provisioning paths is a genuine gap, not an oversight of the reviewer.

## Confidence Rationale

All code paths verified statically, but no live deployment or CI pipeline was available to confirm the ElastiCache configuration or whether merge-env.sh always runs in practice; the JWT fallback impact depends on the backend default-secret finding filed separately.

## What Would Change This Severity

Proof that a real deployment runs with local Redis exposed (or ElastiCache left without auth) would confirm the Redis impact; proof that merge-env.sh never runs in the actual CI pipeline would confirm JWT forgery impact; evidence that ElastiCache is always configured with in-transit encryption and auth would reduce the Redis side to low.

## Technical Analysis

Redis: `infra/scripts/user-data.sh:73-74` runs on EC2 boot and sets the host Redis `requirepass` to the literal `super-agent-redis-password`, which is committed to the repository and therefore public to anyone who reads it. The comment at user-data.sh:71-72 documents that this local Redis is the fallback when ElastiCache is not configured — i.e. it is a real runtime component on at least some deployments. Meanwhile no provisioning path gives the backend a matching secret: `infra/scripts/ci/gen-base-env.py:25` writes `REDIS_PASSWORD=` (empty) even with `NODE_ENV=production`, and `infra/scripts/deploy.sh:213` writes `REDIS_PASSWORD=${REDIS_ENDPOINT:+}` — also empty whether or not ElastiCache is present. So the backend cannot authenticate to the host Redis it is expected to use in fallback mode, and any attacker who can reach the instance's port 6379 authenticates with the public password and can read/mutate BullMQ queues and caches.

JWT: `backend/src/config/index.ts:30` makes `JWT_SECRET` optional with default `'super-agent-local-dev-secret-change-in-production'`, and `:145` gives `INSFORGE_JWT_SECRET` a default of `'spike-test-secret-key-must-be-32-chars-long'`. The interactive `deploy.sh:239` generates a random JWT_SECRET, but only in non-Cognito mode, and `infra/scripts/ci/merge-env.sh:9` appends a random one — yet `infra/scripts/ci/gen-base-env.py`, the base template the CI pipeline builds on, emits no JWT_SECRET at all and `user-data.sh:241` seeds `JWT_SECRET=CHANGE_ME`. On a CI-provisioned host where merge-env.sh is not invoked or where the placeholder survives, the backend runs in production NODE_ENV signing and verifying JWTs with a repository-public string, making all local-auth tokens forgeable (this is the infra-side deployment path for the backend default-JWT-secret weakness; the backend default itself is being reported separately by the auth agent).

The backend `docker-compose.yml` (JWT_SECRET `local-dev-jwt-secret-change-in-production`, `postgres:postgres` published on 5432, unauthenticated Redis published on 6379) is the same root cause — weak/published secret defaults shipped in configuration — at local-development severity, and is merged into this report rather than filed separately.

## Proof of Concept

1. Inspect infra/scripts/user-data.sh:73-74 — Redis requirepass is set to the literal 'super-agent-redis-password', committed to the repository.
2. Inspect infra/scripts/ci/gen-base-env.py:25 (REDIS_PASSWORD empty) and infra/scripts/deploy.sh:213 (REDIS_PASSWORD set to empty regardless of endpoint) — no path ever populates the backend Redis password.
3. Confirm backend/src/config/index.ts:30 — absent JWT_SECRET falls back to the hardcoded 'super-agent-local-dev-secret-change-in-production'; gen-base-env.py emits no JWT_SECRET and merge-env.sh only appends one if invoked.
4. On a deployment using local Redis: `redis-cli -h <host> -p 6379 -a super-agent-redis-password ping` authenticates; queue and cache keys are then readable/writable (not executed; local-only assessment).

## Remediation

Generate the Redis password at provisioning time (e.g. openssl rand) and inject it into both redis.conf and the backend .env from the same secret, never commit a literal password. Set REDIS_PASSWORD in gen-base-env.py from a secret store, set JWT_SECRET unconditionally (removing the backend's hardcoded default fallback), and bind Redis to 127.0.0.1 / firewall the port. Replace the docker-compose development defaults with clearly-named throwaway secrets and avoid publishing service ports to the host.

## Assumptions

Assumes an ElastiCache-disabled or fallback-to-local-Redis deployment (documented fallback behavior of user-data.sh) reachable on port 6379, and/or a deployment provisioned through the CI path where merge-env.sh does not run or runs before JWT_SECRET is checked. Redis network exposure and CI pipeline invocation are unverified (local-only assessment).
