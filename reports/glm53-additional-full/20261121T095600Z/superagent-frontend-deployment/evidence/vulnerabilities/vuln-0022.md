# CVE-2026-25223 in fastify 5.6.2 / 4.29.1 (Content-Type tab validation bypass)

**ID:** vuln-0022
**Severity:** INFO
**Found:** 2026-11-21 10:04:30 UTC
**Target:** super-agent (backend)
**Package:** fastify
**Ecosystem:** npm
**Installed Version:** 5.6.2
**Fixed Version:** 5.7.2
**CVE:** CVE-2026-25223
**CWE:** CWE-436
**Advisory CVSS:** 7.5
**Contextual CVSS Vector:** CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:N
**Fix Effort:** Low

## Description

The backend pins `fastify` 5.6.2 (direct dependency ^5.6.2) in `backend/package-lock.json`. fastify before 5.7.2 is affected by CVE-2026-25223 (advisory CVSS 7.5): request body validation schemas specified by Content-Type can be completely circumvented by appending a tab character followed by arbitrary content to the Content-Type header, while the server still processes the body as the original content type. The same CVE applies to the `app-hosting/poc` services, which pin fastify 4.29.1 (below the 4.x fix in the advisory's range).

## Evidence

**Advisory evidence:** `CVE-2026-25223` applies to `fastify` at installed version `5.6.2`. The advisory is fixed in `5.7.2`.

**Usage analysis:** the advisory's vulnerable code runs in this codebase. Entry point: every HTTP request to the backend API — `backend/src/app.ts:57` creates the Fastify instance (`const app = Fastify({...})`) that serves all routes. Package call: Fastify's content-type-parser selects the validation schema from the request Content-Type header, which the advisory says can be bypassed with a trailing tab; this runs on the attacker's request itself, so the vulnerable code executes for any crafted request (no further call needed). Route schemas using this validation exist (e.g. backend/src/routes/workflows.routes.ts:163, :218, :276, :353 declare `schema:` bodies). The mitigating observation is that routes such as workflows.routes.ts:137 wrap handling in a zod `validateSchema` call independent of Fastify's validation, so not every route's validation is bypassable — but the Fastify-layer bypass itself demonstrably executes. The app-hosting/poc services (app-host-api and runtime) pin fastify 4.29.1 with the same advisory applying (fixed in their line at 5.x per the advisory; 4.x itself is EOL and unpatched).

## Impact

Any route that relies solely on Fastify's Content-Type-based body validation accepts unvalidated bodies. In this codebase most route handlers additionally validate through zod `schema.parse` at handler level, which limits the demonstrated impact to routes whose validation exists only at the Fastify schema layer; the exact set of such routes was not exhaustively enumerated. The bypass is remotely triggerable by any unauthenticated client on any JSON route.

## Contextual CVSS

Fastify 5.6.2 is instantiated as the production API server (backend/src/app.ts:57) and its Content-Type routing runs on every request; routes with JSON body schemas exist (e.g. backend/src/routes/workflows.routes.ts:163,218,276,353). The bypass primitive is therefore exercised by any network client sending a tab-suffixed Content-Type. However, the application's routes overwhelmingly validate bodies a second time through zod schemas at handler level (backend/src/routes/workflows.routes.ts:137 validateSchema calling schema.parse before use), and no route was identified whose entire input-validation guarantee rests on the Fastify JSON-schema layer; without a route whose security depends solely on Fastify body validation, the bypass does not yield a demonstrated confidentiality/integrity effect. The same tab-Content-Type bypass also exists in the app-hosting/poc services pinned to fastify 4.29.1 (app-hosting/poc/services/app-host-api and services/runtime package-lock.json), which are PoC-grade code. Metrics reflect the demonstrated-impact rule: N/N/N with the exposure documented.

## Remediation

Upgrade fastify to >= 5.7.2 in backend/package.json (e.g. ^5.12.2, which also covers the other 2026 fastify CVEs) and regenerate the lockfile. For the app-hosting/poc services on fastify 4.29.1, upgrade to the fixed 5.x line or accept that the 4.x line no longer receives security patches. Ensure every mutating route enforces a handler-level zod parse so validation does not depend solely on the framework layer.
