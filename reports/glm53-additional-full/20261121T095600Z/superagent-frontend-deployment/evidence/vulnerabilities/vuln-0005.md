# Hardcoded default admin password 'Admin1234!' seeded and logged by deployment scripts

**ID:** vuln-0005
**Severity:** CRITICAL
**Found:** 2026-11-21 10:02:23 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent (infra deployment scripts)
**CWE:** CWE-798
**CVSS:** 9.8
**Confidence:** Medium
**Fix Effort:** Low

## Description

The deployment scripts seed a default administrator account (admin@example.com / Admin1234!) on every fresh deployment, never force a password change, and echo the plaintext credential into deployment logs. Because the credential is also published in the repository's deployment documentation, anyone who can reach a deployment's login endpoint can gain full admin access on any instance where the operator did not manually change the password.

## Evidence

infra/scripts/ci/remote-deploy.sh:
```
ADMIN_HASH=$(node -e 'require("bcryptjs").hash("Admin1234!", 10).then(h => process.stdout.write(h))')
psql "$PSQL_URL" -c "UPDATE profiles SET password_hash = '${ADMIN_HASH}' WHERE username = 'admin@example.com' AND password_hash IS NULL;"
echo "Admin login: admin@example.com / Admin1234!"
```
Same block (with `sudo` prefixes) at infra/scripts/deploy.sh:418-421. Credential also in infra/README.md:87 and document/fork-deploy-guide.md:274. Seed admin user created at backend/prisma/seed.ts:56.

## Impact

Full administrative takeover of any deployment provisioned by these scripts where the default was not changed: the admin account can read and modify all tenant data, agents, workflows, and platform configuration via the backend API. Deploy-log readers (CI artifacts, SSH session transcripts) obtain the credential even if the operator never read the docs.

## Counterevidence

The password is only set when `password_hash IS NULL` (first boot of a fresh deployment), so environments where an operator completed a password change or where Cognito mode is used exclusively are unaffected. The seed admin may be documented as a bootstrap-only account. However, no forced rotation, expiry, or login-restriction mechanism exists anywhere in the cited scripts, and the credential is echoed verbatim into deployment logs, so the default persists on any unattended deployment.

## Confidence Rationale

Static trace fully verified in source, but no live deployment was available to confirm the admin account with the default password is internet-reachable on a production instance (local-only assessment mandate).

## What Would Change This Severity

Confirmation that these scripts are the actual production/CI deploy path for an internet-reachable instance (rather than a fork/dev helper) would raise confidence to high; evidence that all deployments use Cognito-only auth with local login disabled would lower severity to medium/low.

## Technical Analysis

Both deployment entry points converge on the same behavior. `infra/scripts/ci/remote-deploy.sh` (commented "runs on EC2 via CI/CD pipeline", i.e. the CI/CD path) and `infra/scripts/deploy.sh:418-421` (the unified deploy script, also invoked by `infra/scripts/deploy-full.sh:198`) run `prisma/seed.ts` on a fresh database, which creates the `admin@example.com` profile, then execute `UPDATE profiles SET password_hash = '<bcrypt("Admin1234!")>' WHERE username = 'admin@example.com' AND password_hash IS NULL`. There is no randomization, no forced first-login rotation, and no expiry: any deployment seeded by these scripts keeps the known password until an operator manually changes it. The scripts additionally print the plaintext credential to stdout (`echo "Admin login: admin@example.com / Admin1234!"`), which lands in CI logs and terminal transcripts. The credential is hardcoded in a public-style repository and repeated in `infra/README.md` and `document/fork-deploy-guide.md`, so it is known to anyone who has ever read the docs. The only mitigating condition is the `AND password_hash IS NULL` guard, which limits the overwrite to fresh deployments but does nothing to prevent the default being left in place.

## Proof of Concept

1. Deploy the stack via infra/scripts/deploy.sh or the CI remote-deploy path — the seed creates the `admin@example.com` profile.
2. Observe the deployment log line `Admin login: admin@example.com / Admin1234!` (remote-deploy.sh, echoed to stdout/CI logs).
3. On the deployed instance, log in with these credentials via the local-auth login endpoint.
4. The same credential is documented in infra/README.md:87 and document/fork-deploy-guide.md:274, so it is known to anyone with repository access without reading any logs.

```bash
# Verified in source: infra/scripts/ci/remote-deploy.sh (seed block) and
# infra/scripts/deploy.sh:418-421 set the bcrypt hash of "Admin1234!" for
# admin@example.com whenever password_hash IS NULL, then echo the plaintext:
#   echo "Admin login: admin@example.com / Admin1234!"
# Documented publicly in infra/README.md:87 and document/fork-deploy-guide.md:274.
# Against any deployed instance built by these scripts where the password
# was not rotated:
#   POST /api/auth/login  {"username":"admin@example.com","password":"Admin1234!"}
# returns an admin session. Not executed here (local-only assessment).
```

## Remediation

Generate a random admin password per deployment and deliver it through a secure channel (or require first-boot rotation), never echo credentials to logs, and do not publish default credentials in documentation. Block authentication on the seeded admin account until the password is changed.

## Assumptions

Assumes a deployment where the seeded admin account is reachable (AUTH_MODE=local or local login enabled) and the operator did not change the default password — the script never forces a change and only sets the hash when NULL. Assumes this deployment path is used for internet-reachable instances; an operator who immediately rotates the password reduces this to defense-in-depth.
