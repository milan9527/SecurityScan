# Unauthenticated webhook trigger endpoint allows arbitrary tenant workflow execution (no auth, no HMAC, no replay/rate limit)

**ID:** vuln-0009
**Severity:** HIGH
**Found:** 2026-11-21 10:02:50 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent (backend)
**CWE:** CWE-306
**CVSS:** 8.2
**Confidence:** High
**Fix Effort:** Low

## Description

The webhook trigger endpoint POST /v1/webhook/:webhookId/trigger requires no authentication, no signature, and has no replay or rate protection. Anyone who obtains a webhook_id can invoke the victim organization's workflow arbitrarily many times, consuming LLM/agent execution resources and driving unauthorized state changes.

## Evidence

Local unit PoC `backend/tests/unit/webhook-trigger-authz.poc.test.ts` boots the real webhook trigger route with mocked persistence: an unauthenticated POST (no Authorization header) returns 200 `{received: true, callRecordId}` and the webhook's async execution is dispatched with attacker-supplied variables. Source review confirms no auth/signature/rate guard on the path.

## Impact

Unauthenticated invocation of tenant workflows/agents on demand: attacker-controlled variables flow into agent execution (prompt-injection surface), resource consumption/cost abuse (each trigger runs the workflow, e.g. Claude/Bedrock calls), and record flooding of the victim org's webhook call history. Integrity impact is unauthorized execution of business logic as the tenant; no direct confidentiality impact was demonstrated.

## Counterevidence

Checked for compensating controls: (1) the route has no preHandler, no schema-level security, and no HMAC/signature check anywhere in the trigger path; (2) `triggerWebhook` only enforces the optional IP allowlist and an enabled flag — when `allowedIps` is empty (default) any source passes; (3) no replay protection, nonce, timestamp window, or rate limiter exists on the route or in the service; (4) webhook_id values are unguessable UUIDs, which is the only practical barrier and is enumeration-resistant but irrelevant once any id leaks. The IP allowlist is a genuine control but is per-webhook, optional, and empty by default.

## Confidence Rationale

Complete source trace of the unauthenticated route and the service path, plus a local unit PoC against the real route handler confirming an unauthenticated trigger executes the victim webhook. Only production network exposure is unverified (out of scope).

## What Would Change This Severity

Evidence of an edge/gateway-level auth or rate-limiting layer in front of this route would lower severity; a demonstrated path from trigger variables to sensitive data exfiltration would raise confidentiality impact.

## Technical Analysis

`webhooks.routes.ts:311` registers `POST /v1/webhook/:webhookId/trigger` as a "Public Trigger Route (no authentication required)" with no preHandler. The handler calls `webhookService.triggerWebhook` (webhook.service.ts:135). The service loads the config by webhook_id only (`prisma.webhooks.findFirst({ where: { webhook_id, deleted_at: null } })`), checks only the optional IP allowlist (`config.allowedIps`, empty by default) and enabled flag, records the call, and fire-and-forget executes the workflow (`executeWebhookAsync`) with attacker-supplied `variables`. There is no HMAC or shared-secret verification, no timestamp/nonce replay protection, and no application-level rate limiting on the route.

## Proof of Concept

1. Obtain a webhook_id (any tenant user can create webhooks via the authenticated API; ids are also returned in webhook management responses). 2. POST /v1/webhook/:webhookId/trigger with no Authorization header and body `{"variables": {"anything": "attacker-controlled"}}`. 3. Response is 200 with `{received: true, callRecordId}` and the workflow executes fire-and-forget with the attacker's variables. 4. Repeat indefinitely — no rate limit, no replay protection.

```gdscript
# Unit PoC: cd super-agent/backend && npx vitest run tests/unit/webhook-trigger-authz.poc.test.ts
# Real trigger route, no Authorization header:
POST /v1/webhook/<victim-webhook-id>/trigger
{"variables":{"cmd":"attacker input"}}
-> 200 {"received":true,"callRecordId":"..."}   # workflow queued for execution
```

## Remediation

Require an authentication/authorization check on the trigger route, or implement a per-webhook secret verified as an HMAC signature over the raw body with a timestamp window (as the IM adapters already do for Slack/Telegram/Discord), plus replay protection and a per-webhook/per-IP rate limit. Log and alert on triggers from unlisted sources.

## Assumptions

Network access to the API host and knowledge of any active webhook_id (UUIDs, obtainable via the authenticated API or from the target tenant's own usage). Production exposure and whether rate-limiting exists in front of the service were not verified — no application-level rate limit exists in the reviewed code.
