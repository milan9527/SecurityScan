**Contextual CVSS Vector:** CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:N/A:N

## Description

The backend pins `protobufjs` 7.5.4 in `backend/package-lock.json`, pulled transitively by `@larksuiteoapi/node-sdk` 1.60.0 (the Feishu/Lark IM adapter). protobufjs before 7.5.5/8.0.1 is affected by CVE-2026-41242 (CVSS 9.8): code injection through attacker-controlled `type` fields in protobuf definitions executed during object decoding.

## Evidence

**Advisory evidence:** `CVE-2026-41242` applies to `protobufjs` at installed version `7.5.4`. The advisory is fixed in `7.5.5`.

**Dependency chain:** `@larksuiteoapi/node-sdk@1.60.0 > protobufjs@7.5.4`

**Usage analysis:** the package is loaded, but this advisory's vulnerable code does not run here. Import check: no application code imports protobufjs (rg 'protobuf' across backend/src finds no imports or symbol usage). Resolution chain: @larksuiteoapi/node-sdk@1.60.0 -> protobufjs ^7.2.6, resolved to 7.5.4 in backend/package-lock.json. Affected-symbol check: the advisory's vulnerable code is the handling of `type` fields in protobuf definitions (e.g. `protobuf.parse`/`Root.load`/`Type.fromJSON` on attacker-supplied schema text). Search of backend/src for these symbols and for any .proto loading found no caller; the only consumer of protobufjs in the tree is the Lark SDK's own message serialization against its vendor-fixed schemas, reached via the WSClient message path (backend/src/services/feishu-adapter.ts:320-330 -> SDK internals -> protobufjs decode of vendor-controlled definition). Attacker-controlled message payloads are data to a fixed schema, not schema text, so the injection path does not execute.

## Impact

No application code path passes attacker-controlled protobuf definitions to protobufjs, so the code-injection primitive is not reachable in this codebase as written. The finding documents that a CVSS-9.8-vulnerable protobufjs ships in the production dependency tree; activation would require a future code path that parses externally supplied .proto definitions.

## Contextual CVSS

protobufjs is loaded in the backend process via the Feishu adapter import chain (backend/src/services/feishu-adapter.ts:15 -> @larksuiteoapi/node-sdk -> protobufjs). The advisory's vulnerable symbol is the `type` field of a protobuf definition — i.e. attacker control requires supplying a .proto definition or attacker-chosen schema to `load`/`parse`/`Root.fromJSON`. A complete search of backend/src shows zero references to protobufjs symbols (no load/parse/Root/new Type calls, rg 'protobuf' returns nothing outside unrelated identifiers), and the SDK's vendor protobuf handling uses its own fixed internal descriptors, so this advisory's code-injection path does not execute under any attacker-controlled input in this codebase. All three impact metrics are N as used; the finding documents the shipped-vulnerable-version exposure.

## Remediation

Add an npm override in backend/package.json ("overrides": { "protobufjs": "^7.5.5" }) so the @larksuiteoapi/node-sdk chain resolves a patched protobufjs; verify with `npm ls protobufjs`. No code change is required today.
