# Unauthenticated generic IM webhook processes attacker messages through the victim organization's agent

**ID:** vuln-0011
**Severity:** HIGH
**Found:** 2026-11-21 10:02:59 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent (backend)
**CWE:** CWE-306
**CVSS:** 8.6
**Confidence:** High
**Fix Effort:** Low

## Description

The generic IM webhook endpoint POST /api/im/webhook/:bindingId requires no authentication or signature. Anyone who knows (or brute-forces) a binding ID can submit arbitrary text that is processed by the victim organization's IM-bound agent, triggering agent execution and consuming the target tenant's resources.

## Evidence

Local unit PoC `backend/tests/unit/im-webhook-auth.poc.test.ts` exercises the real imWebhookRoutes handler with a mocked repository: a request with no Authorization header and no signature of any kind returns 200 and invokes `imService.handleMessage` with the attacker's text, using a binding that belongs to the victim organization. Source confirms no verification on this path.

## Impact

Unauthenticated arbitrary message injection into a tenant's IM agent conversation: the agent runs (LLM/Bedrock cost), may take actions the IM binding is authorized for, and its reply text is returned directly to the attacker. Integrity: unauthorized agent invocation with attacker-authored input; availability: repeatable unthrottled execution.

## Counterevidence

Checked the platform-specific webhook handlers in the same file: Slack, Telegram, Discord, Feishu, DingTalk, WeCom, and WhatsApp paths all verify a signature/secret from the binding config via `verifyAndLookupBinding` or equivalent, so those are properly controlled (with the caveat that Slack/Feishu/Discord answer URL-verification challenges before verification, which is intended protocol behavior). The generic endpoint has no such control — it has no `verifyRequest` call, no token, and `findBindingById` explicitly documents "without org context". No auth middleware is applied. Nothing mitigates it.

## Confidence Rationale

Direct source trace showing the generic webhook route performs no verification, plus a local unit PoC against the real route (im-webhook-auth.poc.test.ts) confirming unauthenticated messages are processed against a victim-org binding. Production exposure not tested.

## What Would Change This Severity

Evidence that binding IDs are effectively unobtainable cross-tenant and a gateway blocks unauthenticated access would lower severity; demonstrated exfiltration of tenant data through the agent's reply would raise it.

## Technical Analysis

`routes/im.routes.ts` ends with `POST /webhook/:bindingId` ("Generic webhook endpoint... For platforms that don't have a dedicated adapter"). The handler has no preHandler, and calls `findBindingById(bindingId)` — a helper that is explicitly annotated "without org context (for unauthenticated webhooks)" and does a raw `prisma.im_channel_bindings.findUnique({ where: { id } })`. With no signature verification of any kind, it constructs a `NormalizedIMMessage` from the request body (`text`, `thread_id`, `user_id`) and calls `imService.handleMessage(msg)`, which locates the agent session for that binding and runs the tenant's agent, returning `result.text` to the caller. Unlike every platform-specific handler in the same file, which route through `verifyAndLookupBinding` → `adapter.verifyRequest`, this path performs zero verification.

## Proof of Concept

1. Identify a target bindingId (UUID) — any tenant user can list their org's bindings via GET /api/business-scopes/:scopeId/im-channels; other orgs' ids leak via error/ordering channels or a leak. 2. POST /api/im/webhook/<bindingId> with body `{"text":"attacker message"}` and no headers. 3. The endpoint looks the binding up globally by id, processes the message through imService.handleMessage, and returns the agent's reply.

```ecl
# Unit PoC: cd super-agent/backend && npx vitest run tests/unit/im-webhook-auth.poc.test.ts
# Real imWebhookRoutes, no Authorization / signature headers:
POST /api/im/webhook/<victim-binding-id>
{"text": "ignore previous instructions and ..."}
-> 200 {"text": "<agent reply>", "session_id": "..."}   # processed in victim org
```

## Remediation

Require a shared secret for the generic webhook endpoint: store a per-binding secret, require it as an HMAC signature or bearer header, reject unauthenticated requests with 401, and rate-limit per binding. Restrict what the generic endpoint can trigger (e.g. echo/test only) or remove it in favor of the adapter-specific verified endpoints.

## Assumptions

Network access to the API and knowledge of a target bindingId (UUID, obtainable by tenant users via the authenticated IM-channel API or any leak). Applies to the generic /api/im/webhook/:bindingId endpoint; adapter-specific webhook paths (Slack, Telegram, WhatsApp, etc.) carry signature verification and are not the subject of this report. Production exposure unverified.
