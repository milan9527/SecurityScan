# Authenticated RCE via eval() of workflow custom transform expression

**ID:** vuln-0025
**Severity:** HIGH
**Found:** 2026-11-21 10:06:56 UTC
**Target:** super-agent backend (local repository /workspace/agentcore-superagent-update)
**CWE:** CWE-95
**CVSS:** 8.8
**Confidence:** High
**Fix Effort:** Medium

## Description

The workflow execution engine evaluates attacker-supplied transform expressions with JavaScript eval() without any sanitization or sandboxing. An authenticated user with ordinary 'member' role in an organization can supply a workflow whose action node carries a crafted custom transform expression, execute it, and achieve arbitrary code execution in the backend Node.js process.

## Evidence

PoC ran locally against the real backend module (vitest, node_modules pre-existing, S3/DB mocked): the crafted expression using process.getBuiltinModule('fs').writeFileSync created the marker file on disk, and Object.keys(process.env).length executed with its value returned in the node output — arbitrary code execution confirmed on the vulnerable code path.

## Impact

Full server-side code execution in the backend process: arbitrary file read/write (demonstrated by writing a marker file via fs.writeFileSync), access to the entire process environment (demonstrated by enumerating process.env), and by extension the Postgres/Redis/S3/AWS credentials held by the process. This compromises all tenants' data.

## Counterevidence

Searched for sanitization/containment on the path: nodes are validated only as z.array(z.unknown()) (workflow.schema.ts), and the preHandlers on the execute route are authenticate, requireModifyAccess, enforceTokenQuota — no content filter on node expressions. eval executes in-process, so no vm2/isolated-vm sandbox applies. The only mitigations found are that the attacker must be an authenticated org member with modify access to the workflow, and that sibling paths (applyFilter/applyReduce) happen to be unreachable. No WAF or expression allowlist exists in the code path examined.

## What Would Change This Severity

Confirmation that the workflow execute endpoint is reachable by unauthenticated or self-service-registered users in production would raise severity toward critical; conversely, evidence that transform expressions are filtered by an upstream allowlist not present in this repository would lower it.

## Technical Analysis

`POST /workflows/:workflowId/execute` (backend/src/routes/execution.routes.ts:154) is guarded by `authenticate, requireModifyAccess, enforceTokenQuota`. `requireModifyAccess = requireRole('owner','admin','member')` (backend/src/middleware/auth.ts:280), so any ordinary org member qualifies. The request body's `canvasData.nodes` is validated only as `z.array(z.unknown())` (backend/src/schemas/workflow.schema.ts:48), so node content — including transform configurations — is fully attacker-controlled. During execution the action executor dispatches to `applyCustomTransform` (backend/src/services/node-executors/action-executor.ts:195), which at lines 316-325 substitutes the `data` placeholder and calls `eval(evalExpr)` with the raw attacker-supplied `transformConfig.expression`. There is no allowlist, sandbox, or vm isolation; the code's own comment in the sibling code-artifact executor acknowledges "In production, use vm2 or isolated-vm".

Scope note on the same class: `applyFilter`/`applyReduce` (lines 265, 290) contain equivalent eval sinks but are unreachable from the dispatch switch. The condition-executor's eval is neutralized by a paren-blocking regex. `code-artifact-executor.ts:296` (`const result = eval(code)`) is a second live sink of the same class, currently blocked only incidentally: a top-level `return` in the generated code throws a SyntaxError before eval. Fixing that functional bug without replacing eval re-opens it; any fix must cover both sinks.

## Proof of Concept

1. Authenticate as any user who is a 'member' (or higher) of an organization.
2. Create or edit a workflow whose canvasData contains an action node with a transform config of type 'custom' whose expression is crafted JavaScript.
3. POST /api/workflows/:workflowId/execute with the crafted canvasData.
4. The engine reaches applyCustomTransform, which evals the expression in-process.
5. Observe side effects: a marker file written to disk via process.getBuiltinModule('fs').writeFileSync, and Object.keys(process.env).length returned through the node output — arbitrary code execution confirmed.

```js
// Local PoC (vitest) against the real action-executor module
import { describe, it, expect } from 'vitest';
import { ActionExecutor } from '../src/services/node-executors/action-executor.js';
import fs from 'node:fs';

describe('applyCustomTransform eval RCE', () => {
  it('executes arbitrary code via custom transform expression', async () => {
    const marker = '/tmp/poc_eval_marker.txt';
    const executor = new ActionExecutor(/* mocked context */);
    // expression supplied via workflow node transformConfig.expression
    const expression = `process.getBuiltinModule('fs').writeFileSync('${marker}','pwned') || Object.keys(process.env).length`;
    const result = executor['applyCustomTransform']({ a: 1 }, expression);
    expect(fs.existsSync(marker)).toBe(true);
    expect(Number(result)).toBeGreaterThan(0);
    fs.unlinkSync(marker);
  });
});
```

## Remediation

Remove eval from the transform pipeline. Replace expression evaluation with a restricted, whitelisted transformation DSL or a sandboxed interpreter (e.g. isolated-vm with no host bindings), and validate transform expressions server-side before persisting or executing them. Apply the same treatment to code-artifact-executor.ts:296, which evals node 'code' fields of the same provenance. Ensure workflow canvas node payloads are structurally validated (schema-restricted), not z.array(z.unknown()).

## Assumptions

Assumes the workflow execute route is exposed to authenticated tenant users in production (role 'member' is included in requireModifyAccess). Local runtime validation used the real backend code with mocked AWS dependencies; production deployment exposure is unverified.
