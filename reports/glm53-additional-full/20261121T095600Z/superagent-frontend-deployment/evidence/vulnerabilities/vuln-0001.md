# Missing origin and state validation on OAuth postMessage handler in ConnectorPanel

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-11-21 10:01:50 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent (frontend)
**CWE:** CWE-346
**CVSS:** 4.2
**Confidence:** Medium
**Fix Effort:** Low

## Description

The OAuth callback message listener in the SPA accepts any 'oauth-callback' postMessage without validating event.origin or a state nonce, so any window holding a reference to the SPA can deliver a forged callback and bind the victim's connector to an attacker-chosen credentialId.

## Evidence

Code at frontend/src/components/ConnectorPanel.tsx:264-275 shows `const onMessage = (event: MessageEvent) => { if (event.data?.type !== 'oauth-callback') return; ... const { success, error: oauthError, credentialId } = event.data.payload; if (success && credentialId) { setOauthCredentialId(credentialId) } }` with no reference to event.origin, event.source, or any state/nonce comparison.

## Impact

An attacker page that holds a window reference to the SPA (e.g. an opener, or an adjacent attacker-controlled page) can send a forged `{type:'oauth-callback', payload:{success:true, credentialId:<attacker value>}}` message while a victim initiates a connector OAuth flow. The victim's connector is then configured with the attacker's credentialId, so subsequent agent actions using that connector authenticate with attacker-controlled credentials — a credential-confusion outcome where the attacker acts under the victim's context or observes traffic routed through their credential.

## Counterevidence

The handler gates on event.data?.type === 'oauth-callback', so unsolicited cross-origin messages with other types are ignored, and it is registered only while an OAuth popup flow is in flight and removed on first match — shrinking the attack window to the authorization period. The payload only sets a connector credentialId in local component state; no direct script execution or data exfiltration occurs from the message itself. No other postMessage listener accepting this message type was found.

## Confidence Rationale

Validated by complete static trace of the listener and its data flow; no live deployment or browser-based reproduction was performed, so exploit timing (attacker-reachable reference during the OAuth window) is reasoned rather than demonstrated.

## What Would Change This Severity

Confirmation that third-party pages can routinely obtain a window reference to the SPA (e.g. via the OAuth popup opener relationship or embedded content) would raise this to high; confirmation that credentialId values are strictly server-issued and re-validated server-side before use would lower it.

## Technical Analysis

`ConnectorPanel.tsx` starts an OAuth popup and registers a global `message` listener (`frontend/src/components/ConnectorPanel.tsx:264-275`). The handler filters only on `event.data?.type === 'oauth-callback'` and then destructures `success`, `error`, and `credentialId` from `event.data.payload`, storing `credentialId` via `setOauthCredentialId`. There is no `event.origin` check, no `event.source` check, and no state/nonce correlation with the OAuth request, so the listener trusts any origin that can dispatch a message to the window. The registered credentialId is later used as the credential binding for the connector, so a forged message during the authorization window swaps the binding.

## Proof of Concept

1. As a victim, open the SPA and start a connector OAuth authorization (opens the popup).
2. From a window holding a reference to the SPA (e.g. its opener or an attacker page that window.open'ed it), dispatch `window.postMessage({type:'oauth-callback', payload:{success:true, credentialId:'attacker-controlled-id'}}, '*')` while the flow is pending.
3. The SPA removes the listener and sets the connector credentialId to the attacker-supplied value with no origin check, as shown in ConnectorPanel.tsx:264-275.

```gdscript
// Run in any window holding a reference to the SPA (e.g. `const spa = window.open(spaUrl)`)
// while the victim has an OAuth connector flow pending:
spa.postMessage(
  { type: 'oauth-callback', payload: { success: true, credentialId: 'attacker-chosen-credential-id' } },
  '*'
);
```

## Remediation

Validate `event.origin` against the expected API/popup origin and verify a per-flow state nonce echoed in the message payload (generate a random state before opening the popup, require it in the callback, and reject mismatches). Also confirm `event.source` is the expected popup window.

## Assumptions

Requires a window holding a script-accessible reference to the SPA (opener, embedded attacker-controlled page, or same-origin neighbor) to fire during the OAuth authorization window. No live deployment was available to confirm the attacker-reachable window in production; this is a code-trace finding validated locally by inspection only.
