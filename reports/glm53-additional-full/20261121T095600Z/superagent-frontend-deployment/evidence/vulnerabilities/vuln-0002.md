# Session token passed in URL query string across preview endpoints

**ID:** vuln-0002
**Severity:** LOW
**Found:** 2026-11-21 10:02:00 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent (frontend + backend auth middleware)
**CWE:** CWE-598
**CVSS:** 3.7
**Confidence:** Medium
**Fix Effort:** Medium

## Description

The SPA appends the user's full authentication token as a `?token=` query parameter on preview, PDF, published-app, and static-asset URLs, and the backend explicitly accepts query-string tokens. Session tokens therefore leak into browser history, proxy/server access logs, and Referer headers.

## Evidence

Confirmed construction sites: `frontend/src/pages/Chat.tsx:527` (`...&token=${encodeURIComponent(token)}` for dev-server/file previews), `frontend/src/pages/Chat.tsx:617` (PublishedAppPreviewTab `fullUrl` with `?token=`), `frontend/src/pages/Chat.tsx:634` (`window.open(fullUrl)`), `frontend/src/pages/ProjectBoard.tsx:190-197` (preview-ready handler appending `?token=`), `frontend/src/components/WorkspaceActions.tsx:179-184` (published-app static URL with `?token=`). Backend acceptance: `backend/src/middleware/auth.ts:150-157` reads `request.query.token` and uses it as the bearer token when no Authorization header is present.

## Impact

The user's session token (Cognito ID token or local auth token) is embedded in URLs that are stored in browser history, recorded in web-server and proxy access logs, and can be leaked via Referer headers if such a URL is embedded on a third-party page. Anyone with access to those channels obtains the victim's full session token and can act as the victim against the API until token expiry. No confidentiality/integrity impact is demonstrated without log/history access — this is a token-exposure weakness.

## Counterevidence

Tokens are URL-encoded, and most of these URLs target same-origin API endpoints, limiting passive Referer leakage to cases where the API origin is embedded by third parties (not observed here). The query-token path exists to support iframe/browser-native viewers that cannot set Authorization headers — a functional requirement, not an oversight alone. Backend still validates the token (auth.ts rejects missing/invalid tokens), so exposure requires capture of the URL, not just discovery of the endpoint. No evidence was found that tokens are logged by the backend itself; the leak channels are browser history, intermediary proxies, and Referer headers.

## Confidence Rationale

Complete static trace of every token-in-URL construction plus the backend middleware that accepts ?token=; impact depends on log/history/Referer access that was not demonstrable in the local-only assessment.

## What Would Change This Severity

Confirmation that production fronting infrastructure (CDN, load balancer, API gateway) logs full query strings would raise severity to high; a short token TTL and per-resource single-use preview tokens would lower it.

## Technical Analysis

Multiple frontend components build resource URLs embedding the raw session token read from localStorage (`local_auth_token` or `cognito_id_token`): dev-server and workspace-file previews (`frontend/src/pages/Chat.tsx:527`), the PublishedAppPreviewTab full URL also opened in a new tab via `window.open` (`frontend/src/pages/Chat.tsx:617-634`), PDF raw-file iframes (`frontend/src/pages/Chat.tsx:296-304`), the project-board preview-ready handler (`frontend/src/pages/ProjectBoard.tsx:190-197`), and published-app static links (`frontend/src/components/WorkspaceActions.tsx:179-184`). On the backend, `authenticate()` in `backend/src/middleware/auth.ts:150-157` accepts `request.query.token` as an alternative to the Authorization header, making the query string an authentication channel. Query strings are logged by proxies/servers and stored in browser history, and are sent in Referer headers when the resource URL is embedded elsewhere.

## Proof of Concept

1. Open a chat session with a workspace file preview, a published app, or a PDF file in the SPA.
2. Observe the iframe/img URL, e.g. `${baseUrl}/api/apps/<id>/static/index.html?token=<full JWT>` at WorkspaceActions.tsx:179-184, or the preview URL at Chat.tsx:527/617.
3. Open the browser history for the session — the full token is recorded in the URL.
4. Send the same request with the extracted `?token=` value and no Authorization header — `backend/src/middleware/auth.ts:150-157` accepts it as authentication, proving the URL-carried token is a usable session credential.

```ecl
# After a preview renders, the token is recoverable from history/logs:
# e.g. logged URL: http://<api>/api/apps/<id>/static/index.html?token=eyJhbGciOi...
# Replay without header:
curl "http://<api>/api/apps/<id>/static/index.html?token=<extracted-token>" -i
# -> HTTP 200 (authenticated), because auth.ts:150-157 uses query token
```

## Remediation

Replace query-string tokens with short-lived, single-purpose, HttpOnly-cookie or one-time preview tickets minted for the specific resource URL (e.g. signed download URLs with expiry), and remove `?token=` acceptance from the backend middleware. Where iframe rendering is unavoidable, use a POST-issued temporary cookie or a per-session preview token distinct from the primary session token.

## Assumptions

Attacker must obtain the token from browser history, proxy/server access logs, or Referer leakage; the finding is a code-trace validated locally with no live deployment, so production log retention and Referer exposure are unverified. Tokens here are the SPA's auth tokens read from localStorage (local_auth_token or cognito_id_token).
