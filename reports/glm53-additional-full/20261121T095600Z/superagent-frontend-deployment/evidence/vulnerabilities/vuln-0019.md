# lodash 4.17.21 in backend (CVE-2026-4800 template code injection, not reachable as used)

**Ecosystem:** npm

**CWE:** CWE-94

**Contextual CVSS Vector:** CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:N/A:N
**Fix Effort:** Low

## Description

The backend pins `lodash` 4.17.21 in `backend/package-lock.json` (transitive via langfuse, @fastify/swagger-ui and others). lodash before 4.18.0 is affected by CVE-2026-4800 (advisory CVSS 9.8): the fix for the earlier _.template command injection (CVE-2021-23337) validated the `variable` option but not `options.imports` key names, both of which flow into a `Function()` constructor — code injection when an application passes untrusted input as imports key names, plus prototype-pollution-key inheritance via assignInWith.

## Evidence

**Advisory evidence:** `CVE-2026-4800` applies to `lodash` at installed version `4.17.21`. The advisory is fixed in `4.18.0`.

**Usage analysis:** the package is loaded, but this advisory's vulnerable code does not run here. Import check: no application code imports lodash (rg "from 'lodash'|require('lodash')" over backend/src returns nothing). Resolution chains into the backend tree include langfuse@10.5.0 -> lodash 4.17.21, @fastify/swagger-ui, and prisma-related packages (backend/package-lock.json:9286). Affected-symbol check: the advisory's vulnerable symbols are _.template with attacker-controlled options (options.imports key names / polluted prototype keys). A complete search of backend/src for _.template, template(, or any lodash invocation found no callers; nothing in application code invokes lodash at all — it executes only inside the private internals of the packages that depend on it, none of which expose template compilation on untrusted input in their used code paths here.

## Impact

No code path in this repository calls `_.template` or passes untrusted input to lodash's template machinery, so the code-injection primitive is not reachable as this codebase is written. The finding documents the CVSS-9.8-vulnerable lodash in the production dependency tree; it would only become exploitable if a future/updated dependency began templating with attacker-controlled options.

## Contextual CVSS

lodash 4.17.21 is loaded in the backend process via several direct dependencies' import chains, but no application code imports it (rg "from 'lodash'" over backend/src returns nothing). The advisory's sink is _.template's options.imports key names flowing into a Function() constructor — activation requires application code to call _.template with attacker-controlled options, and a complete search found zero _.template or lodash-template callers in backend/src. The vulnerable symbols therefore never execute under attacker influence here; all impact metrics are N as used. The 9.8 advisory score is retained as the published reference; this report documents the shipped-vulnerable-version exposure only.

## Remediation

Add an npm override in backend/package.json ("overrides": { "lodash": "^4.18.0" }) so all chains resolve the patched lodash; verify with `npm ls lodash`. No code change required today.
