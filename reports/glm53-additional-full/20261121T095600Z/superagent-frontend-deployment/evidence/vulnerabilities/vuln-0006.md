# Authentication forgery family: internal-token HMAC key publicly disclosed, default JWT secret, and query-parameter token acceptance

**ID:** vuln-0006
**Severity:** CRITICAL
**Found:** 2026-11-21 10:02:35 UTC
**Target:** /workspace/agentcore-superagent-update/super-agent (backend)
**CWE:** CWE-287
**CVSS:** 9.8
**Confidence:** High
**Fix Effort:** Low

## Description

The backend's authentication middleware (middleware/auth.ts) can be satisfied by three separately forgeable token classes: (a) JWTs signed with the hard-coded default secret `super-agent-local-dev-secret-change-in-production` that config applies whenever JWT_SECRET is unset in local auth mode; (b) "internal service tokens" whose HMAC key in Cognito mode is derived from the Cognito userPoolId — a value the backend itself discloses unauthenticated at GET /api/auth/config; (c) JWTs passed as a `?token=` query parameter on any route, which leak into logs, referrers, and proxy histories. Each allows impersonating any user, role, and organization.

## Evidence

Local unit PoC `backend/tests/unit/auth-forgery.poc.test.ts` runs the real `authenticate()` from src/middleware/auth.ts with mocked prisma: (1) with JWT_SECRET deleted from the environment, `config.jwtSecret` equals the hard-coded default; (2) a JWT signed with that public default secret and claims of a victim user id / `role: 'owner'` authenticates with `req.user.role === 'owner'` and the attacker-chosen orgId; (3) an `internal.`-format token HMAC-signed with the userPoolId string authenticates without any profile existing in the database; (4) the same forgery succeeds when the token is supplied only as `?token=` query parameter.

## Impact

Complete authentication bypass. In Cognito production mode the internal-token path lets an anonymous attacker who fetched /api/auth/config forge a token for any user id, any role (including `owner`), and any organization, bypassing even the profile-existence check that normal tokens undergo. In local mode (or wherever JWT_SECRET is unset) the default secret allows forging arbitrary local JWTs. Query-param tokens additionally expose valid credentials in URLs. Consequence is full cross-tenant account and privilege impersonation across the API.

## Counterevidence

Actively checked for guards: (1) the authenticate hook performs no separate validation of internal tokens beyond the HMAC — the internal-token branch returns before any profile/membership lookup (auth.ts:170-179), so the profile-existence check that protects Cognito/local JWT paths does not apply; (2) there is no allowlist of callers (e.g. no loopback/private-network check or mutual TLS) on internal tokens; (3) query-token acceptance is not restricted to any path, method, or content-type allowlist; (4) no startup check anywhere enforces that JWT_SECRET is set when AUTH_MODE=local in production (the zod schema silently defaults it). The only mitigating facts are deployment-mode preconditions, noted in assumptions; the default-secret path is only exploitable where JWT_SECRET is unset, and the internal-token path is only exploitable where an attacker can read /api/auth/config and reach the API.

## Confidence Rationale

Every mechanism is a complete, line-cited source trace, and the local unit PoC (backend/tests/unit/auth-forgery.poc.test.ts) forges tokens that pass the real authenticate() middleware. Production exposure of these routes was not tested against a live deployment (out of scope for this assessment), which is the only gap.

## What Would Change This Severity

Confirmation that the API is internet-exposed in Cognito mode would keep this at critical; evidence that /api/auth/config is blocked at a gateway and internal tokens are accepted only from a private network would lower it to high.

## Technical Analysis

Three interacting weaknesses in `middleware/auth.ts` and `config/index.ts`. (a) `config/index.ts:30` defaults `JWT_SECRET` to the hard-coded string `super-agent-local-dev-secret-change-in-production`; `verifyLocalToken` (auth.ts:66-78) verifies any JWT against `config.jwtSecret`, so when the env var is unset every forged local JWT is valid. (b) `INTERNAL_TOKEN_SECRET` (auth.ts:81-83) is `config.cognito.userPoolId` in Cognito mode; `createToken`/`verifyInternalToken` (auth.ts:86-126) HMAC-sign/verify internal tokens with it. `auth.routes.ts:30-40` exposes `GET /api/auth/config` with no authentication, returning `userPoolId` (and clientId, region, domain) — so any anonymous caller can mint a valid internal token for arbitrary `sub`/`orgId`/`role` claims. Critically, the internal-token branch in `authenticate` (auth.ts:170-179) returns immediately with the forged claims and skips the `profiles.findUnique` lookup that normal tokens undergo — no victim account even needs to exist. (c) `authenticate` (auth.ts:129-157) accepts the JWT from `?token=` in the query string on every route ("for iframe/img src"), placing bearer credentials in URLs where they leak via logs, Referer headers, and intermediary caches.

## Proof of Concept

1. (b) Send GET /api/auth/config unauthenticated; response includes `userPoolId`. 2. Build payload `internal.<base64url({"sub":"<victim-user-id>","email":"x@y","orgId":"<victim-org>","role":"owner","exp":<now+3600>})>.<HMAC-SHA256(data, userPoolId) base64url>` — this is exactly `createToken()` in auth.ts. 3. Send any API request with `Authorization: Bearer internal...` — authenticate() verifies the HMAC against the same userPoolId, sets request.user from the payload, and returns before any profile/membership lookup. 4. (a) With JWT_SECRET unset (local mode), sign a jsonwebtoken JWT with the default secret and arbitrary sub/orgId/role claims; it verifies via verifyLocalToken. 5. (c) Send either token as `?token=` on any route — authenticate() accepts it from the query string.

## Remediation

(1) Give internal service tokens their own high-entropy secret (dedicated environment variable), never derive them from the public userPoolId, and restrict their acceptance to a private network path or an explicit allowlist of internal callers; consider a dedicated Fastify plugin/prefix only reachable internally. (2) Remove the default JWT_SECRET from the zod schema and fail startup when AUTH_MODE=local and JWT_SECRET is missing in non-development environments. (3) Remove query-parameter token acceptance in authenticate(); if iframe/img use cases need it, restrict it to a narrow, explicit allowlist of read-only routes and short-lived tokens, and ensure tokens never appear in logs.

## Assumptions

Mechanisms (a) and (c) apply in local auth mode (AUTH_MODE=local, default per config schema) or any deployment where JWT_SECRET is unset. Mechanism (b) applies in production Cognito mode: requires only knowledge of the userPoolId, which the backend itself publishes at GET /api/auth/config without authentication. All paths require network reachability of the API, which is unverified for production (local-only validation).
